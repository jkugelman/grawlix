# Worker data tier — the worker owns the wordlists, main is a thin view

The pipeline worker is the **sole owner of the wordlist data**, and the main thread is a thin, asynchronous view over it. The worker reads each source's text from IndexedDB, parses, rescores, and merges it, builds every scoped view, runs the pipeline, and computes the stats/histograms; main holds no merged or scoped corpus — only the small per-wordlist config and the DOM. This rearchitecture has **shipped**. Its design and the whys behind it now live with the code they describe:

- [`../design.md`](../design.md) § *Cooperative runtime* — the worker-owns-corpus model, why it removed the cold-boot / scope-switch / fetch-import freezes a main-resident corpus left behind, the main-heap / GC payoff, and the windowed flat + grouped result tiers (with the grouped-render freeze root cause: a letter-bank-`*` result is ~53k mostly-small groups, so the group-ROW list — not the chains per group — is what had to be windowed). The transform tier stays fully materialized by deliberate decision.
- [`../worker-protocol.md`](../worker-protocol.md) — the main↔worker contract: data ownership, every message (`syncConfig`, `run`, the windowed `fetchRows`/`fetchGroups`/`fetchGroupChains` fetches, the `editEntry`/`deleteEntry` commands, the per-source `serializeFor`, the `mergeDisk`/`flushEdits` disk-merge commands), the deferred-run queue, and the cancellation/supersession rules.
- [`../design.md`](../design.md) § *Disk sync* — the disk-sync tail: the sync record split into owner-keyed `sync_main_` (handle, main-written) / `sync_worker_` (baseline, worker-written) records, the worker-side My Edits 3-way merge with its two-direction baseline ownership, and the first IDB-record migration (machinery in [`../migration.md`](../migration.md)).

This doc tracks the one piece that has **not** yet shipped: the fetch content-diff. Once it lands, the worker-data-tier rearchitecture is complete and this doc retires.

## Not yet shipped: fetch content-diff

The fetch/import path reprocesses an unchanged wordlist end to end — parse, rescore, and re-merge every entry — even when an automatic background update changed only a handful. The cost should scale with the *diff*, not the wordlist: a 300k-entry list that gains 200 changes should cost ~200 entries' work. That's the common shape of a periodic update (a maintainer adds some entries and retunes some scores; the bulk is untouched), and the payoff is as much *not interrupting the page* as raw speed — patching only the changed norms in place leaves the current search, scroll, and on-screen rows undisturbed, where a full reprocess re-runs the pipeline and repaints.

The mechanism reuses what's already there: main fetches the new text, the worker diffs it against the previous version (an O(n) pass keyed by entry, classifying each as added / removed / score-or-comment-changed), and applies only those changes through the same in-place splice path the `editEntry` / `deleteEntry` commands use — a content-diff fetch is a batch of those splices.

A **diff-size threshold** keeps it from ever costing more than today. The diff is always measured cheaply; above some fraction of the list it's discarded in favor of a full rebuild (one-at-a-time splices lose to a clean batch build once the change set approaches the whole list). A fresh import has no previous version, so it degenerates to the full path behind a near-free "is there a previous version?" check; a wholesale change falls back to a full rebuild after the cheap O(n) scan. So the common "mostly the same" update gets dramatically cheaper and non-interrupting, while the worst cases match today.

Orthogonal to the thread move (it would help on any architecture) and independently shippable; planned after the disk-sync tail.

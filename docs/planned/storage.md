# Disk storage

## What this is

Disk storage lets Grawlix keep its data in a folder you pick on your hard drive, the same way a desktop app does. Pick a folder; from that point on Grawlix saves and loads its settings and wordlists from there. IndexedDB is no longer involved. The folder *is* Grawlix.

Two driving concerns:

1. **Data loss.** A browser crash, a "clear site data" click, or moving to a new computer should not erase years of edits.
2. **Workflow integration.** Construction software (Crossfire, Ingrid, Crossword Compiler, Crosserville) reads wordlists from disk. Grawlix should participate in that loop, not stand apart from it.

Disk storage is one thing the user picks: a folder. There is no second copy in IndexedDB, no bidirectional reconciliation engine, no pending-edits log. One source of truth, on disk.

## What changes when storage is on

- **Storage backend.** Wordlists are read from and written to files in the chosen folder. Settings live in `grawlix.json` in the same folder.
- **IndexedDB is abandoned** in this mode. Without storage configured, today's IDB-backed mode is unchanged.
- **External edits load automatically.** Edit `my-edits.txt` in vim or VS Code, save, and Grawlix's file watcher re-reads it.
- **Cross-tab consistency is free** via the same watcher — tab A writes, tab B re-reads.

The storage layer lives behind an adapter shim; most code is backend-agnostic. The two-mode reality is real but bounded: one branch per read/write site.

## Folder layout

Flat — all files at the root of the chosen folder.

```
my-folder/
├── README.txt
├── grawlix.json
├── my-edits.txt
├── jkugelman.txt
├── xwi.txt
├── stwl.txt
├── broda.txt
├── nediger.txt
├── all-rescored.txt
├── jkugelman-rescored.txt
├── xwi-rescored.txt
├── stwl-rescored.txt
├── broda-rescored.txt
└── nediger-rescored.txt
```

**Raw wordlist files** (no suffix) are read-write. Grawlix loads them on boot; the user can edit them in any text editor. My Edits is the primary case for hand-edits; publisher wordlists are typically updated via Grawlix's Update button, but a manually-dropped newer file gets picked up too.

**Rescored variants** (`-rescored` suffix) are write-only outputs for construction software. Grawlix regenerates them whenever the underlying data or rescore rules change; user edits to a rescored file are silently overwritten on the next regeneration. The filename suffix is the signal — users shouldn't edit these; end of story.

**`grawlix.json`** holds settings: wordlist names, source URLs, rescore rules, enabled flags, scoring tier labels — everything except wordlist content. Loaded on every page load, so hand-edits and restored copies are picked up automatically.

**`README.txt`** is generated by Grawlix on first setup, written in Markdown but named `.txt` for non-techie familiarity. Names each file, says which are editable vs. generated, and explains the cross-device trick.

## Header affordance

Disk storage has one entry point: a button in the header bar, next to Settings.

- **Icon by default.** [Lucide hard-drive](https://lucide.dev/icons/hard-drive) when enabled; [Lucide globe](https://lucide.dev/icons/globe) when not. Both MIT-licensed.
- **A label grows next to the icon after the user's first My Edits entry** — first AtomPopover save, first add-entry, or first My Edits import. That's the moment the user has created state they'd care about losing, so the label appears just in time to be relevant.
- **Wording varies by device type and storage state:**
  - Not enabled, all devices: "In this browser"
  - Enabled, desktop: "On disk"
  - Enabled, mobile/tablet: "On device" (academic — mobile browsers don't currently support FSA)
- **Label dismissal**: open the dialog → back out → label hides, icon stays. No direct ✕ on the label, so the user reads the dialog once before swatting it away.

The same button is the management entry once storage is enabled — pitch surface, then status indicator. Click → storage dialog.

No popups, no nudges, no first-load prompts, no time-based heuristics. The header label after first My Edits entry is the only proactive signal.

## Storage dialog — enabled state

Opens from the header button when storage is on.

```
# Storage

Grawlix wordlists are saved to disk so your construction
software can use them directly. Edits in either place flow
to the other automatically.

📁 grawlix

[Turn off]                                       [Close]
```

The folder chip shows the FSA `.name` (leaf folder name only — FSA doesn't expose the full filesystem path). One action: **Turn off**. To move folders, user turns off → re-enables, pointing at a different folder.

### Turn-off sub-dialog

```
# Turn off storage

Grawlix will stop saving to disk. What about the files?

[Keep files on disk]   [Delete files from disk]
                                       [Cancel]
```

- Delete styled destructively (red).
- Delete removes only Grawlix-managed files (`README.txt`, `grawlix.json`, all `.txt` wordlist files). Other files in the folder untouched.
- Either action triggers a page reload to fresh-default Grawlix. Safer than in-place backend swap.

## Storage dialog — not-enabled state

Opens from the header button when storage is off.

```
# Set up storage

Save your Grawlix wordlists and settings to a folder on
your disk, so your construction software can use them
directly.

  [ New folder │ Existing folder ]

Pick an empty folder. Your wordlists and settings will
move there.
You can create a new folder in the picker.

                              [Cancel]   [Pick folder…]
```

The **Existing folder** tab swaps the description to:

> Pick a folder that already has Grawlix data — for example, one synced from another device via Dropbox.

Both tabs end at the same FSA picker. The tabs convey *intent*, which determines the confirmation dialog that follows.

## Confirmation after picking

Six cells, based on the user's tab choice × the folder Grawlix finds. Identity check: a folder "has Grawlix data" when `grawlix.json` is present at its root.

| Intent ↓             | Empty folder              | Grawlix folder              | Other files                  |
|----------------------|---------------------------|-----------------------------|------------------------------|
| **New folder**       | Confirm migration         | Redirect → use existing?    | Three-button anomaly         |
| **Existing folder**  | Redirect → set up here?   | Diff-only merge dialog      | Error: not a Grawlix folder  |

**Simple confirms** (the three plain cells): straight 2-button dialogs.
- *New folder + empty*: "Set up Grawlix in this folder?" → `[Set up]` / `[Cancel]`.
- *Existing folder + empty*: "This folder is empty. Set up here instead?" → `[Set up here]` / `[Pick different folder]`.
- *New folder + Grawlix folder*: "This folder already has Grawlix data. Did you mean to use it as an existing folder?" → `[Load this data]` (branches into the merge dialog) / `[Pick different folder]`.

**Error** (Existing folder + other files): "This folder has files but isn't a Grawlix folder. Pick a different folder." No Continue option — there's no `grawlix.json` to load.

### Three-button anomaly (New folder + other files)

```
# This folder isn't empty

It has files but doesn't look like a Grawlix folder.

[Pick different folder]   [Create a 'grawlix' subfolder here]   [Add Grawlix files alongside what's here]
```

- **Pick different folder** (primary): the most likely intent — user picked the wrong folder.
- **Create a 'grawlix' subfolder**: Grawlix creates `<picked>/grawlix/` and uses it. Escape hatch for the user who picked Documents and meant to set up inside it.
- **Add Grawlix files alongside what's here** (destructive-styled): proceeds with the picked folder. For users who deliberately want Grawlix mixed with other content.

### Diff-only merge dialog (Existing folder + Grawlix folder)

The interesting case. Grawlix diffs the picked folder against the current IDB state. The dialog displays only what's *different*; silent on whatever matches.

```
# Load Grawlix data from this folder?

These wordlists will be replaced by the folder's version:
  • XWI
  • John Kugelman

My Edits: 3 entries differ — keep ( ○ this device  ○ folder )
                                  [show entries ▾]

                                  [Cancel]   [Load]
```

The minimal case (nothing notable to call out): just the title and the two buttons.

Rules:
- **My Edits**: merged into a single list — non-conflicting entries from both sides survive silently. Same-entry conflicts surface in the dialog as a bulk pick. `[show entries ▾]` expands inline (`BAGEL — this device: 50 | folder: 60`) for transparency, without forcing per-entry decisions. `[Load]` stays disabled until a radio is chosen when conflicts are present.
- **Wordlists matched on both sides**: the folder's version of content + rescore rules wins. Listed under "These wordlists will be replaced."
- **Wordlists only on this device**: kept, added to the folder going forward. Not mentioned in the dialog.
- **Wordlists only in the folder**: loaded. Not mentioned.
- **Settings and scoring rules**: folder wins. Not mentioned even if different.

The dialog is diff-only by design — it stays out of the user's way for everything they don't need to act on, and only surfaces what matters.

**Wordlist identity**: match by name, with `publisherId` as tiebreaker if both sides have one. Edge case: a custom wordlist named the same as a publisher gets treated as the publisher (rare; not worth a separate matching mechanism).

After any success path, Grawlix performs the migration or load, then triggers a page reload.

## The blocking dialog

When storage is configured but the browser doesn't have a live FSA handle, page load is blocked on a modal before wordlist data is shown. This happens routinely in non-installed Chromium tabs (FSA permissions don't persist across sessions there); also after a permission revocation or browser restart.

```
# Open your Grawlix folder

Open the folder named "grawlix" to load your data.

[Open my folder]   [Install Grawlix]   [Use without disk storage this session]
```

(The folder name shown is the leaf name from the last-known handle, persisted to localStorage as a string. We don't have the full path, just the name to remind the user what to look for.)

- **Open my folder**: triggers the FSA grant flow. The user picks the folder; Grawlix loads from disk.
- **Install Grawlix** (Chromium, not yet installed): pitched as "skip this prompt next time, get a real app window." Installation gives Chromium persistent FSA permissions; the blocking dialog never appears after install.
- **Use without disk storage this session**: see below.

The blocking-on-boot pattern is deliberately in-your-face. The alternative — loading Grawlix with empty data and a subtle "click to sync" indicator — has well-known failure modes: users miss subtle indicators, make edits, and discover later their edits went into IDB instead of disk. Blocking the page until the user makes one explicit click eliminates that class of bug.

### Folder unavailable variant

If the user clicks "Open my folder" and the picker returns an error or the folder isn't accessible (drive dismounted, files moved externally), the dialog evolves:

```
# Your Grawlix folder isn't accessible

[Try again]   [Pick a different folder]   [Use without disk storage this session]
```

"Pick a different folder" re-runs the picker — the user navigates to wherever they relocated their folder. The folder name in the FSA handle updates; Grawlix continues. This is also the path for the most common relocation case: user dragged the folder somewhere else in Finder/Explorer; on the next session they re-pick from the new location.

### Use without disk storage this session

Skip loading disk data and proceed as if it were a fresh page load — default tier scale, default publisher wordlists, empty My Edits. IDB blank for the session; any edits made disappear when the tab closes.

This is not a usable read-only or "degraded" mode with a fall-back UI. Building one would be a large surface to maintain. It's an escape hatch for the cases where the user needs Grawlix to load anyway, *without* loading their data and *without* destroying it: folder deleted, drive corrupted, NAS locked out today.

After clicking the option, a persistent banner sits at the top of the page:

```
Disk storage paused for this session — your data is safe in your folder.
[Reload to try again]   [Turn off storage]
```

The session reverts to defaults, but the user has clear off-ramps.

## PWA install

Installation isn't required for disk storage, but it removes the per-session prompt. The pitch is contextual: the install button sits in the blocking dialog itself, where the user is currently paying the friction install removes.

What installation does:
- Persistent FSA permissions in Chromium — the blocking dialog doesn't appear after install.
- Standalone window with dock/taskbar icon.
- Separate OS-level presence (Alt-Tab, app switcher, distinct from browser tabs).

What it doesn't do: pin the app version. The installed PWA still fetches grawlix.wtf on every launch; updates land automatically.

Install pitches outside the blocking dialog (after N sessions, after first import, etc.) are not part of this design. The blocking-dialog moment is the strongest contextual sell available; secondary nudges would be promotional noise.

## Multi-tab and external edits

Two tabs editing the same folder, plus external edits from a text editor, all work through one mechanism: the **file watcher**.

- **Atomic writes.** Every file write uses write-to-temp + atomic-rename (FSA's standard idiom). Two tabs writing the same file simultaneously can't corrupt it; whichever rename lands second wins, but neither produces a half-written file.
- **Suppress-own-tick.** A tab that just wrote a file stamps the in-progress write path; the next watcher tick matching that stamp is ignored. Prevents the read-what-we-just-wrote feedback loop.
- **Cross-tab updates use the same mechanism as external edits.** Tab A writes, tab B's watcher sees an external change, re-reads. The disk is the coordination point — no separate BroadcastChannel.

External edits to My Edits or any raw wordlist file are picked up automatically on save. Rescored variants are write-only outputs; any user edit to one is overwritten on the next regeneration (the filename suffix carries the warning).

Honest caveat: two tabs editing the same file in the same instant produce last-rename-wins. Same model as opening one document in two text editors simultaneously.

## Cross-device via OS sync

**Grawlix ships no cloud code.** Cross-device works because the user's existing cloud-drive client (Dropbox, iCloud Drive, OneDrive, Google Drive) syncs the folder.

Workflow:
1. User picks `~/Dropbox/grawlix/` (or any cloud-synced folder) as their data folder on device A.
2. On device B, the user clicks the header icon → setup dialog → **Existing folder** → picks `~/Dropbox/grawlix/`. The diff-only merge dialog handles whatever's there.
3. From then on, both devices load and save through the cloud-synced folder.

The README.txt covers this workflow explicitly so users discover it without being told. The line "drop this folder in Dropbox/iCloud/OneDrive for cross-device" does a lot of work for one sentence.

No OAuth flows, no per-provider integration. The user already has a cloud client; Grawlix doesn't need to reinvent it.

Caveats:
- **Two devices open simultaneously, both editing**: last-write-wins per file, possibly lost work. Intermittent multi-device with a gap between sessions is fine — cloud clients sync each file's latest version.
- **Conflicting copies**: most cloud clients produce `my-edits (conflict copy).txt` when they can't decide. Grawlix ignores files it doesn't recognize; the user resolves the conflict in their editor.

## Mobile / no-FSA browsers

Disk storage is per-browser, per-device — not per-account. Phone Grawlix has no knowledge of a desktop folder, so the header icon stays in its not-enabled state and the blocking dialog never appears. Mobile Grawlix runs as a normal unsynced IDB-backed tab.

Firefox and Safari on desktop are in the same boat — no FSA support, no disk storage. They get unsynced Grawlix and the option to manually download wordlist files for backup.

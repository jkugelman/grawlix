# Planned: in-memory cross-run result cache (finished runs)

Re-running an expensive pipeline is reflexively wasteful. A complex Umiaq query scans the whole corpus (~1s) and joins before its first tuple; navigate to another tool and back, or re-enter the same query later, and Grawlix pays that cost again from zero. Today the worker retains exactly **one** result per tier and drops it on the next run — so a revisit is always a recompute. Users work around this by juggling browser tabs to stash a query. (User ask: `TODO.md` "Cache Umiaq results".)

This plan retains **finished** results across runs, keyed so that re-entering an identical pipeline against an unchanged corpus serves instantly instead of re-joining. It builds directly on the shipped join/view separation (§1); it is the last un-built piece of that effort. Partial (in-flight) runs are **out of scope** here and recorded as a parked follow-on (§10).

**The cache lives in memory.** An earlier draft weighed in-memory against IndexedDB as the central open decision; that decision is made. In-memory is the far smaller change, reprojects for free, and reuses the object-identity staleness signal the worker already computes — dodging the durable content-signature that an IDB variant would have to design and keep correct. IDB's unique wins (survive a reload, serve a single-list result cross-scope) are secondary to the dominant pain (revisit within a session after tab-hopping between tools), so IDB is parked as a possible later **L2** durability layer beneath this **L1** (§11), not built now. §4 records the rationale.

Scope in one line: **retain any finished result whose run cost ≥ a time floor and whose footprint ≤ a byte ceiling; bind each to the corpus object it was built against; validate on a hit with an object-identity test plus the `replaced` splice signal; evict by cost-aware (GreedyDual) LRU under a byte budget.** No tool-tier taxonomy, no generation counter.

## 1. The foundation this builds on (already shipped)

The join/view separation is in place, so most of the machinery already exists — this plan adds a retention layer around it, not a new result model. All anchors below were re-verified against current `worker.js`.

- Each tier retains its result in a single mutable **display slot** — `lastFlatResult` / `lastGroupedResult` / `lastTransformResult` ([worker.js:124-126](../../site/src/engine/worker.js#L124); the inline comments there are terse). The live shapes are richer: the flat slot literal at [worker.js:366](../../site/src/engine/worker.js#L366) is completed by the assignments at [worker.js:374-376](../../site/src/engine/worker.js#L374) into `{ runId, version, indices, join, scope, viewSpec, highlighters, familySort, histogram, widthHints, stats }`. The **join** is every produced row/group/chain, unfiltered and order-agnostic; the **view** (`indices`/`groups`/`chains`) plus `histogram`/`stats`/`widthHints` are the sorted+filtered, **score-derived** projection.
- A **view change** (sort, score-range) **reprojects** over the retained join — it re-derives the view and ships a `reprojected` snapshot without re-running the pipeline ([`handleReproject`, worker.js:563](../../site/src/engine/worker.js#L563); the per-tier reprojectors [`reprojectFlat`/`reprojectGroup`/`reprojectTransform`, worker.js:578-605](../../site/src/engine/worker.js#L578)). **All three tiers already reproject** — flat is not special (flat's join is `_i` **indices** into `corpus.entries`; grouped/transform joins hold direct object references; both reproject). The emitters build the join incrementally and adopt-on-terminal (streaming is authoritative).
- The three slots are **mutually exclusive** and nulled/overwritten on the next run — the emitter's first batch nulls the other two ([worker.js:367-368](../../site/src/engine/worker.js#L367), [462-464](../../site/src/engine/worker.js#L462), [529-531](../../site/src/engine/worker.js#L529)), and a config change nulls all three via `releasePriorCorpus` ([worker.js:1778-1784](../../site/src/engine/worker.js#L1778)). **That single-slot-nulled-on-next-run/config-change is exactly what the cache generalizes: a keyed `Map` of N finished joins that outlives the display slots, with a hit re-populating a display slot from the Map.** The `retainedDiffs` map ([worker.js:132](../../site/src/engine/worker.js#L132)) is a working precedent for a worker-owned keyed retention map with its own lifecycle.
- The worker owns its corpora: `ownedMerged` (the eager self-built MERGED corpus, held regardless of active scope, [worker.js:137](../../site/src/engine/worker.js#L137)) and `ownedCorpus` (the active-scope corpus, [worker.js:138](../../site/src/engine/worker.js#L138)); for MERGED scope `ownedCorpus === ownedMerged`. Reads gate on `ownedCorpusFresh` + `ownedScope === scope` ([worker.js:159](../../site/src/engine/worker.js#L159), [565](../../site/src/engine/worker.js#L565)) — a **necessary but not sufficient** validity check for the cache (§5).
- A structural in-place corpus edit runs through [`spliceOwnedCorpus`, worker.js:1298](../../site/src/engine/worker.js#L1298), which returns a **`replaced`** flag: `false` when the splice reconciled onto the existing row objects in place (`old.score = r.score`, [worker.js:1323](../../site/src/engine/worker.js#L1323), membership + positions intact, `_i` not restamped), `true` when it spliced the array and swapped row objects ([worker.js:1329-1331](../../site/src/engine/worker.js#L1329), membership changed, `_i` restamped). **`replaced` is the structural signal the cache's invalidation hooks (§5).**

## 2. What is cached — and the admission rule

**The unfiltered join, and nothing view-derived.** For each retained result keep its **unfiltered join** (the tier's authoritative row/group/chain set), a reference to its **bound corpus** (§5), and the metadata to rehydrate a display slot (`scope`, `stack`, `laneKind`, `capped`). The `viewSpec` and every **view- or score-derived** field — the sorted/filtered view (`indices`/`groups`/`chains`), `histogram`, `stats`, `widthHints` — are **not** retained as authoritative: a `replaced === false` score splice (§5) mutates the join's scores in place under the retained objects, so those fields must be **recomputed from the join on every hit** (O(join), cheap — the same reproject the worker already does). The revisiting run supplies its own sort/score-range. Everything downstream of the display slot (`fetchGroups`, `fetchGroupChains`, export) is unchanged.

**The cache is tool-kind-blind.** An earlier draft cached the grouped/tuple/transform tiers and skipped flat. That split is dropped, because the properties it stood in for are per-tool, not per-tier:

- **"The buffered tiers are bounded" is false in general.** A tuple result is capped only because *Umiaq* caps it (`numResults`, [umiaq.js:376](../../site/src/engine/umiaq.js#L376); `capped`, [umiaq.js:458](../../site/src/engine/umiaq.js#L458)) — the cap lives in the tool, not the tier. A future tuple or transform tool need not cap, and a transform's output size is whatever that transform emits. Boundedness is a property of a specific tool.
- **"Flat is corpus-position-coupled, so exclude it" does not survive the invalidation model.** Flat's `_i` indices ([`buildFlatRows`, worker.js:750](../../site/src/engine/worker.js#L750), resolving `corpus.entries[indices[i]]`) only go stale on a *structural* (`replaced === true`) change — which is exactly what §5 invalidates on, for **every** tier. The flat slot is already reprojectable and structurally uniform with the others.
- **"Flat is cheap, so skip it" is subsumed by the time floor.** A sub-second flat run never clears the floor, so it is excluded on cost grounds without naming a tier — and baking "flat is cheap" into the design would mis-handle a future slow flat tool. Kind is orthogonal to speed.

So kind drops out entirely. A run is cached iff it clears an **admission rule** with two absolute parts (§7 explains why both are irreducible):

- **Time floor** — the run's wall-clock compute time (dispatch → streamed terminal) ≥ `RESULT_CACHE_MIN_MS` (start at **5000 ms**). Fast runs regenerate faster than they are worth retaining; the floor is also the only force that keeps the cache from filling just because slots are free.
- **Byte ceiling** — the estimated footprint of the **retained unfiltered join** (§7 — *not* the shipped window; a transform join is the whole frozen `seen` set, a grouped join every group's full chain list) ≤ `RESULT_CACHE_MAX_ENTRY_BYTES` (a fraction of the total budget). A RAM-safety cap that refuses any single result too large to hold, independent of how valuable it is (jetsam prices peak bytes, not recompute-time saved).

A capped/truncated result is cacheable but records its `capped` flag so a served entry renders the trailing `+` truthfully (§6, §14).

## 3. Where it lives, physically

A `Map<key, retainedEntry>` the worker owns, holding the live join objects — no longer nulled on the next run or config change. It is **separate from** the three display slots (`lastFlatResult` etc.): the slots remain the transient render state, and a hit re-populates the matching slot from the Map. Each entry carries the join, a **reference to the corpus object it was built against** (`ownedMerged`, or a scoped `ownedCorpus`), the rehydration metadata + `capped`, and its bookkeeping fields (`elapsed`, `bytes`, GDS priority `H`). `retainedDiffs` ([worker.js:132](../../site/src/engine/worker.js#L132)) is a working precedent.

## 4. Why in-memory, not IndexedDB

The two are not just "RAM vs disk" — they force different designs, and for **finished, bounded, in-session** results the in-memory side wins decisively:

| Axis | In-memory (chosen) | IndexedDB (parked, §11) |
|---|---|---|
| **Serialization / format** | None — retain the live join objects the slots already hold | Encode to self-contained rows (`encodeChain`/`encodeGroup`/`encodeGroupFull`, [worker.js:1071-1104](../../site/src/engine/worker.js#L1071)) on write, decode on read — a real format layer |
| **Validity signal** | Object identity + the `replaced` splice signal the worker already computes | A durable content-signature (hash of sources + rules + order + scoring + asset versions) — new design work, incl. the My Edits wrinkle |
| **Reproject on hit** | Free — the entry *is* the live reprojectable join | Decode + rehydrate the slot first, then reproject |
| **Hit latency** | Synchronous pointer-swap + O(join) reproject | Async `idbGet` + decode |
| **Memory** | Holds N joins in RAM — jetsam-counted, competes with the ~100 MB corpus + ~100 MB assets | Disk-backed — does not count against the iOS jetsam budget |
| **Survives reload / respawn** | No — lost on reload or worker crash; repopulates cold | Yes |
| **Cross-scope serving** | Only while the result's corpus object is resident (§5): a merged join survives scope detours (`ownedMerged` is stable across `setScope`), an inactive single-list scope's does not | Self-contained — servable whenever the signature matches |
| **New machinery** | Small — a `Map`, stop nulling, an identity test + a `replaced`-hook purge, a byte-estimate GDS/LRU, a `result`-shaped hit reply | Larger — record family, signature computation, async probe, decode/rehydrate, byte accounting |

The decisive facts: the memory worry is milder than an earlier partial-inclusive framing implied (a finished result that cleared the byte ceiling is bounded by construction, so N of them is tens of MB, not a second corpus), and the durable signature is IDB's largest open risk — it must capture *everything the result is a pure function of* or it silently serves stale. In-memory sidesteps the signature entirely by reusing object identity. IDB's unique wins are reload-survival and cross-scope single-list serving; both are secondary to the in-session revisit, and both can be added later as an L2 without disturbing the L1 design (§11).

## 5. Validity and invalidation

The key is **`(pipeline-signature, scope)`**:

- **pipeline-signature** — the serialized tool `stack` that already crosses on `run`, JSON-stringified. Purely-view fields (sort, score-range) are excluded — they ride separate `run` fields and reproject on a hit, so two revisits with different sorts hit the same entry. Note the pre-search cache's `lastUserStackSig` drops the trailing search row ([worker.js:229](../../site/src/engine/worker.js#L229)); the result-cache key wants the **whole** stack including the search.
- **scope** — `MERGED_ID` or the scoped source's `dbKey`, already retained per result.

The third question — proving the corpus hasn't changed under the entry — needs **no generation counter and no signature**. Each entry is **bound to the corpus object it was built against** and is servable only while that object is the resident, structurally-intact corpus. Two mechanisms enforce this, because the worker's corpus lifecycle changes a corpus in two different ways:

**Rebuild → invalidate by an explicit object-identity test.** Any config change that routes through `resyncWorkerConfig` rebuilds the owned corpus as a **new object** ([`releasePriorCorpus()` then `ownedMerged = buildScopeCorpus(...)`, worker.js:2011-2022](../../site/src/engine/worker.js#L2011)): enable/disable, reorder, a **rescore-rule edit** (traced: `setWordlistRescoreRules` → `applyRescoreRulesChange`, [persist.js:118](../../site/src/data/persist.js#L118) → `repaintAfterCacheChange` → the `cacheVersion$` render effect → `resyncWorkerConfig`, [rendering.js:125](../../site/src/ui/rendering.js#L125) — a full rebuild, **not** the splice path), a scoring-tier change, and a user-initiated fetch/import (`configChanged` branch, [actions.js:624-632](../../site/src/app/actions.js#L624)). The serve-time check is therefore an **explicit identity test** — `entry.corpus === (entry.scope === MERGED_ID ? ownedMerged : ownedCorpus)`. The existing scope-freshness gate (`ownedCorpusFresh && ownedScope === entry.scope`, [worker.js:565](../../site/src/engine/worker.js#L565)) is **necessary but not sufficient**: after an *in-scope* rebuild it still passes (`ownedScope` stays `MERGED_ID`, `ownedCorpusFresh` is re-set true at [worker.js:1764](../../site/src/engine/worker.js#L1764)) while the entry points at the discarded old object — so identity, not the gate, is what catches the swap. This replaces the display slots' current invalidation (`releasePriorCorpus` nulling them, [worker.js:1778](../../site/src/engine/worker.js#L1778)). It is coarse (any such change drops the affected scope's entries) and **correct** — each genuinely changes the result — and it is not the rejected global counter: keyed to the corpus object, a rebuild of scope A's corpus never touches an entry bound to scope B's.

**Proactively purge on rebuild — don't just let stale entries age out.** A stale entry still occupies the byte budget and skews GDS `H` (§7) until an identity-miss at serve time. So on a corpus rebuild, immediately drop every entry whose bound corpus was just replaced. Only `ownedMerged` and the edited source's scoped `ownedCorpus` are ever spliced/rebuilt by an edit ([`applyOwnedEdit`, worker.js:1359, 1365](../../site/src/engine/worker.js#L1359)), so the purge targets exactly those scopes' entries.

**In-place splice → keep or purge by `replaced`.** The two operations that mutate the owned corpus in place rather than rebuilding it — `editEntry`/`deleteEntry` (My Edits) and a background score-only `applyFetched` — run through [`spliceOwnedCorpus`](../../site/src/engine/worker.js#L1298) and expose `replaced`. **Object identity cannot catch these:** the splice mutates the *same* `ownedMerged` object in place (it splices the array, it does not replace the object), so `entry.corpus === ownedMerged` still holds. This is precisely why the `replaced` hook is required *alongside* identity, not subsumed by it.
- `replaced === false` (score/comment edit, membership + positions intact): the existing entry objects are mutated in place (`old.score = r.score`), and because a retained join holds `_i` indices / references into that same corpus, its projection re-reads the new scores. **Keep the entry** — but the next hit must **recompute** its score-derived view + histogram, since the stored ones predate the mutation (§2, §6). This score-only-KEEP path is confirmed shipped (the `reprojectMergedScroller(true)` branch after a splice ack, [actions.js:645](../../site/src/app/actions.js#L645)).
- `replaced === true` (add/delete entry): the array was spliced and `_i` restamped, so a flat join's indices and grouped/transform joins' object references now name the wrong rows. **Purge** the affected corpus's entries; a fresh run repopulates.

**Scope detours.** A merged entry survives a detour to another scope and back: `setScope` rebuilds only `ownedCorpus` and never touches `ownedMerged` ([worker.js:1915-1922](../../site/src/engine/worker.js#L1915)), which is reused on return to MERGED — so the merged entry's bound object stays identical and the identity test passes. A single-list scoped `ownedCorpus`, by contrast, is a **fresh** `buildScopeCorpus` object on every entry into that scope, so a single-list entry fails the identity test after any scope-leave — correctly unservable (and purged when its scope is torn down). **v1 favours the merged scope** (where the dominant pain lives) and treats single-list entries as best-effort. Cross-scope serving of a non-resident single-list result is the one case that *would* need durable change-detection — parked with the IDB L2 (§11).

There is **no global generation counter** — staleness is a scope-precise, object-identity fact, consistent with the worker's shipped local-staleness discipline.

## 6. Serving flow

The cache is a retention layer *around* the existing display slot, so the run path gains a load-before-compute and a save-on-finish; nothing downstream changes.

1. **On `run`** for `(stack, scope)`: a synchronous `Map` get. On a hit, apply the §5 **identity test** (`entry.corpus === resident corpus for entry.scope`, with `ownedCorpusFresh` guarding an in-flight rebuild). A miss on identity is a cache miss → compute.
2. **Hit:** re-populate the tier's display slot from the entry, set its `viewSpec` to the run's requested sort/score-range, and **reproject the retained join against the entry's bound corpus, recomputing the view *and* every score-derived summary** (histogram/stats/widthHints — force `recomputeHistogram`; see [`reprojectFlat`, worker.js:584](../../site/src/engine/worker.js#L584)). Never ship the *retained* view or histogram: a `replaced === false` score KEEP (§5) may have moved them. Then ship a **`result`-shaped message**, not a reproject snapshot — a cache hit is a completed (non-streamed) run, and only the terminal `result` carries `capped`, `existsInScope`, and the `rebindQuery`/`rebindEntry`/`rebindExists` echoes ([`postResult`, worker.js:627-687](../../site/src/engine/worker.js#L627); the reproject snapshots carry none of them). `capped` is retained on the entry; the exists/rebind echoes are live `ownedCorpus.byNorm`/`byKey` lookups ([`resolveRebindExists`, worker.js:1184](../../site/src/engine/worker.js#L1184)) recomputed at hit time against the (identity-matched) resident corpus. So a hit reuses the existing **`result`** channel and `materializeResult` ([pipeline-worker.js:372](../../site/src/ui/pipeline-worker.js#L372)) — **no new message *type* and no new client path, but not the reproject channel** the earlier draft named. Re-base the entry's GDS priority (§7).
3. **Miss:** run as today. **On the streamed terminal** (finished only — never a mid-stream partial, never a superseded run), if the run cleared the admission rule (§2, elapsed ≥ floor ∧ join-bytes ≤ ceiling), insert the live join under the key, bind it to the corpus object, record `elapsed`/`bytes`/`capped`, and update byte accounting + eviction (§7).

Only the **terminal** writes the cache — consistent with "streaming is authoritative, completion is bookkeeping" ([`docs/worker-protocol.md`](../worker-protocol.md)); a cache hit takes the same non-streamed-terminal path that path already sanctions for a result too small to have streamed.

## 7. Admission and eviction

Admission and eviction answer three orthogonal questions; each mechanism answers exactly one, and none subsumes another:

| Question | Mechanism | Kind |
|---|---|---|
| Is there enough recompute time to bother saving? | `elapsed ≥ RESULT_CACHE_MIN_MS` (≈5 s) | absolute floor |
| Will one entry crowd out the whole budget? | join-`bytes ≤ RESULT_CACHE_MAX_ENTRY_BYTES` | absolute cap |
| Under contention, which entry wins a slot? | GreedyDual density `elapsed / bytes` | relative order |

**Why the floor and the ceiling are irreducible** (not crude stand-ins for a fancier single rule): the cache exists to save *time*, so "is there enough time to bother?" is a question about the numerator alone — a 100 ms run producing one byte has near-infinite density yet is worthless to cache, so no density threshold can replace an absolute time floor. And jetsam prices *peak bytes*, not time-saved, so a genuinely expensive but huge result (high density) must still be refused — a constraint that a density metric, which by definition trades time against bytes, structurally cannot state. The floor and ceiling are precisely the two absolutes GDS's relative ordering presupposes.

**Eviction: byte-bounded GreedyDual-Size.** Keep a running byte total and a global aging `clock`. Each entry's priority is `H = clock + elapsed / bytes` (recompute-seconds saved per byte held — the cache's actual objective). On insert or hit, set `H = clock + elapsed/bytes`; when a write would exceed the byte budget, evict the entry with the smallest `H` and advance `clock` to the evicted `H`. This blends cost and recency in one number: an expensive entry earns longevity, but the rising clock eventually sinks one that is never revisited, and a re-access re-bases it. The set is small (tens of entries after the floor), so a linear scan for min-`H` is free and no heap is needed. GDS with the aging clock subsumes plain LRU-by-access, so there is no separate recency policy to run.

**The byte estimate prices the retained join, not the shipped window.** `bytes ≈ join-size × a per-shape constant`, stamped at insert — where join-size is the whole unfiltered set: the transform join is the frozen `seen` set ([worker.js:531](../../site/src/engine/worker.js#L531)), the grouped join holds every group's full chain list, both of which can dwarf the `FIRST_WINDOW` slice actually shipped. Because only admitted (sub-ceiling) results are stored, this estimate is a reliable governor.

**Staging.** Ship the floor + ceiling + GDS as above; carry `elapsed`, `bytes`, `H` on every entry from day one. If GDS ever proves not worth its subtlety, `H = clock + elapsed` (cost without the byte weighting) or even plain recency is a one-line comparator swap — eviction policy is **never a correctness concern** (a bad eviction only forces a recompute, never a wrong result), so this knob is tunable post-hoc with zero risk.

**Deferred elegance (not v1).** Two refinements are known and deliberately skipped: (a) *unified admission* — admit a candidate only if it would beat the entry it displaces (the TinyLFU/GDSF "compare candidate to victim", with a zero-byte sentinel at the floor priority unifying the full and underfull cases); over a tens-of-entries cache the floor already suppresses admission churn, so it buys little. (b) *Pressure-adaptive floor* — raise `RESULT_CACHE_MIN_MS` as the cache approaches its byte budget, turning "stay under budget" from a hard cap into a continuous restraining force. Add either only after watching the fixed floor behave.

## 8. Disposable derived data

The result cache is **derived and disposable** — every entry is recomputable from the corpus — so it is **exempt from the migrate-don't-wipe policy** ([`docs/migration.md`](../migration.md)) that governs canonical stored data. On any invalidation (§5) the entry is simply dropped and recomputed; no migration step, no `SCHEMA_VERSION` involvement (the cache is never persisted). The canonical corpus text and metadata are untouched by this feature. On worker respawn the in-memory cache is lost (as the display slots are today) and repopulates cold.

A hit ships a **`result`-shaped message** (the non-streamed-terminal path) so it carries `capped`/`existsInScope`/`rebindQuery` — reusing the existing `result` channel and `materializeResult`, **no new message type**. It is *not* a reproject snapshot.

## 10. Parked: caching partial (in-flight) runs

Explicitly **out of scope**, recorded so the thinking isn't lost. Partial runs are *not* less valuable than finished ones — value tracks how much the user **invested** in a run (a 60-second, 4000-row Umiaq run they scrolled through is worth more than a completed keystroke-artifact), not whether it completed. Completion only determines *storage cost and shape*. Two real workflows want partial retention: iterative query editing where the user judges a query from its first screenful and backtracks without letting it finish, and explicitly setting a slow run aside to detour through another tool, then restoring it and **continuing** past where it was.

Two mechanisms, at different cost points:

- **Partial output cache (cheap).** Retain the streamed partial *output* (the rows already produced) keyed like a finished entry; on backtrack, redisplay it instantly. Bounded like the finished cache. Covers "backtrack to a query I glanced at" — but cannot continue the computation.
- **Parked coroutine (expensive, memory-unmeasurable).** Suspend the tool's continuation at a cooperative yield point (JS async functions/generators already capture their full internal state for free) and resume it later. The *only* mechanism that continues an unfinished expensive scan without redo. Its costs: it pins the unbounded *working set* (far larger than the bounded result), JS gives no way to *measure* a suspended continuation's retained heap (so a byte-bounded LRU can't govern it), and it rewrites the load-bearing "a superseded run posts nothing and aborts" invariant.

If pursued, the safe shape is **investment-gated**: park a coroutine only when the run invested enough (produced ≥ N rows, active ≥ T seconds, or was *explicitly* set aside) — so the 99% of per-keystroke partial runs never qualify — with a small count cap and **investment-weighted** (not recency-based) eviction. A parked coroutine is invalidated by a structural corpus change (it closed over the corpus), composing with the finished cache's invalidation. Umiaq resumability specifically: the *probe* path (a linear pool scan) resumes cleanly from a cursor; the *bucket* path's expensive Phase 1 is a monolithic buffer with no partial emits, so mid-Phase-1 there is nothing to resume and a restart re-pays it.

## 11. Parked: IndexedDB durability as an L2

IDB is not rejected — it is deferred as a durability upgrade beneath the in-memory L1, to be added only if reload-survival proves worth its weight. The encoders already produce the serializable form (`encodeChain`/`encodeGroup`/`encodeGroupFull`, [worker.js:1071](../../site/src/engine/worker.js#L1071)), and the worker already opens `grawlix`/`data` with `idbGet`/`idbPut`/`idbDelete`. An L2 would hold a `result_<key>` record family: the **encoded** join + rehydration metadata + a durable **corpus-signature**, with a byte-accounting record. A hit `idbGet`s, decodes, rehydrates the slot, and reprojects; L1 fronts it so the common in-session revisit stays a synchronous pointer-swap.

The L2's whole burden is the **corpus-signature** — validity across a reload, where object identity is meaningless. It must capture *everything the result is a pure function of* or it serves stale:

- Enabled sources' content + rescore rules + merge order + scoring tiers. Durable material exists per source (`fetchedSize`, `lastUpdated`, [persist.js:25-26](../../site/src/data/persist.js#L25); `rescoreRules`; enabled + position) — a manifest hash over those is a strong content proxy. **My Edits is the wrinkle** — edited in place every keystroke without a natural size/timestamp bump, so its contribution needs a real content hash or a monotonic edit stamp.
- **Data-asset versions for asset-dependent tools.** A tool declaring `def.asset` (e.g. Space-out → the unigram corpus) is a pure function of that asset too, and assets refresh independently. `DATA_ASSETS` carry a stored content-length ([assets.js:17](../../site/src/engine/assets.js#L17), `sizeIdbKey`) usable as a version; the signature must fold in the referenced assets' versions.

An L2 cache record is derived/disposable like L1: on a signature or format-tag mismatch it is dropped, with **no `SCHEMA_VERSION` bump on the cache's account** — records carry their own format tag. Cross-scope single-list serving (§5) falls out of the L2 for free, since a signature match is servable regardless of the resident corpus.

## 12. Rejected / superseded alternatives

- **Tool-kind (tier) admission** — caching by `laneKind` and excluding flat. Superseded (§2): the properties it proxied (boundedness, cost, coupling) are per-tool or handled uniformly by the invalidation model, so kind is orthogonal to the real admission axes (time, bytes).
- **The scope-freshness gate as the sole validity check.** Insufficient (§5): `ownedCorpusFresh && ownedScope === entry.scope` still passes after an in-scope rebuild that swapped the corpus object, so it would serve stale. An explicit `entry.corpus === resident` identity test is mandatory.
- **A global `structuralGeneration` counter** as the key's generation. Never adopted — it over-bumps across scopes (a background update to list A falsely marks a list-B result stale). Object-identity binding (§5) is scope-precise and needs no counter. (Confirmed absent from the codebase.)
- **Retaining corpus-coupled joins in IDB** (`_i` indices, or live entry-object references). Neither survives serialization/reload — indices are position-encoded against a specific build, references don't serialize. This is *why* an IDB L2 must encode to self-contained rows (§11); it is not a reason against caching in memory, where the live join and its corpus reference are exactly what makes reproject free.
- **Patch-in-place of a cached result on a structural corpus change.** Out — a combination result can gain a member from an added entry partnering an existing one; an incremental patch misses those. `replaced === true` → invalidate → recompute is the correct tool (the same reasoning that makes combination tiers pin-and-chip under refresh-on-consent).

## 13. Uncertain — decide during implementation

- **Byte budget and footprint-estimation grain.** The total budget (`RESULT_CACHE_MAX_BYTES`, low tens of MB — jetsam-counted alongside the ~100 MB corpus + ~100 MB assets), the per-entry ceiling, and the per-shape byte constants for the **join** estimate (§7). Start conservative (e.g. total 32 MB, per-entry ceiling a quarter of that) and tune against measured join sizes.
- **Time floor value.** Start `RESULT_CACHE_MIN_MS = 5000`; confirm it sits above keystroke artifacts, reprojects, and flat runs (all sub-second) while catching the moderately-heavy joins users tab-hop away from.
- **Scope-detour serving.** Confirm a merged entry survives `setScope` detours (bound `ownedMerged` stays identical on return) and that an inactive single-list-scope entry fails the identity test rather than resolving against the wrong resident corpus.
- **Threading the bound corpus through reproject.** `reprojectFlat`/`buildFlatRows`/`corpusFor` currently hard-read `ownedCorpus`/`r.pinnedCorpus` ([worker.js:579, 693, 398](../../site/src/engine/worker.js#L579)). Functionally the entry's bound corpus equals the resident one once the identity gate passes, but the reproject helpers should take the corpus explicitly rather than assume the global — decide how invasively.

## 14. Verify during implementation

- **Re-anchor every `file:line` above against current code first.** These were verified during this rewrite (a prior draft's anchors were off by a few lines each), but code moves.
- **A cache hit must equal a fresh run**, byte-for-byte in the shipped rows, under the same `viewSpec` — including sort/filter reproject over the retained join, group `+N more` paging, and export. **And it must carry the `result`-only fields**: `capped` (trailing `+` renders identically), `existsInScope`, and the `rebindQuery`/`rebindEntry`/`rebindExists` echoes — a hit that ships a bare reproject snapshot drops them.
- **Validity is an identity test, not the scope gate.** After an in-scope rescore-rule edit / enable / reorder / tier change, the same-`(stack, MERGED_ID)` entry must **miss** — assert it does not serve the pre-edit rows even though `ownedScope`/`ownedCorpusFresh` are unchanged.
- **Invalidation is exercised per §5**: rebuild changes (enable/disable, reorder, rescore-rule edit, scoring-tier, user fetch/import) → identity miss + proactive purge. A My-Edits **score/comment** edit and a background **score-only** fetch (`replaced === false`) → the entry is **kept**, and the next hit **recomputes** its histogram/stats (assert the served histogram reflects the new scores, not the stored one — this is the subtle half). A My-Edits **add/delete** and a **structural** fetch (`replaced === true`) → the entry is purged.
- **Terminal-only writes**: never cache a mid-stream partial; a superseded run writes nothing.
- **Admission**: a sub-floor run (any tier, incl. a fast tuple/transform) is not cached; an above-ceiling result (priced on the **join**, not the window) is not cached; both regenerate on revisit without error.
- **Disposability**: an invalidation drops the entry silently; canonical corpus/meta untouched; a worker respawn loses the cache and repopulates cold.
- **Eviction** holds the byte budget under a session of many distinct expensive queries, and a frequently-revisited query survives (GDS re-base on hit) while one-offs age out.

# Web worker protocol — the main ↔ pipeline-worker contract

This is the **source-of-truth interface contract** between the main thread and the pipeline web worker: who owns which data, every message that crosses the boundary (fields + what each one *does* on receipt), and the cancellation/supersession rules. Code is not the only source of truth — when you add or change a message, a data structure, or the supersession policy, **update this doc in the same commit.**

**Why a worker at all, and the deeper *why* behind each decision** live in [`design.md` § Cooperative runtime](design.md) (why the off-thread move, the data-ownership inversion, the rejected alternatives). This doc is *what the interface is*, present-tense.

## Where we are now

**The worker owns the merged and scoped corpus, unconditionally.** Main holds no merged/scoped corpus at all — only `state` (sources, scoring tier labels, search state), the per-wordlist `rawEntries` for My Edits (so it can seed an edit), and the per-config summaries the worker ships (`sourceCounts`, `mergedCount`, the all-sources badge axis). The worker builds its own corpus from IndexedDB on a `syncConfig`: it loads, parses, rescores, and merges every configured source itself, and the corpus never crosses the boundary as bulk data. Results no longer cross as indices into a shared main corpus — there is no main corpus to index into; the worker ships **rich, self-contained rows and atoms**.

`runPipeline` ([`ui/tool-stack.js`](../site/src/ui/tool-stack.js)) posts a `run` (with the active `sort`) to the worker through the client ([`ui/pipeline-worker.js`](../site/src/ui/pipeline-worker.js)). The worker always executes against its own owned corpus, sorts and filters the result itself, and ships the **flat** (filter-only) tier as a transferred index + score buffer plus an inline first window of rich rows. The **grouped** tier ships its first window of group rows (each with a `firstChains` window of its chains) plus result-level summaries; the worker retains the full sorted+filtered group list and serves later windows on demand. The **transform** tier ships every chain's rich atoms up front (it self-filters hard, so it's small). The client owns run-id tracking, settling a superseded run as aborted, dropping stale results, the per-run `_error` reset, and — because a run can outrun the corpus it needs — the **deferred-run queue** (below).

The flat scroller windows by default: it requests its visible rows from the worker via `fetchRows`, rendering shimmer skeletons on a miss (rare, since the first window ships inline with the result) and serving ordinary scrolling from a bounded local cache. The grouped scroller windows the same way at two levels — the group-ROW list via `fetchGroups` (windowed group rows, sized from the shipped `groupCount`) and a group's CHAINS via `fetchGroupChains` when the "+N more" popover pages past the inline window. Export (`fetchAllRows` flat / `fetchAllGroups` grouped), serialize (`serializeFor` — merged or single-source, for download + disk mirror), and the edit-popover bridges (`fetchEditSeed`/`fetchProvenance`) read the worker's owned corpus the same way. My Edits add/edit/delete drive `editEntry`/`deleteEntry` commands that splice the owned corpus in place and write the My Edits IDB from the worker, in O(affected norms) — no full rebuild.

A worker crash respawns a fresh worker, has it rebuild the owned corpus from IDB, and re-dispatches the in-flight (and any deferred) run; after `MAX_CRASHES` it latches `workerUnavailable` and settles every run gracefully errored. There is no main-thread engine fallback — the flip left no main corpus to run against.

## Data ownership

The dividing line: **the worker owns the corpus and everything derived from it; the main thread owns `state` and presentation.** The worker is the only place a merged or scoped corpus exists, so its corpus is **rich** — it carries `comment` and source identity, because it feeds rendering directly through the rich rows/atoms it ships.

### Main thread owns

| Data | Shape | Notes |
|---|---|---|
| `state` | sources, scoring (tier labels), search state | the app's root state; never crosses the boundary |
| My Edits `rawEntries` | `[{ norm, display, score, comment }]` | the only per-wordlist entry records resident on main — kept so an edit can be seeded/optimistically rendered. Every other source's entries live only in the worker |
| shipped per-config summaries | `sourceCounts` (`[{ wordlist, count }]`), `mergedCount`, the all-sources badge axis, the scoped histogram layout | read straight from the worker's `selfReady`/`result`; `getSourceCounts`/`mergedEntryCount` ([`data/merge.js`](../site/src/data/merge.js)) read **only** these — there is no local recompute path |
| score-range view filter, histogram, stats, virtual scroller, rendering | — | the scroller windows the table; the flat tier arrives pre-sorted and pre-filtered from the worker, transform/grouped sort on main. The score-range filter is normally the worker's job (it ships filtered survivors); main's local view-filter is the no-op fallback path |
| the pipeline-worker **client** | run-id → promise tracking; the deferred-run queue; flat result → index-backed handoff; rich atom → chain-row decode | [`site/src/ui/pipeline-worker.js`](../site/src/ui/pipeline-worker.js) |

### Worker thread owns

| Data | Shape | Notes |
|---|---|---|
| `ownedBuilt` | per-source **rich** wordlists `[{ dbKey, enabled, type, rescoreRules, rawEntries }]` | every configured source (enabled **and** disabled), loaded+parsed+rescored from IDB on `syncConfig`; the source of every corpus build |
| `ownedMerged` | rich merged corpus (`entries`/`byNorm`/`byKey`/`_initialChains`/`sourceCounts`) | the enabled-only deduped merge; feeds the config summaries **regardless** of the active scope |
| `ownedCorpus` | rich active-scope corpus | `=== ownedMerged` when the active scope is merged, else `buildScopeCorpus(ownedBuilt, scope)` (the single source, ignoring `enabled`). The corpus the pipeline executes against |
| `ownedEntryToIndex` | `Map(ownedCorpus.entries[i] → i)` | built **once per corpus rebuild** (never per run), kept strictly paired with `ownedCorpus`; the key to encoding the flat result's indices |
| `ownedScope`, `ownedCorpusFresh` | scope label + freshness flag | the enrichment/fetch gate (see *Freshness*) |
| `ownedAllSourcesAxis`, `ownedConfigVersion` | the scope-stable badge axis + monotonic config version | per-config, never per-run |
| `lastFlatResult` | `{ runId, indices, scores, scope, highlighters }` | the retained last flat result, `.slice()`d before the run's transfer detaches the originals — serves `fetchRows`/`fetchAllRows` |
| `lastGroupedResult` | `{ runId, groups, scope }` | the retained last grouped result — the **full** sorted+filtered group list, each group carrying its complete `chains` — serves `fetchGroups`/`fetchGroupChains`/`fetchAllGroups`. Mutually exclusive with `lastFlatResult`: a grouped result nulls the flat one and vice versa, so a stale-tier fetch is dropped by its freshness guard |
| the executor + full tool catalog | `executePipeline` / `runToolStage` / `bucketize` / `unify` + every tool's `run`/`prepare`/`group` | imported directly from `engine/` (the worker runs the identical module text) |
| `_preSearchCache` | pipeline state up to just before the search row | so a keystroke re-runs only the search row; invalidated on a user-stack change or a corpus rebuild |
| segmenter I/O (unigram corpus) | `configureIO({ idbGet, idbPut, onSize })`, called once at worker boot | `idbGet`/`idbPut` live in `data/storage.js` (not importable from `engine/`), so the worker opens the **same** IndexedDB DB/store (`grawlix`/`data`, v1) directly — the cached unigram corpus is per-origin, shared with main. `onSize` is a no-op (the LS corpus-size note is main-only). Also how the worker reads each source's wordlist text (`data_<dbKey>`) and writes the My Edits IDB |

### Building the corpus

The worker builds its corpus from the same IDB text and the same `engine/` code main would have used, so the result is byte-identical to a main-thread merge. `buildByNorm`/`canonicalNormRow` ([`engine/snapshot.js`](../site/src/engine/snapshot.js)) — the canonical-row selection per norm — are shared with the worker's owned-corpus splice, so case variants (`'CAT'` vs `'Cat'`) can never be resolved two different ways. (Those two functions are all that remains of `engine/snapshot.js`; the columnar pack/unpack it once held is gone.)

## Message encoding & packing

Two encodings cross the boundary, by design — a deliberate **mix**, not "objects everywhere" nor "binary everywhere." The split is by size:

**1. The control envelope — a small structured-clone object.** Every message is a plain object with a `type` discriminator and a handful of scalar fields (`runId`, the serialized `stack`, `sort`, `scope`, …). These ride `postMessage`'s default structured clone, and that's the right call *because they're tiny and bounded* — cloning a few integers plus a small stack descriptor (≈ what the URL encodes) is negligible.

**2. The flat result's bulk payload — raw binary, transferred.** The one O(results) thing that crosses is the flat tier's survivor list: two `Int32Array`s (indices + parallel scores), packed into `ArrayBuffer`s and handed to `postMessage`'s **transfer list**, which moves ownership instead of copying — a multi-megabyte buffer crosses in ~1 ms. This is the lag lever: the pathological 1-letter-matches-1M case ships two buffers in ~1 ms and materializes ~50 visible rows instead of structured-cloning a 1M-element highlights array (~3.2 s) and a million rows.

- **numbers → typed arrays.** `indices` and `scores` are `Int32Array`s; the backing `ArrayBuffer`s are transferred. **Int32** for scores — scores are always integers; a fractional one would truncate silently.

**Results cross as indices for the flat tier, rich rows everywhere else.** The flat survivor list ships as integer indices into the worker's own corpus order (one `Int32` per survivor) plus parallel scores; the worker serves the actual rich rows on demand via `fetchRows`. The transform/grouped tiers ship their atoms **rich and self-contained** (`{ norm, display, score, rawScore, comment, sourceId }`), and synthetic tool-output atoms travel inline as `{ s: {...} }`. There is no `{ i }` index-only atom encoding anymore: with no resident main corpus there is nothing to index into.

**The flat and grouped tiers are windowed; transform is not.** The flat tier (the one that *can* match everything) ships no bulk objects: just the transferred index + score buffers, an inline first window of rich rows, and small scalar/summary fields. The grouped tier windows at two levels — the `result` ships only the first window of group ROWS, each with only a `firstChains` window of its chains, plus result-level summaries; main fetches more group rows, more per-group chains, and the full export result on demand (`fetchGroups`/`fetchGroupChains`/`fetchAllGroups`). The transform tier alone stays **fully materialized** — every chain ships up front — because it self-filters hard (anagram/behead emit only on merged-corpus hits), so it's small and never a freeze source.

### Encoding at a glance

| Payload | Encoding | Transport |
|---|---|---|
| message envelope (`type`, `runId`, `stack`, `sort`, `scope`, `existsQuery`, `scoreRange`, `rebindQuery`) | plain object | structured clone (tiny) |
| flat result: survivor indices (sorted) + parallel scores — **filtered** when `filtered`, else unfiltered | `Int32Array` ×2 | **transferred** |
| flat result: column width hints | small `{ maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }` object | structured clone (tiny) |
| flat result: stats (scope-independent) + histogram counts (any scope, **always unfiltered**) + histogram layout (scoped runs only) + `filtered` flag | small `{ stats, histogramCounts, histogramLayout, filtered }` object | structured clone (small) |
| flat result: `existsInScope` / `existsInMerge` | booleans / `null` | structured clone (tiny) |
| flat result: `rebindQuery` echo + `rebindEntry` (rich row / `null`) + `rebindExists` | small object | structured clone (tiny) |
| flat result: `firstRows` (the inline above-the-fold window) | array of rich rows | structured clone (small — bounded by `FIRST_WINDOW`) |
| flat result: highlights | **not shipped** for the off-screen rows — re-derived on the worker per `fetchRows` window | — |
| transform-chain atoms | rich atom objects (`{norm,display,score,rawScore,comment,sourceId}` or `{s}` synthetic, each with optional `h`/`g`) | structured clone (small) |
| grouped result: first window of group rows + result-level summaries | group summaries `{ key, anchor, _minScore, _maxScore, _count, firstChains }` (window) + `{ stats, histogramCounts, histogramLayout, groupWidthHints, chainCount, groupCount, filtered }` | structured clone (small — bounded by `GROUP_ROW_WINDOW` × `GROUP_FIRST_WINDOW`) |
| `rows`/`allRows` reply | array of rich rows, each with an `atoms` array | structured clone |
| `groups`/`groupChains`/`allGroups` reply | windowed group summaries / a group's chain window / full groups (`encodeGroupFull`) | structured clone |
| serialize reply (`serialized.text`) | a single serialized wordlist string — merged or single-source (`null` when not fresh) | structured clone |

The rule of thumb for a new message: **scalars and small/filtered structures go as the object; the flat survivor set gets packed into a transferable `ArrayBuffer`.**

## Messages

Messages on one `Worker` are **FIFO**, which gives ordering for free (a `setScope` or `syncConfig` always arrives before a `run` that depends on it). Every message is a plain object with a `type` discriminator (see *Message encoding & packing* for how its fields and any bulk payload are encoded).

### Main → worker

#### `ping`
`{ type: 'ping' }` — liveness / spawn check. Worker replies `pong`.

#### `run`
`{ type: 'run', runId, stack, sort, scope, existsQuery, scoreRange, rebindQuery }` — **execute the pipeline against the worker's owned corpus.**
- `runId` — monotonic; the supersession key (see *Cancellation*).
- `scope` — `MERGED_ID` when the active scope is the merged view, else the scoped wordlist's `dbKey` (derived from `state.selected`, which is the wordlist object or the `MERGED_ID` string — never a dbKey). The worker executes against `ownedCorpus`, which it keeps built for this scope; the client only dispatches a run once it has confirmed the worker is fresh for `scope` (else it defers — see *The deferred-run queue*). The worker retains `scope` on the flat result and uses it to gate `fetchRows` enrichment.
- `stack` — the serialized tool stack: an array of `{ tool, params, grouped }` descriptors (≈ what the URL encodes), plucked off each `ToolStack.getStack()` row by the client. The worker rebuilds each row via `makeToolRow(tool)` then overlays `params`/`grouped` — the same defaults-then-override order `router.js applyURL` uses, so the executor sees the identical row shape. The tool **code** is looked up in the worker's own copy of the catalog; functions never cross the boundary. An unknown `tool` key is skipped.
- `existsQuery` — the **raw trimmed search text** (or `null` when blank), so the worker can answer two existence questions per result: `existsInScope` (in the run's scope) and `existsInMerge` (in the merge). Main sends the raw string and lets the worker `toNorm` it (same `engine/norm.js toNorm` both threads use); it does **not** apply `isLiteralQuery` here — that gate stays at the consumer (`newEntrySeedQuery`).
- `scoreRange` — the **raw range string** (e.g. `'60-80'`, `'30+'`, `'45'`) the active scope's score-range filter is set to, or `null` when no filter is active. Sourced from `app-view.js activeScoreRange()` (the canonical per-scope range owner — **not** the scroller's `this.scoreRange`); the worker `parseRange`s it. The worker filters its survivor `indices`/`scores` against any range that parses, shipping the filtered set with `filtered: true`; a non-empty range that doesn't parse (a transient typing state like `"60-"`, which `parseRange` returns `null` for — matching main) ships the **unfiltered** set with `filtered: false` so the table shows everything rather than flashing empty. The histogram counts are bucketed **before** the filter (over the unfiltered scores), so out-of-range bars stay clickable. A score-range change re-runs the pipeline rather than re-filtering locally.
- `rebindQuery` — `{ norm, display }` of the **open edit popover's re-anchor target**, or `null` when no popover is open (`popoverRebindQuery()`). When a new result lands while the popover is open, the table re-anchors it via `EntriesScroller.updateEntries → AtomPopover.rebindEntry → scroller.findResultEntry / resultHasEntry`, which run **synchronously** in the render path — so rather than awaiting the worker there (which would ripple a dual async path through the sync render), the open popover's target **rides the run** and the worker resolves it against `ownedCorpus`, shipping the answer on the same `result` (`rebindEntry`/`rebindExists`). Resolved exactly as main's flat `findResultEntry`+`resultHasEntry` once did — a **full-corpus** `byKey.get(mergeKey(norm,display)) ?? byNorm.get(norm)` lookup that re-anchors even to an entry **filtered OUT** of the visible (range-filtered) view.
- `sort` — `{ key, dir }` (axis + direction). **Honored for the flat tier:** the worker sorts the survivor indices by this axis before shipping them, mirroring the scroller's single-tier `SORT_AXES` (`entry`/`length`/`score`, each with its fixed-direction tiebreaker chain) — those axes read only `corpus.entries[idx].{norm,score}` + `norm.length`, all worker-resident. Even `entry`/asc is sorted (native merge order ties by display, the `entry` axis by score), so main never re-sorts. The transform/grouped tiers ignore `sort` (their axes need every atom → the scroller sorts the materialized rows). A flat-tier sort-axis change re-runs the pipeline rather than re-sorting on main.
- **On receipt:** worker sets `latestRunId = runId`, stashes the request as `pending`, and drives a drain-to-latest run loop: `executePipeline(ownedCorpus, stack, signalShim)` against its cached pre-/post-search state, then posts `result` — unless superseded first. The signal shim's `aborted` is `thisRunId !== latestRunId`. **The worker drops its `_preSearchCache` when the user-stack portion of the stack changes between runs** (it compares a signature of `stack` minus the trailing search bar) — main's `ToolStack` mutation handlers invalidate the cache via in-realm signals the worker never sees. It **also** drops the cache when `ownedCorpus` changed identity since the last run (a scope switch or config re-sync rebuilt it), since the cached chains hold the previous corpus's entry objects by reference.

#### `cancel`
`{ type: 'cancel' }` — explicit supersession, for teardown / search-cleared. Optional given that a newer `run` implicitly supersedes (see *Cancellation*).
- **On receipt:** worker advances `latestRunId` past every live run and clears `pending`, so the in-flight shim aborts at its next yield and no run is queued. No reply.

#### `setScope`
`{ type: 'setScope', scope }` — **rebuild `ownedCorpus` for a newly-selected scope** from the resident `ownedBuilt`, synchronously (no IDB read — `ownedBuilt` already holds every source's parsed+rescored wordlist from the last `syncConfig`). Fire-and-forget; no reply.
- `scope` — `MERGED_ID` when the merged view is selected, else the scoped wordlist's `dbKey`.
- **Sent:** from `rendering.js`'s `setScope`, **before** the scope's run dispatch. FIFO then puts the rebuild ahead of the run, so `ownedCorpus` matches the run's scope before any execution or enrichment. The client mirrors the new fresh-scope synchronously on `sendWorkerScope` (so the run dispatches rather than defers) — but only once *some* build has landed; before the first build the mirror stays `null` and the run still defers.
- **On receipt:** if `ownedBuilt` is null (no `syncConfig` yet) → **inert** (leave `ownedCorpus`/`ownedScope`/`ownedCorpusFresh` as-is). Otherwise rebuild `ownedCorpus` (`ownedMerged` for a merged scope, else `buildScopeCorpus(ownedBuilt, scope)`), via `setOwnedCorpus`, which sets `ownedScope = scope ?? MERGED_ID` and `ownedCorpusFresh = true`. The rebuild is synchronous, so it completes the instant the message is processed — before the scope-switch's run arrives. Because it's synchronous and FIFO-before the run, `setScope` needs **no** deferral on the client side.

#### `fetchRows` (windowed row fetch)
`{ type: 'fetchRows', requestId, runId, start, end }` — **request a window `[start, end)` of the retained flat result.** The flat scroller fetches its visible window + prefetch buffer, renders shimmer skeletons on a miss, and serves ordinary scrolling from a bounded local cache (seeded from the result's inline `firstRows`, so the first paint rarely misses).
- `requestId` — monotonic per client; echoed on the `rows` reply so a stale response (superseded by a newer request) is matched and dropped.
- `runId` — which flat result this window names. The worker retains the **last flat result** only (`lastFlatResult = { runId, indices, scores, scope, highlighters }`). A grouped or rich (transform-chain) result nulls `lastFlatResult`, so a fetch for a non-flat result is dropped by the runId guard.
- `start` / `end` — the half-open window into the sorted survivor list. `start` is floored at 0, `end` capped at `length`; a `start` past the end simply yields an empty `rows`. `start | 0` / `end | 0` coerce.
- **On receipt:** dropped silently (no reply) unless the retained result is still **serveable** (`fetchResultFresh`: `lastFlatResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastFlatResult.scope`) — the same supersession discipline as runs. Main re-fetches against the current result on the next run. Otherwise post `rows` with the clamped window, always **rich** (built by `buildFlatRows`).

#### `rows` (windowed row fetch reply)
`{ type: 'rows', requestId, runId, start, rows }` — reply to `fetchRows`.
- `requestId` / `runId` — echoed for matching.
- `start` — the floored window start the worker served (`max(0, requested)`; differs from the requested `start` only when it was negative).
- `rows` — an array, one **rich** row per index in the window: `{ norm, display, score, rawScore, comment, sourceId, atoms }`. `sourceId` is the winning source's `dbKey`; `rawScore` is `undefined` for an unrescored row (structuredClone preserves the slot). `atoms` is an **array** — one slot for a plain row, more when stacked highlighting searches produce multiple same-word atom lines — each `{ highlights, glyph }` (`highlights` is the re-derived search-match range array, `null` when no highlighting filter is active; `glyph` is `null`, since flat rows never carry one). The client (`_richRowToChain`) rebuilds each row's `wlEntry` from the inline fields and resolves `sourceId → state.sources`.

There is **no** index-only row shape: with no resident main corpus, an index would be un-decodable. The freshness guard above (`fetchResultFresh`) is what makes a rich-only reply sound — a fetch whose corpus changed between the run and the fetch is dropped, not served wrong; main re-fetches on the next run.

#### `fetchAllRows` (full-result row fetch, export)
`{ type: 'fetchAllRows', requestId, runId }` — **request the ENTIRE retained flat result** (no window) so main can format it for **export** (Copy / .txt wordlist / CSV / JSON). It is `fetchRows` with `start = 0, end = indices.length` — same retention, same `fetchResultFresh` guard, same rich row shape (built by the shared `buildFlatRows`, so an export row encodes identically to the same entry's scroller row).
- `requestId` — monotonic per client, in its **own request-id space** (independent of both `fetchRows`' and the run's id spaces), echoed on the `allRows` reply for stale-drop matching; a client-side timeout resolves `null` so main can recover rather than hanging. (Grouped/transform export is **always** local — it formats resident `ChainRow[]`, not a flat result — and never issues this message.)
- `runId` — which flat result to serve; the same `fetchResultFresh` guard as `fetchRows` (drop silently otherwise).

#### `allRows` (full-result row fetch reply)
`{ type: 'allRows', requestId, runId, rows }` — reply to `fetchAllRows`. `requestId`/`runId` echo for matching. `rows` is the **whole** retained result, one **rich** row per survivor index — the *same* row shape and the *same* `buildFlatRows` builder as the `rows` reply, so an export row can't drift from the scroller's windowed row. The client reconstructs a `ChainRow` per row (resolving `sourceId → state.sources`); the result is the `ChainRow[]` the export formatters walk.

#### `fetchGroups` / `fetchGroupChains` / `fetchAllGroups` (windowed grouped result)

The grouped tier windows like the flat tier — but at **two levels**, because a grouped result is a list of group ROWS and each group holds a list of CHAINS, and either dimension can be the size that freezes main. The worker owns, sorts, and filters the grouped result and retains the full sorted+filtered list (`lastGroupedResult = { runId, groups, scope }`, where each `group` carries its FULL `chains`). The `result` ships only the first window of group rows (each with a `firstChains` window); main fetches more group rows on scroll, more of a group's chains on "+N more", and the whole result on export. All three fetches are guarded by `groupedResultFresh(runId)` (the grouped sibling of `fetchResultFresh` — `lastGroupedResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastGroupedResult.scope`), so a fetch whose corpus changed since the run is dropped silently rather than served against the wrong corpus; main re-fetches on the next run.

#### `fetchGroups` (windowed group-row fetch)
`{ type: 'fetchGroups', requestId, runId, start, end }` — **request a window `[start, end)` of the retained grouped result's group ROWS**, the grouped analogue of `fetchRows`. The grouped scroller windows the group-row list: it renders the visible group rows from a bounded local cache (seeded from the result's inline first window), shimmer skeletons on a miss, and fetches the missing window. This is the fix for the grouped-render freeze — main holds only a window of group rows, never decodes the whole list.
- `requestId` — monotonic per client; echoed on the `groups` reply so a stale (superseded) response is matched and dropped.
- `runId` — which grouped result this window names; the `groupedResultFresh` guard drops a fetch for a superseded run or a result that's since been replaced by a flat/transform one.
- `start` / `end` — the half-open window into the sorted group-row list (`start` floored at 0, `end` capped at `groups.length`; `| 0` coerces).
- **On receipt:** dropped silently unless `groupedResultFresh(runId)`. Otherwise post `groups` with the clamped window, each group **encoded as a summary envelope + `firstChains` window** (`encodeGroup`) — *not* its full chains.

#### `groups` (windowed group-row fetch reply)
`{ type: 'groups', requestId, runId, start, groups }` — reply to `fetchGroups`. `requestId`/`runId` echo for matching. `start` is the floored window start served. `groups` is an array of **encoded group summaries** (`encodeGroup`): each `{ key, anchor, _minScore, _maxScore, _count, firstChains }` — `key` the tool-derived group key; `anchor` the rich anchor-atom encoding or `null`; `_minScore`/`_maxScore`/`_count` the precomputed group stats (`_count` is the group's **full** chain count, the source for the Count badge and the "+N more" arithmetic, **not** `firstChains.length`); `firstChains` the first `GROUP_FIRST_WINDOW` chains (each `{ atoms: [<atom>, …] }`, the rich atom encoding) for the collapsed row's slot-fill. The client decodes each group, resolving `sourceId → state.sources` per atom.

#### `fetchGroupChains` (windowed per-group chain fetch, "+N more")
`{ type: 'fetchGroupChains', requestId, runId, groupKey, start, end }` — **request a window `[start, end)` of ONE group's CHAINS**, for the "+N more" popover (`GroupMorePopover`) on a group whose chain count exceeds what the collapsed row or the popover's first page shows. The popover paginates `POPOVER_CHUNK` (200) chains at a time as the user scrolls, caching by **absolute** chain index so a cross-window atom edit routes to the right atom.
- `requestId` — monotonic per client; echoed on the `groupChains` reply for stale-drop matching.
- `runId` — the grouped result; `groupedResultFresh`-guarded.
- `groupKey` — which group's chains (the `key` from its summary). The worker finds the group by key in `lastGroupedResult.groups`; an unknown key is dropped.
- `start` / `end` — the half-open window into that group's full chain list (`start` floored at 0, `end` capped at the group's `chains.length`).
- **On receipt:** dropped silently unless `groupedResultFresh(runId)` and the group is found. Otherwise post `groupChains` with the group's `chains.slice(lo, hi)` encoded.

#### `groupChains` (windowed per-group chain fetch reply)
`{ type: 'groupChains', requestId, runId, groupKey, start, chains }` — reply to `fetchGroupChains`. `requestId`/`runId`/`groupKey` echo for matching. `start` is the floored window start served. `chains` is the window of that group's chains, each `{ atoms: [<atom>, …] }` in the rich atom encoding. The popover decodes them into its absolute-index chain cache.

#### `fetchAllGroups` (full grouped-result fetch, export)
`{ type: 'fetchAllGroups', requestId, runId }` — **request the ENTIRE retained grouped result** (every group with its FULL chains, no windowing) so main can format it for **export** (Copy / .txt / CSV / JSON). The grouped sibling of `fetchAllRows`: a one-round-trip full-result walk worker-side, restoring export completeness that windowing would otherwise cut (a windowed group ships only `firstChains`, so exporting from the windowed rows would silently drop every chain past the window).
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `allGroups` reply for stale-drop matching; a client-side timeout resolves `null` so main can recover rather than hang.
- `runId` — which grouped result to serve; the same `groupedResultFresh` guard.
- **On receipt:** dropped silently unless `groupedResultFresh(runId)`. Otherwise post `allGroups` with every group **encoded full** (`encodeGroupFull` — the summary envelope + the group's complete `chains`, not `firstChains`).

#### `allGroups` (full grouped-result fetch reply)
`{ type: 'allGroups', requestId, runId, groups }` — reply to `fetchAllGroups`. `requestId`/`runId` echo for matching. `groups` is the **whole** sorted+filtered group list, each encoded as `{ key, anchor, _minScore, _maxScore, _count, chains }` (`encodeGroupFull`) — the summary envelope plus the group's **complete** chains. The client decodes the full groups and the export formatters walk them; the per-group `chains` here are exhaustive, so a >`GROUP_FIRST_WINDOW`-chain group exports every member.

#### `serializeFor` (corpus serialize, download + disk mirror)
`{ type: 'serializeFor', requestId, scope, format, sort }` — **serialize a worker-owned corpus to wordlist text** so a download or disk mirror needs no main-thread corpus read. `scope` discriminates the target: `MERGED_ID` serializes the deduped merge (`ownedMerged`) for the merged download (`downloadMergedWordlistFromPanel`) / merged disk mirror; any other `scope` is a **source `dbKey`**, serializing that one source's full rescored entry list for the individual download (`downloadSourceWordlist`) / per-source disk mirror (`MirrorSync._serialize`).
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `serialized` reply for stale-drop matching; a client-side timeout resolves `null`.
- `scope` — `MERGED_ID` for the merge, else a source `dbKey`.
- `format` — the output-format object (`{ spaces, punctuation, accents, comments }`, from `getOutputFormat()`) that `serializeEntries` applies. Main sends the resolved format so the worker doesn't read localStorage.
- `sort` — **load-bearing boolean** reproducing two distinct call sites per target: the **download is UNSORTED** (`sort: false` — merged ships merge order, per-source ships `rawEntries` order), the **disk mirror is SORTED** (`sort: true` — `sortedEntries(...)`). The two are NOT unified: unifying would silently diverge one path's bytes.
- **On receipt:** `serializeEntriesForScope(scope)` resolves the entries — guarded by `ownedCorpusFresh`; `MERGED_ID` → `ownedMerged.entries`, else the matching `ownedBuilt` source's `getRescoredEntries(wl)`. A miss (not fresh, or no such source) replies `text: null`. The per-source path serializes the source's **full rescored entry list undeduped** — NOT `buildScopeCorpus`, whose dedup/variant-collapse would diverge from main's `getRescoredEntries`-based bytes. Otherwise `text = serializeEntries(sort ? sortedEntries(entries) : entries, format)` and replies `serialized`. The disk-sync seam (`configureMirrorSerializer`, `data/disk-sync.js`) keeps the data layer off `ui/`: it hands disk-sync a `(scope, format) → text-or-null` worker attempt (SORTED) and disk-sync owns the fallback. The merge has no resident main corpus, so its fallback mirrors empty; a source still holds its `rawEntries` on main, so its fallback serializes locally.

#### `serialized` (corpus serialize reply)
`{ type: 'serialized', requestId, text }` — reply to `serializeFor`. `requestId` echoes for matching. `text` is the serialized wordlist string (sorted or unsorted per the request's `sort`; merged or single-source per `scope`), or **`null`** when the worker wasn't fresh / no source matched `scope`.

#### `fetchEditSeed` (edit-popover seed)
`{ type: 'fetchEditSeed', requestId, norm, display }` — **resolve the All Wordlists merge winner for a clicked `(norm, display)`** so the inline edit popover can seed without a main-thread corpus read. The popover's seed is always the merged winner even from a scoped view (under a scoped lower-priority list the clicked atom holds that list's losing value, but the editor must show what the merge serves), and in a scoped view that winner may be a *different, higher-priority* wordlist main can't reach without its corpus — so the worker resolves it.
- `requestId` — monotonic per client, in its **own request-id space, independent of the run's `runId`** (a popover query must not interfere with run supersession). Echoed on the `editSeed` reply so a stale response is matched and dropped; a client-side timeout resolves `null` so main falls back to the clicked atom.
- `norm` / `display` — the clicked atom's norm and display (`null` for a bare click).
- **Target is `ownedMerged`, never `ownedCorpus`** — the seed is the merged winner regardless of the active scope. **On receipt:** if `ownedMerged` is present **and** `ownedCorpusFresh` (the latter stands in for an `ownedMerged`-specific freshness flag — a `syncConfig` clears it synchronously and only a committed `syncConfig` or an edit command re-sets it, so `fresh ⇒ ownedMerged` is current), resolve the winner via the shared `resolveEditSeedWinner(ownedMerged, norm, display)` — `byKey.get(mergeKey)`, then the **bare-display quirk** (a bare click with no bare merged row picks the first-alphabetical spelled variant, else `byNorm.get(norm)`). Reply `editSeed` with `winner = { norm, display, score, comment, sourceId }` (`sourceId` = the winning source's `dbKey`, so main resolves it to `state.sources` and applies the My-Edits raw-score adjustment locally — that adjustment stays on main, where `edits.rawEntries` is resident). When the norm is **absent from the merge**, or the worker isn't fresh, reply `winner: null` and main falls back to the clicked row (`row._wlEntry`).

#### `editSeed` (edit-popover seed reply)
`{ type: 'editSeed', requestId, winner }` — reply to `fetchEditSeed`. `requestId` echoes for matching. `winner` is `{ norm, display, score, comment, sourceId } | null`.

#### `fetchProvenance` (edit-popover provenance + preview)
`{ type: 'fetchProvenance', requestId, typedRaw, previewRaw, clickedNorm, clickedDisplay }` — **resolve the popover's live preview (the merge row for the typed/seed text) and its cross-wordlist provenance table** so the inline edit popover does no main-thread corpus read. The two targets the worker holds: `ownedMerged` for the preview (the merge winner), and `ownedBuilt` (the all-sources rich wordlists, enabled **and** disabled) for the provenance walk — disabled/non-winning lists must still surface.
- `requestId` — monotonic per client, in its **own request-id space, independent of both the run's `runId` and the edit-seed lane**. Echoed on the `provenance` reply; a client-side timeout resolves `{preview:null,rows:null}`.
- `typedRaw` — the raw text driving the **provenance target** (the entry-input value per keystroke; `''` at the initial open so the target falls to the clicked atom). `previewRaw` — the raw text driving the **footer preview** (the input value per keystroke; the seed entry at open). The two diverge **only at the initial open**, where the synchronous code uses two different targets — `previewWlEntry(seed.entry)` for the footer but the clicked atom for the table — which a single raw string can't express; per keystroke both are the input value.
- `clickedNorm` / `clickedDisplay` — the clicked atom's norm/display (`null` display for a bare click), the provenance target's fallback when `typedRaw` is blank.
- **On receipt:** guarded by `ownedMerged && ownedBuilt && ownedCorpusFresh`; a miss replies `{preview:null, rows:null}`. Otherwise it reproduces main's logic verbatim:
  - **preview** = `previewRaw.trim() ? (ownedMerged.byNorm.get(toNorm(previewRaw)) || null) : null`, shipped as `{ norm, display, score, comment, sourceId }` (lean; main re-resolves `sourceId → state.sources`) or `null`.
  - **provenance target**: `target = preview-for-typedRaw ?? (typedRaw.trim() ? {norm: toNorm(typedRaw), display: null} : {norm: clickedNorm, display: clickedDisplay})`.
  - **rows**: for each source in `ownedBuilt` order (= `state.sources` order), `getRescoredByNorm(wl).get(target.norm)`, included by the **asymmetric bare-display quirk** `display == null || e.display === display || e.display == null`. Each row is `{ sourceId: wl.dbKey, enabled: wl.enabled !== false, entry: { norm, display, score, comment } }`. Main resolves `sourceId → state.sources` and renders through the same body builder, so the table HTML is byte-identical to a local build.

#### `provenance` (edit-popover provenance + preview reply)
`{ type: 'provenance', requestId, preview, rows }` — reply to `fetchProvenance`. `preview` is `{ norm, display, score, comment, sourceId } | null`; `rows` is the ordered provenance array `[{ sourceId, enabled, entry: { norm, display, score, comment } }]`, or `null` when the worker wasn't fresh. A `null` `rows` means "worker didn't answer" → main keeps its last-good render. Main holds the last shipped `rows`/`preview` per open popover and re-renders only when a newer reply lands (a monotonic token drops stale replies, never cleared to empty mid-flight — so the table/footer don't flash).

#### `editEntry` (My Edits in-place edit/add)
`{ type: 'editEntry', editId, orig, next }` — **mutate the worker's owned corpus in place for one My Edits edit or add**, in O(affected norms), so a My Edits change no longer forces a full `syncConfig` rebuild. The worker also **writes the My Edits IDB itself** (main holds no `rawEntries`-to-serialize beyond the seed and skips its own write).
- `editId` — monotonic per client; echoed on the `editAck` reply for ack-matching. Edits apply in FIFO order.
- `orig` — `{ norm, display }` of the entry being edited/moved, or **`null` to add a new entry**. The `norm` is `toNorm`-derived; `display` is the clicked variant's display (so a specific variant of a multi-variant norm can be targeted).
- `next` — `{ norm, display, score, comment }` — the post-edit entry. `norm` is `toNorm(display)`; `display` is the raw entry text My Edits stores verbatim.
- **On receipt:** **bump `latestSyncToken` at the top** — an older in-flight `syncConfig` build (started before this edit, reading pre-edit `rawEntries`) then discards via its commit guard rather than overwriting the edit with stale data. Then: if the owned corpus isn't present (`!editsWordlist()`/`!ownedMerged`/`!ownedCorpus`), reply a no-op `editAck` (so the bridge's await resolves) — a later `syncConfig` rebuilds from IDB. Otherwise:
  1. **Mutate the My Edits source's `rawEntries`** (the `type: 'edits'` source in `ownedBuilt`) exactly as `actions.js`'s `saveEdit` does: on an entry-text change remove the orig record, then upsert by `(norm, display)`. Invalidate that source's rescored caches.
  2. **Affected norms** = the dedup of `[orig?.norm, next.norm]` (falsy filtered) — one for an in-place edit, two for a move.
  3. **Splice `ownedMerged`** per affected norm (`spliceOwnedCorpus`): recompute the bucket via the **rawScore-dropping** `computeMergedBucket(norm, ownedBuilt)` (a full merge drops `rawScore`, so the splice must too), then splice `entries`/`byKey`/`byNorm`/`_initialChains` and shift `sourceCounts` by the winner delta — **counted per merged row, not per distinct winning source** (a multi-variant norm one source wins several times contributes one merged entry *per variant*, so the decrement iterates the old rows symmetrically with the per-row `winners` increment; a `Set` would drift `sourceCounts` from a rebuild's by the duplicate-winner count).
  4. **When scoped to My Edits** (`ownedScope === editsDbKey`, so `ownedCorpus !== ownedMerged`), splice `ownedCorpus` too — a single-source recompute (`recomputeScopedBucket`) that **ignores `enabled`** and **carries `rawScore`** (a scoped corpus keeps `rawScore` for the rescore-preview arrow). For MERGED scope `ownedCorpus === ownedMerged`, already spliced.
  5. **Full-rebuild `ownedEntryToIndex`** (a count-changing splice shifts every later index) and **invalidate the pre-search cache** (the splice replaced entry objects the cached chains hold by reference).
  6. **Set `ownedCorpusFresh = true`** — the in-place mutation leaves the owned corpus coherent, so a subsequent run/`fetchRows` serves fresh rich rows with no resync.
  7. **Recompute the per-config summaries** — bump `ownedConfigVersion`, recompute `ownedAllSourcesAxis`, gather fresh `sourceCounts`/`mergedCount` — since `editEntry` skips the `syncConfig` that would otherwise refresh them; carry them on the ack.
  8. **Post the `editAck` first, then `await` the IDB write** (`idbPut('data_' + edits.dbKey, serializeEntries(sortedEntries(edits.rawEntries)))` — byte-identical to main's old `persistEdits` write), so ack consumption isn't delayed by disk I/O. **Then bump `latestSyncToken` again** — a `syncConfig` that read the pre-write IDB text (started between the ack and the write landing) discards too.

#### `editAck` (My Edits edit/add reply)
`{ type: 'editAck', editId, norms, edited, axis, counts }` — reply to `editEntry`. `editId` echoes for matching.
- `norms` — the lean affected-bucket patch shape `[{ norm, rows: [{ norm, display, score }] }]` — `[]` on a no-op ack.
- `edited` — the rich merged **winner** for `next` (`{ norm, display, score, rawScore, comment, sourceId, index? }` — `index` present **only** for a MERGED-scope edit where `ownedEntryToIndex` indexes `ownedMerged`), or **`null`** when `next` no longer wins/exists in the merge.
- `axis` — the refreshed all-sources histogram layout (`{ mode, slots, min, max }`), same shape/role as `selfReady`'s `axis`.
- `counts` — `{ sourceCounts: [{ sourceId, count }], mergedCount, version }` — the refreshed per-config summaries.
- **On receipt:** `actions.js`'s `applyEditAck` consumes it: `setShippedAllSourcesAxis(axis, counts?.version)` + `setShippedConfigCounts(sourceCounts, mergedCount, version)` (version-guarded, mirroring `selfReady`'s consumption), then `refreshDerivedDisplays()` to repaint the X-of-Y meta + scoring legend with the fresh shipped values — so a per-entry edit needs no resync to keep those summaries current. The edited row itself updates instantly via the optimistic `applyEditsChange` path; the ack lands a few ms later to settle the steady state.

#### `deleteEntry` (My Edits in-place delete)
`{ type: 'deleteEntry', editId, norm, display }` — **remove one My Edits entry in place from the worker's owned corpus**, the removal-only sibling of `editEntry`. Runs the *same* O(affected-norms) owned-corpus update for the deleted norm, splices **only** the owned corpus, and writes the My Edits IDB itself.
- `editId` — monotonic per client (shares `editEntry`'s id counter); echoed on the `editAck` reply. Applies in FIFO order.
- `norm` / `display` — the `(norm, display)` to remove. The worker **re-derives the rawEntries index itself** (`findIndex(e => e.norm === norm && displayOf(e) === display)`) against its **own** copy of the source's `rawEntries` — it does not accept a caller-supplied array index, since the worker owns its own rawEntries order.
- **On receipt:** bump `latestSyncToken` (same edit-race harden as `editEntry`, at the top and again after the IDB write). If the owned corpus isn't present, or the entry isn't found (already gone), reply a no-op `editAck`. Otherwise splice the record out of `rawEntries`, invalidate its rescored caches, then run the **shared owned-edit tail** (`applyOwnedEdit`): affected norms = `[norm]`; recompute that norm's merged bucket via `computeMergedBucket` (now without the deleted entry — it may keep other variants/lower-priority sources, or become empty → `byNorm.delete`) and splice `ownedMerged` (and the scoped `ownedCorpus` when scoped to My Edits); full-rebuild `ownedEntryToIndex`; invalidate the pre-search cache; recompute the per-config summaries; set `ownedCorpusFresh = true`. Reply `editAck` with `edited: null` (a delete has no surviving winner), **then `await` the IDB write**.

#### `editAck` (delete)
A `deleteEntry` replies with the **same `editAck` shape** as `editEntry` — `editId` echoes; `norms` is the affected-bucket patch; `axis`/`counts` carry the refreshed summaries; `edited` is **always `null`** for a delete. `applyEditAck` consumes the axis/counts identically.

**Undo of a delete needs no new command.** Undoing = re-adding the deleted entry's full record, which is exactly an `editEntry` with `orig: null` (the add path) — `deleteFromEdits`'s undo callback fires `sendEditEntry(null, …)`. Because the corpus **sorts** everywhere it's built or serialized and `getRescoredByNorm` is a map, the re-added record's position in `rawEntries` (a plain `push`) is irrelevant — the post-undo corpus is byte-identical to the pre-delete corpus, including for a multi-variant norm.

#### `syncConfig` (self-build)
`{ type: 'syncConfig', configId, scope, sources }` — hand the worker the config it needs to **independently load+parse+rescore+merge** its own corpus. This is how the worker gets its corpus — it never receives the corpus as bulk data.
- `configId` — monotonic per client; echoed verbatim on the `selfReady` reply so each in-flight `syncConfig` awaits **its own** reply (correlation, below). Multiple syncs are routinely concurrent — the completeness hook fires one and a post-write re-sync fires another before either build settles.
- `sources` — an array in **merge-priority order** (`sources[0]` highest). Each: `{ sourceId, enabled, type, rescoreRules }`, where `sourceId` is the wordlist's `dbKey`, `type` is `'edits'` for My Edits (else `null` — carried so the `editEntry` handler can find the My Edits source in `ownedBuilt`), and `rescoreRules` are stripped to the **four editor fields** (`input`, `length`, `output`, `note`) — the worker recompiles them.
- `scope` — the **active scope** at sync time (`MERGED_ID` or the scoped wordlist's `dbKey`). It determines which corpus the worker builds into `ownedCorpus`; the merged build (`ownedMerged`) is built unconditionally and feeds the config summaries regardless of `scope`.
- **Sent:** from production boot (`init()`, after `propagateDefaults`); **re-sent on every config change** (`resyncWorkerConfig`); and by the test bridge (`syncWorkerConfig`). The boot first paint awaits the boot `selfReady` reply (via the deferred-run drain — see below).
  - **The re-send on config changes (completeness).** A config change must always re-sync, or `ownedCorpus` goes stale-but-fresh and the worker enriches rows from stale data — silent corruption of every rendered row. Two trigger sites cover them all: (1) the **completeness hook** — `resyncWorkerConfig()` in `rendering.js`'s render-effect cache branch, firing on every `cacheVersion$` bump (rules/enable/order/import/fetch/bake); and (2) **post-IDB-write re-syncs** — `resyncWorkerConfig()` after each `Storage.writeWordlist` in `applyWordlistText` (import/fetch), the `ingestFile` My-Edits-combine branch, and the non-edits `bakeRescoring` write, all of which read **fresh** IDB text. (A per-entry My Edits edit/delete instead refreshes via the `editEntry`/`deleteEntry` command + `editAck`, no resync.) The completeness hook for a mutation that also does a post-write re-sync fires *prematurely* (before the write lands → stale text), made harmless by supersession (below).
- **On receipt:** worker stores `selfConfig = data`, captures a fresh **`latestSyncToken`** (supersession key, below), clears `ownedCorpusFresh` synchronously (so a run dispatched in the rebuild gap defers rather than running against the stale corpus), and asynchronously builds the all-sources wordlists from IDB (retained as `ownedBuilt`). When the build settles **and is still the latest** (token guard): bump `ownedConfigVersion`, compute `ownedAllSourcesAxis`, eager-build `ownedMerged` (the enabled-only deduped merge — feeds the config summaries), and `setOwnedCorpus` for the active scope (`ownedMerged` when merged, else `buildScopeCorpus(built, scope)`). A superseded build discards its result (`ownedCorpusFresh` stays `false`). A build **failure** in the latest sync nulls `ownedBuilt`/`ownedMerged`/`ownedCorpus`. Either way the `.finally` replies `selfReady` (echoing `configId`) once the build settles — even when superseded or failed (so the bridge's `await` always resolves).
- **Supersession (`latestSyncToken`).** A single config change can fire two re-syncs — the premature completeness hook (stale text) and the post-write re-sync (fresh text). Each `syncConfig` captures `const myToken = ++latestSyncToken` synchronously at handler start, and the build's `.then`/`.catch` guard their commit with `if (myToken !== latestSyncToken) return`. Only the **latest** sync's build commits; a stale build discards. Because the post-write re-sync is always posted after the premature hook one (FIFO), the committed build always read fresh IDB text. (The same token guard is what makes an in-flight stale build lose to a concurrent `editEntry`, which also bumps the token.)
- **Reply correlation (`configId`) — load-bearing with supersession.** A superseded build still posts a `selfReady` (so its bridge listener resolves), carrying the *currently-committed* `version`. Without `configId` the listeners were unkeyed (first-`selfReady`-wins), so a listener awaiting the **committed** build's reply could instead consume — and unregister on — a superseded build's stale-`version` reply; the committed build's genuine reply then arrived with no listener and was dropped, leaving main's shipped axis/counts silently stale. Echoing `configId` makes each listener resolve only on its **own** reply.
- **The all-sources axis (`axis` + `version`).** Per-config (rides this handshake, **never** the per-run `result`), the worker computes `getHistogramLayout(<union of every configured source's rescored scores>, 'all')` — the union over **all** sources (enabled **and** disabled, **not** deduped). This is the **scope-stable badge-gradient axis** main's `scoreColor` reads (`allSourcesHistogramLayout()`), equal to the merged scope's histogram layout. It must be computed **only** here, never per run or per scope — a per-run recompute would silently shift badge colors on every keystroke. The worker invalidates its histogram-layout cache (key `'all'`) before computing, so a later `syncConfig` with changed scores doesn't return a stale axis.

#### `dumpCorpus` (test-only)
`{ type: 'dumpCorpus', scope }` — build a corpus from the synced `selfConfig` and post it back for fixture comparison.
- `scope` — `MERGED_ID` for the merged build (enabled sources only), or a `sourceId` for a single-source scoped build (regardless of `enabled`).
- **On receipt (`corpusForScope`):** `MERGED_ID` dumps the held `ownedMerged` (no rebuild). A scope equal to the active owned scope (`ownedScope === scope && ownedCorpusFresh`) dumps the live, in-place-spliced `ownedCorpus` directly — so an `editEntry` splice is observable. Any other scope builds on demand from IDB. Replies `corpusDump`. Requires a prior `syncConfig`.

#### `queryEntry` (test-only)
`{ type: 'queryEntry', requestId, scope, norm, display }` — a single-entry `byKey`/`byNorm` lookup against a scope's owned corpus. Used by the test-api `getMergedEntry`.
- `requestId` — monotonic per client; echoed on the `entry` reply for matching; a client-side timeout resolves `null`.
- `scope` / `norm` / `display` — the lookup target. `display !== undefined` → `corpus.byKey.get(mergeKey(norm, display))`, else `corpus.byNorm.get(norm)`.
- **On receipt:** resolve the scope's corpus (`corpusForScope`, building from IDB if it's not the live owned scope), look the entry up, and reply `entry` with the tuple `[norm, display, score, rawScore, comment, sourceId]` (or `null`).

#### `__testFailNextBuild` (test-only)
`{ type: '__testFailNextBuild' }` — forces the next `syncConfig` build to throw, so the suite exercises the build-failure `selfReady` (`built: false` → the client settles the deferred run errored, no-hang settle path 4). Sibling of `__testCrash`.

#### `__testPatchTool` (test-only)
`{ type: '__testPatchTool', tool, method, message }` — the suite breaks a tool to exercise the error path, but the worker has its own `TOOLS` realm a page-side patch can't reach, so it patches the worker's copy (`message == null` restores the original).

#### `__testCrash` (test-only)
`{ type: '__testCrash' }` — throws uncaught, firing the parent `Worker`'s `error` event (the real crash signal the client's recovery path keys on).

### Worker → main

#### `pong`
`{ type: 'pong' }` — reply to `ping`.

#### `result` (all three tiers)
`{ type: 'result', runId, grouped, atomCount, ranAgainstOwned, payload }` — **pipeline output.** Always carries `ranAgainstOwned: true` (the worker always runs against its own corpus; main keys export/rebind eligibility on it).
- `runId` — main **drops stale results** whose `runId` isn't the latest dispatched.
- `grouped` — whether the bottom row is grouped (shapes `payload`).
- `atomCount` — atoms per row (the scroller also derives this from the stack alone, so row heights don't block on the result).
- The **atom encoding** — the shared unit of the transform/grouped tiers. An atom is a small tagged object, exactly one of:
  - `{ norm, display, score, rawScore, comment, sourceId }` — a **corpus atom**, shipped rich/self-contained (the same field set `buildFlatRows` emits), so main decodes it with no resident corpus. `sourceId` is the winning source's `dbKey`; `rawScore` is `undefined` for an unrescored row.
  - `{ s: { norm, display, score } }` — a **synthetic** atom: a tool output that exists in no wordlist (`wlEntry.wordlist === null`). Inline and self-contained, **not** looked up by norm on receipt.
  - plus optional `h` (the atom's `highlights`, omitted when null) and `g` (its `glyph`, one of `'→' | '↔' | '⊃'`, omitted when null).
- `payload` — tiered:
  - **filter/search** (the common, laggy case): all transferred, **no off-screen highlights, no per-row objects** beyond the inline first window. `payload = { indices, scores, widthHints, stats, histogramCounts, histogramLayout, existsInScope, existsInMerge, rebindQuery, rebindEntry, rebindExists, filtered, firstRows }`.
    - `indices` is an `Int32Array` of survivor indices into `ownedCorpus.entries`, **already sorted** by the run's `sort` axis/dir; `scores` is a parallel `Int32Array` (one score per survivor, in sorted order) the main thread scans for the count readout. `filtered` is `true` when the worker applied the score-range filter itself, in which case `indices`/`scores`/`widthHints`/`stats` describe the **filtered** survivor set (the windowed scroller fetches filtered positions directly); `false`/absent otherwise. `histogramCounts` is **always** the unfiltered distribution.
    - `widthHints = { maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }` — the one-pass column-width summary the scroller needs to size its grid tracks without scanning all rows. `maxRawDigits` is the rescore-preview arrow's raw-score column width, which main can't scan the full result for; main applies it only when the preview is active.
    - `firstRows` — the **first window's rich rows** (`buildFlatRows(0, min(FIRST_WINDOW, length))`), shipped inline with every flat result so main paints the above-the-fold rows instantly instead of flashing skeletons until a `fetchRows` round-trip lands. The scroller seeds its window cache from it.
    - **per-result stats summaries** (`stats` + `histogramCounts` any scope; `histogramLayout` scoped runs only): `stats: computeStatsRaw(scores)` (`{count,min,max,distinctScores}`). The order is load-bearing — `histogramCounts` is computed **first, over the unfiltered scores** (so out-of-range bars stay clickable); **then** a filtered run narrows `indices`/`scores`; **then** `stats` is computed **last, over the (now filtered) scores**. So `stats` describes the filtered set when `filtered`, the full set otherwise. `histogramCounts` buckets against a **scope-appropriate axis**: a merged run against `ownedAllSourcesAxis` (already on `selfReady`); a scoped run against `getHistogramLayout(ownedCorpus.entries, 'scoped:'+scope)`, shipped alongside as `histogramLayout` (merged ships `histogramLayout: null`). The client stashes the shipped layout in `data/derived.js`'s scope-keyed holder (`setShippedScopedLayout`), re-stamped on **every** flat result so a scope switch can't leave a previous scope's layout behind; `scopedHistogramLayout()` trusts it only while its scope-key still equals `state.selected?.dbKey`.
    - **per-result `existsInScope` / `existsInMerge`**: two booleans for the run's `existsQuery`. `existsInScope = ownedCorpus.byNorm.has(toNorm(existsQuery))` (the active scope's norms) feeds the add-entry FAB seed (`newEntrySeedQuery`); `existsInMerge = ownedMerged.byNorm.has(toNorm(existsQuery))` feeds the empty-state "this word exists / Add it" message (`_renderEmptyState`). Shipping both reproduces main's pre-existing merged-vs-scope consumer split. `null` when `existsQuery` is blank (or `ownedMerged` is absent for `existsInMerge`).
    - **per-result popover re-bind answer**: for the open edit popover's `rebindQuery`, the payload carries `rebindEntry` (a **rich row** `{ norm, display, score, rawScore, comment, sourceId }` or `null`) + `rebindExists` (boolean) + an echoed `rebindQuery`. The worker resolves them the same way the flat `findResultEntry`+`resultHasEntry` do — `rebindEntry = ownedCorpus.byKey.get(mergeKey(norm,display)) ?? ownedCorpus.byNorm.get(norm)` (a **full-corpus** lookup, so it re-anchors even to a range-filtered-out entry), `rebindExists = ownedCorpus.byNorm.has(norm)`. All `null` when no popover was open. Main rebuilds the rich `rebindEntry` into a `wlEntry` (`sourceId` → `state.sources`) and stashes the trio on the scroller; `findResultEntry`/`resultHasEntry` return the shipped answer when `ranAgainstOwned` and the stashed `_rebindQuery` matches the requested `(norm,display)`.
  - **transform chains**: `payload = { chains: [{ atoms: [<atom>, ...] }, ...] }` — one chain per row, each atom in the rich encoding above. Fires when any row is *rich* — carries a glyph, spans more than one word, or holds a synthetic — i.e. the flat index encoding would be lossy. The transform tier stays **fully materialized** (every chain ships, no windowing) by deliberate decision: it self-filters hard (anagram/behead emit only on merged-corpus hits), so it's never the freeze source the flat and grouped tiers are. Structured-cloned, not transferred: heavily filtered, so small.
  - **grouped** (windowed): `payload = { groups: [<group window>], stats, histogramCounts, histogramLayout, groupWidthHints, chainCount, groupCount, filtered }`. The grouped result is **windowed at both levels** (mirroring the flat tier), so `groups` is the **first window** of group ROWS only — `sorted.slice(0, GROUP_ROW_WINDOW)`, *not* the whole list — and within each, the chains are windowed too. The worker retains the full sorted+filtered group list as `lastGroupedResult` and serves later windows via `fetchGroups`/`fetchGroupChains` (above).
    - each group in the window is `encodeGroup(g)` = `{ key, anchor, _minScore, _maxScore, _count, firstChains }`. `key` is the tool-derived group key. `anchor` is `null` or the rich atom encoding (never `h`/`g`) for the group's anchor entry. `_minScore`/`_maxScore`/`_count` are the precomputed group stats — `_count` is the group's **full** chain count (the Count badge and "+N more" arithmetic read it, **not** `firstChains.length`). `firstChains` is the first `GROUP_FIRST_WINDOW` chains (`{ atoms: [<atom>, …] }`), wide enough that a collapsed group row never needs a chain fetch to fill its slot.
    - the result-level summaries are computed worker-side over **all** groups (main holds only a window, so it can't): `stats` (`computeStatsRaw` over the survivor scores), `histogramCounts` (always the **unfiltered** distribution, so out-of-range bars stay clickable), `histogramLayout` (the scoped layout on a scoped run, `null` on merged), `groupWidthHints` (the column-width summary the scroller sizes from without scanning every group), `chainCount` (total surviving chains across all groups), `groupCount` (total group rows — **the size main lays the scroller out from**; the shipped `groups` length is the window, not the count), and `filtered` (`true` when the worker applied the score-range filter — `groups`/summaries then describe the filtered set; histogram stays unfiltered). Structured-cloned.
- **On receipt:** the client checks the `runId` is the latest dispatched (else drop). For the **flat tier** it returns an index-backed result — `{ flat: true, indices, scores, widthHints, stats, histogramCounts, histogramLayout, existsInScope, existsInMerge, rebindQuery, rebindEntry, rebindExists, filtered, ranAgainstOwned, firstRows, atomCount, grouped: false }` — and the scroller stores the index array + scores + hints + shipped summaries, seeds its window cache from `firstRows`, and fetches off-screen windows via `fetchRows`. The shipped `histogramLayout` is stashed in `data/derived.js`'s scoped-layout holder. For the **grouped tier** it decodes the inline first window of group rows and seeds the grouped scroller's window cache from it, then lays the scroller out from the shipped `groupCount` (not the window length) and fetches off-screen group-row windows via `fetchGroups`, a group's later chains via `fetchGroupChains` on "+N more", and the whole result via `fetchAllGroups` on export — the result-level `stats`/`histogramCounts`/`histogramLayout`/`groupWidthHints`/`chainCount`/`filtered` ride alongside so main needs no full group list. For the **transform tier** it decodes every chain up front (no windowing). Decoding a group or chain walks each atom — a rich corpus atom → a `wlEntry` rebuilt from its inline fields (`sourceId` resolved via a `state.sources` Map built once per decode pass), `{s}` → a freshly built synthetic `wlEntry` (`{ norm, display, score, comment: '', wordlist: null }`, **not** norm-resolved) — reattaching `h`/`g` and the group `key`/`anchor`/stats. Either result settles the run's pending promise; `runPipeline` decrements the in-flight counter that gates `pipelineIdle()`. The score-range view filter then runs on main as a **no-op** when the worker already filtered (`_workerFiltered`); a score-range change re-runs the pipeline so the worker re-filters and windowing stays engaged.

#### `error`
`{ type: 'error', runId, stackRowIndex, message }` — a tool threw (a `ToolStageError`). `stackRowIndex` is the row's position in the run's stack (or `null` if it can't be located).
- **On receipt:** the client sets `stack[stackRowIndex]._error = message` → the red `⚠` row marker + `ErrorPopover`, and settles the run's promise with the errored shape (`{ aborted: false, errored: true, rows: [], atomCount, grouped: false }`). Main owns the per-run `_error` *reset* too — the client clears stale marks on every row at dispatch.

#### `selfReady`
`{ type: 'selfReady', configId, count, built, axis, version, sourceCounts, mergedCount }` — reply to `syncConfig`.
- `configId` — echoes the request's `configId` so the bridge resolves each `syncConfig`'s own reply (see `syncConfig` § *Reply correlation*).
- `count` — the number of synced sources.
- `built` — `ownedCorpusFresh && ownedScope === (scope ?? MERGED_ID)`, read at settle (the **currently-committed** state, not this build's own outcome). It is the **deferred-run drain gate** on the client: `true` ⇒ a usable owned corpus committed for this sync's scope, so a deferred run for that scope can dispatch (no-hang settle paths 1/3); `false` (build failed, or this build was superseded by one for a different scope) ⇒ the client does **not** mark the worker fresh — for a genuinely failed *latest* build it settles the deferred run errored (path 4), for a superseded build it ignores the reply (a newer sync will drain).
- `axis` — the per-config **all-sources histogram layout** (`{ mode, slots, min, max }`); see `syncConfig`. The scope-stable badge-gradient axis (`== the merged histogram layout`).
- `version` — `ownedConfigVersion`, monotonic, bumped once per committed `syncConfig`. Main caches `axis`/`sourceCounts`/`mergedCount` keyed by it, each ignoring a repeat version.
- `sourceCounts` — per-config **merged contribution counts**: `[{ sourceId, count }]`, one per configured source (`dbKey`, merge-priority order), `count` = how many merged entries that source *wins* (the "X" in the scope selector's "X of Y entries"). Derived from `ownedMerged.sourceCounts` — **always the merged build, never the active-scope `ownedCorpus`**. `null` on a build failure. Per-config, never per-run.
- `mergedCount` — `ownedMerged.entries.length`, the deduped merged total (the "All Wordlists" entry total, the download-button gate, the Welcome dialog's merge count — all reading `mergedEntryCount()`). `null` on a build failure. Per-config.
- **On receipt (main):** the client (`syncWorkerConfig`) **always** applies `axis`/`version` via `setShippedAllSourcesAxis` and `sourceCounts`/`mergedCount`/`version` via `setShippedConfigCounts` — these are the only source for those displays. Each set bumps the `configSummary$` signal so the async-arriving counts repaint their consumers (the merged-count/X-of-Y/badge-axis displays subscribe to it; bumping `cacheVersion$` there would loop the re-sync). Then `applySelfReadyFreshness` uses `built` to drain or settle the deferred run.

#### `corpusDump` (test-only)
`{ type: 'corpusDump', scope, entries, error? }` — reply to `dumpCorpus`. `entries` is an array of tuples `[norm, display, score, rawScore, comment, sourceId]` (the **oracle contract**). `rawScore` is `undefined` for a row no rescore rule changed. On a build error, `entries` is `[]` and `error` carries the message.

#### `entry` (test-only)
`{ type: 'entry', requestId, entry }` — reply to `queryEntry`. `requestId` echoes for matching. `entry` is the tuple `[norm, display, score, rawScore, comment, sourceId]` (same shape as a `corpusDump` row) or `null`.

## The deferred-run queue

With no resident main corpus to fall back on, a run whose owned corpus isn't yet fresh for its scope **can't dispatch** — there's no snapshot, no main-thread engine, nothing to run against. So the client **defers** the run and drains it when the worker becomes fresh for that scope. The triggers for a not-yet-fresh run: boot's first paint (before the boot build lands); a config-change re-sync gap; a My-Edits edit window; an import/fetch. (`setScope` is **not** a trigger — the worker rebuilds `ownedCorpus` synchronously from `ownedBuilt`, FIFO-before the run, so the run that follows finds the worker fresh.)

### The client's state (`ui/pipeline-worker.js`)

- **`deferredRun = { stack, sort, scope, resolve }`** — a single latest-wins deferral. A new deferral replaces the prior one (settling the replaced one aborted).
- **`ownedFreshScope`** — a **synchronous** mirror of the scope the worker's owned corpus is fresh for; `ownedFreshFor(scope)` is the race-free gate. `syncWorkerConfig` clears it synchronously at post time (mirroring the worker clearing `ownedCorpusFresh` at `syncConfig` handler start), so a run dispatched in the rebuild gap defers rather than running against the stale corpus. `sendWorkerScope` (setScope) optimistically re-sets the mirror to the new scope once any build has landed (the worker rebuild is synchronous + FIFO-before the run). `onWorkerCrash` clears it (forcing in-flight/incoming runs to defer until the respawn's `selfReady`).

### The dispatch path

`runOnWorker(stack, sort)` computes `scope` from `state.selected`; if `ownedFreshFor(scope)` it dispatches immediately (`dispatchRun`), else it **defers** — replacing any prior deferral (settling the replaced one `{aborted:true}`) and arming a timeout backstop. `drainDeferred` fires on a fresh `selfReady` (or a `setScope` mirror update) and dispatches the deferral, but only re-checks `ownedFreshFor` against the deferral's **own** scope, so a `selfReady` for a different scope leaves it deferred. The boot run repoints through this naturally: the boot run defers and drains on the boot `syncConfig`'s `selfReady`, and `init()` awaits `Promise.all([firstPaint, syncWorkerConfig(state.sources)])`.

### The no-hang guarantee

A hung deferred promise wedges `_pipelineRunning` → `pipelineIdle()` → the whole Playwright suite, so **every** deferred promise must settle via exactly one of six paths:

1. **Normal drain.** A `selfReady` with `built: true` → `applySelfReadyFreshness` sets `ownedFreshScope` → `drainDeferred` dispatches → the `result` resolves it.
2. **Superseded before dispatch.** A replacing `runOnWorker` (a newer run) or a `setScope` resolves the prior deferral `{aborted:true}` before it ever dispatched.
3. **Build commits → drain dispatches.** Same as path 1 from the build side; a crash-respawn's re-registration also lands here (the respawn's `selfReady` drains the re-registered deferral).
4. **Build fails.** A failed `syncConfig` build still posts `selfReady`, but with `built: false` (`ownedCorpus` null). The client settles the deferred run **errored** (the `erroredResult` shape `{aborted:false, errored:true, rows:[], atomCount, grouped:false}`), not waiting. **Critical nuance:** a *superseded* build also reports `built: false`, so the client only settles errored when the failing `selfReady`'s `configId` is still the latest (`configId === configRequestId`) **and** its scope matches the deferral — a superseded build's reply is ignored, because a newer `syncConfig` is in flight that will drain the deferral. Getting this wrong either hangs (settling nothing) or prematurely fails a run a later build would serve.
5. **Crash while deferred.** `onWorkerCrash` handles `deferredRun` in **both** branches: below `MAX_CRASHES` it re-registers via `runOnWorker` (which re-defers and drains on the respawn's `selfReady`); at `MAX_CRASHES` it latches `workerUnavailable` and settles the deferred run errored.
6. **Timeout backstop (5 s).** If a `selfReady`/crash signal is somehow lost, a timer resolves the deferred run `{aborted:true}` rather than leaving `pipelineIdle` wedged forever.

## Cancellation / supersession

Single thread → **at most one run executes at a time**. Supersession is message-driven:

1. Each `run` carries a monotonic `runId`. The worker stores `latestRunId` (written by its own `onmessage`, so no shared memory).
2. A **newer `run` implicitly supersedes** an older one — no explicit `cancel` needed for the fast-typist case. `cancel` exists only for teardown / search-cleared.
3. The worker's yielder, at each due point, does a **macrotask yield** so a queued `run`/`cancel` message can fire, then checks `if (thisRunId !== latestRunId) throw AbortError`. The throw unwinds the superseded run; a tiny scheduler then starts whatever run is latest.

**The yield must be a macrotask, and `setTimeout(0)` is the one to use** — empirically confirmed to preempt an in-flight run within one yield window on all three engines, and (a fresh callback per call) naturally **re-entrant**. Re-entrancy matters because superseding runs overlap by construction. A *microtask* yield (`queueMicrotask`) drains only microtasks and **never** delivers the `message` task. `scheduler.yield()` is **forbidden** in the worker: its boosted-priority continuation **starves** the `message` on Chromium (preempts on Firefox, absent on WebKit), so relying on it would silently break cancellation on the dominant engine.

**A superseded run sends NO reply** (it throws `AbortError` internally and moves on). The main client therefore **must settle that `runId`'s pending promise itself** (as aborted) on dispatch of the newer run — otherwise `pipelineIdle()` (which the whole Playwright suite awaits after a keystroke) dangles. **Reap superseded runs by `runId`, not by waiting for a terminal message:** an abandoned run's terminal event can arrive *after* the winner's `result`, or never, so the client tracks the in-flight `runId` and settles the stale one when it dispatches the newer one.

The worker yields **coarsely** (~30 ms) — it has no UI to keep at 60 fps, so it yields only often enough to honor cancellation, which also makes the compute faster than the main thread's ~6 ms cadence.

## Worker lifecycle

- **Spawn:** lazily via `getWorker()` on first use, one worker per tab — but that first use is the boot-time `syncConfig`, so in practice it comes up at boot. Spawned via `new Worker(new URL('./engine/worker.js', baseURL), { type: 'module' })`, where `baseURL` is **`main.js`'s `import.meta.url`**, injected at boot through `configurePipelineWorker({ baseURL })`. (Anchoring on `main.js` is load-bearing — bundling inlines the `new URL` literal verbatim without rewriting its relative path, and the client module sits at a different depth than the bundle, so a client-anchored URL is dev-passing/prod-404.)
- **Memory:** the worker holds the only corpus copy — roughly **1× peak corpus memory** in the worker (rich `entries` + `byNorm`/`byKey`/`_initialChains`, plus the separate `ownedMerged` when scoped away from merged). Main holds no merged/scoped corpus, only My Edits' `rawEntries`.
- **Crash → respawn → rebuild → re-dispatch.** A worker crash — the parent `Worker`'s `error` / `messageerror` event, **distinct from a tool `error` *message*** (which the worker posts cleanly over a live connection) — has no main-thread engine to fall back to, so recovery is *respawn + rebuild-from-IDB + re-dispatch*:
  - **Crash detection.** The client wires `error` and `messageerror` listeners on the `Worker` at spawn, both → `onWorkerCrash`. (Both are catch-alls for a dead worker; neither carries a usable recovery payload.)
  - **Teardown.** `onWorkerCrash` removes the dead worker's listeners, `terminate()`s it, nulls `worker`, **clears `ownedFreshScope`** (so in-flight/incoming runs defer until the respawn's `selfReady`), and increments `crashCount`.
  - **Below `MAX_CRASHES` (respawn path).** Capture and clear both `pendingRun` and `deferredRun`, call `syncWorkerConfig(state.sources)` — which respawns the worker (`getWorker()`) and posts `syncConfig` so the fresh worker **rebuilds its owned corpus from IDB** — then re-dispatch the in-flight run **and** re-register the deferred run through the normal `runOnWorker(stack, sort)` path, chaining `.then(resolve)` onto each **original** awaiter. Re-dispatching through `runOnWorker` (not a bespoke post) is load-bearing: it keeps supersession intact (a newer run advances `runCounter` and settles this rescue `{aborted:true}`) and re-defers each run via the freshness mirror, so they drain on the respawn's `selfReady`.
  - **At `MAX_CRASHES` (graceful latch).** There's no corpus to rescue onto, so latch `workerUnavailable = true` and resolve both the in-flight `pendingRun` and the `deferredRun` with the **errored shape** `{aborted:false, errored:true, rows:[], atomCount, grouped:false}`. `runOnWorker` short-circuits every subsequent run to that errored result on its first lines (also settling any prior deferral), so latched runs **settle gracefully and never hang**. The errored/empty result flows through the normal render path to an empty scroller.
  - **`MAX_CRASHES = 2`** — a hard ceiling on a crash → respawn → recrash loop.
  - **State.** `pipelineWorkerState()` returns `{ workerUnavailable, crashCount }`.
  - **Test hooks.** `crashWorkerForTest()` posts `__testCrash` (exercises the real `error`-event wiring); `forceWorkerCrashForTest()` calls `onWorkerCrash` directly (deterministic); `failNextWorkerBuildForTest()` posts `__testFailNextBuild` (exercises the build-failure `selfReady`).

## Invariants (do not break these)

1. **`byNorm` cannot drift.** The worker builds `byNorm` via the one shared `buildByNorm(entries)` ([`engine/snapshot.js`](../site/src/engine/snapshot.js)) — canonical row = the **code-unit-minimum** display per norm. The per-norm splice path uses the sibling `canonicalNormRow(rows)`, which applies the **same** rule to one norm's rows; the owned-corpus splice routes through it, so it can't disagree on case variants (`'CAT'` vs `'Cat'`). Never reimplement the canonical-row selection on one side.
2. **`ownedEntryToIndex` stays paired with `ownedCorpus`.** It is built once per corpus rebuild (never per run) and replaced wholesale on every splice; a desync silently indexes one corpus into another and corrupts every rendered row. The flat result's indices name `ownedCorpus.entries`, so a `fetchRows` is served only against a still-fresh, scope-matched corpus (`fetchResultFresh`). The grouped result's retained `lastGroupedResult` holds chains that reference *that* run's corpus by entry identity, so its windowed fetches carry the same freshness discipline: `groupedResultFresh` (`lastGroupedResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastGroupedResult.scope`) gates `fetchGroups`/`fetchGroupChains`/`fetchAllGroups`, dropping any fetch whose corpus changed since the run. `lastFlatResult` and `lastGroupedResult` are mutually exclusive — every result branch sets one and nulls the other — so a fetch addressed to the wrong tier is dropped by the runId mismatch.
3. **Worker = the corpus; main = presentation.** The worker is the only place a merged/scoped corpus exists, and its corpus is **rich** — it carries `comment` and source identity because it feeds rendering directly through the rich rows/atoms it ships. `engine/` stays DOM-free (enforced by `tests/unit/engine-dom-free.test.mjs`): the worker reasons about norms/displays/scores/comments and resolves `sourceId` to a `dbKey`, but never renders or touches the DOM. Anything view-only (HTML, the resolved `wordlist` object, the My-Edits raw-score swap) is reconstructed on main.

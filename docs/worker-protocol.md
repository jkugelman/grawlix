# Web worker protocol — the main ↔ pipeline-worker contract

This is the **source-of-truth interface contract** between the main thread and the pipeline web worker: who owns which data, every message that crosses the boundary (fields + what each one *does* on receipt), and the cancellation/supersession rules. Code is not the only source of truth — when you add or change a message, a data structure, or the supersession policy, **update this doc in the same commit.**

**Why a worker at all, and the deeper *why* behind each decision** live in [`design.md` § Cooperative runtime](design.md) (why the off-thread move, the data-ownership inversion, the rejected alternatives). This doc is *what the interface is*, present-tense.

## Where we are now

**The worker owns the merged and scoped corpus, unconditionally — and now the per-source entry records too.** Main holds no merged/scoped *corpus* and, post-inversion, **no non-Edits source's entries at all** — only `state` (sources' metadata, scoring tier labels, search state), **My Edits' `rawEntries`** (its seed/optimistic-render source, edited every keystroke), and the per-config summaries the worker ships (`sourceCounts`, `sourceTotals`, `rescoreInputs`, `mergedCount`, the all-sources badge axis). Every other source is metadata-only on main: it is **not parsed at boot** (the worker reads its text from IDB and builds), and a fetch/import parses it only **transiently** (to write IDB + seed rules) without retaining it. The worker builds its own corpus from IndexedDB on a `syncConfig`: it loads, parses, rescores, and merges every configured source itself, and the corpus never crosses the boundary as bulk data. Results no longer cross as indices into a shared main corpus — there is no main corpus to index into; the worker ships **rich, self-contained rows and atoms**. The few main-thread reads that need a non-Edits source's bytes (bake, the not-fresh download/mirror fallback) re-read IDB transiently.

`runPipeline` ([`ui/tool-stack.js`](../site/src/ui/tool-stack.js)) posts a `run` (with the active `sort`) to the worker through the client ([`ui/pipeline-worker.js`](../site/src/ui/pipeline-worker.js)). The worker always executes against its own owned corpus, sorts and filters the result itself, and ships the **flat** (filter-only) tier as a survivor `count` plus an inline first window of rich rows (it owns the sorted survivor list and serves later windows on demand) — the same windowed shape as the other two tiers. A flat scan additionally **streams** its survivors as `partial` snapshots as they're found — each a **SORTED** window over the client's reported viewport plus a climbing total and a version, ahead of that terminal `result`, so the table paints a climbing, correctly-sorted result that reshuffles as better matches arrive and a mid-stream scroll always sees a sorted window of *the rows it's actually viewing* (viewport-driven streaming — see `viewport`); the `result` is the reconciling truth (a client may ignore the partials entirely) and, because the worker sorts incrementally with a *total* comparator, ships the exact order the stream painted — no end-of-stream reshuffle — see `partial`. The **grouped** tier ships its first window of group rows (each with a `firstChains` window of its chains) plus result-level summaries; the worker retains the full sorted+filtered group list and serves later windows on demand. A **tuple** tool (Umiaq) produces a fixed-arity **tuple** result — structurally a grouped result (each tuple is a row of N side-by-side single-atom chains) — and rides the grouped tier's entire path: payload shape, retained `lastGroupedResult`, and `fetchGroups`/`fetchGroupChains`/`fetchAllGroups`. A long run additionally **streams** its tuples as `partialGroups` snapshots (the grouped-tier sibling of `partial`) — each a SORTED window of tuple rows over the client's reported viewport plus a climbing total and a version, ahead of the terminal `result` — so the table paints climbing tuples that reshuffle as the join finds them; because the incremental merge uses a *total* comparator (the group axes plus a unique `g.key` tiebreak), completion adopts the same order with no reshuffle. Which tier streams is driven by tool IO-modes: a streamed-out producer streams — a flat filter, the tuple producer (whether it's the last non-inert tool or followed only by stream-safe filters, which run per-batch in its emit path so the streamed tuples are already filtered), or a **transform** when it's the last non-inert tool (the worker folds its mirror pairs **online** into a running sorted list — `unify`'s whole-set fold becomes an incremental one, see `partialChains`). A buffered-out group tool does not; nor does a filter chained *after* a transform (v1). The only discriminator is the result's `laneKind`: `'single'` for a flat/transform result, `'set'` for a group cluster (an equivalence class — trimmable, a member can drop while the cluster survives), `'record'` for a tuple (fixed positional lanes — all-or-nothing). The client keys its render off that (a record draws bare positional lanes, no overflow chrome) but the transport is identical — a record rides the grouped tier's path. The **transform** tier ships every chain's rich atoms up front (it self-filters hard, so it's small) and **streams** them as `partialChains` snapshots as it scans. The client owns run-id tracking, settling a superseded run as aborted, dropping stale results, the per-run `_error` reset, and — because a run can outrun the corpus it needs — the **deferred-run queue** (below).

The flat scroller windows by default: it requests its visible rows from the worker via `fetchRows`, rendering shimmer skeletons on a miss (rare, since the first window ships inline with the result) and serving ordinary scrolling from a bounded local cache. The grouped scroller windows the same way at two levels — the group-ROW list via `fetchGroups` (windowed group rows, sized from the shipped `groupCount`) and a group's CHAINS via `fetchGroupChains` when the "+N more" popover pages past the inline window. Export (`fetchAllRows` flat / `fetchAllGroups` grouped), serialize (`serializeFor` — merged or single-source, for download + disk mirror), and the entry-panel bridges (`fetchEditSeed`/`fetchProvenance`/`fetchFamily`) read the worker's owned corpus the same way. My Edits add/edit/delete drive `editEntry`/`deleteEntry` commands that splice the owned corpus in place and write the My Edits IDB from the worker, in O(affected norms) — no full rebuild. A re-fetch/re-import of a populated source drives `applyFetched`, which diffs the new text against the worker's resident copy and splices the same way (batched over the changed norms), falling back to a wholesale rebuild only when the diff approaches the whole list — the fetch/import path no longer re-reads and re-merges every source.

A worker crash respawns a fresh worker, has it rebuild the owned corpus from IDB, and re-dispatches the in-flight (and any deferred) run; after `MAX_CRASHES` it latches `workerUnavailable` and settles every run gracefully errored. There is no main-thread engine fallback — the flip left no main corpus to run against.

### Streaming is authoritative — completion is bookkeeping, never a recompute

**Hard rule.** When a run streams, the streamed snapshots (`partial` / `partialGroups` / `partialChains`) *are* the result. The terminal `result` message exists to do end-of-stream **bookkeeping** — flip the scroller out of its busy/streaming state, ship the final window if one is needed, and **adopt** the already-streamed order, histogram, and stats. It must **not** recompute, re-sort, re-filter, or otherwise re-derive a *streamed* result "for real."

**Why this is a rule and not a nicety.** The streaming emitter and a terminal recompute are *different code paths* (incremental `mergeSortedGroups` vs. a full `sortGroups`; per-batch accumulated `histScores` vs. a full pass over `rows`). If they ever diverge, a terminal recompute silently overwrites the streamed result with the "correct" one — so a streaming bug is **masked** rather than surfaced. Adopting the streamed result instead means any such bug shows up as a visible wrong result, which is what you want: fix the streaming path, don't paper over it at the end. There must be **no observable "post-streaming state" that differs from the last streamed frame** beyond the busy indicator turning off.

**The one legitimate compute-at-completion** is the **non-streamed** path: a result small/fast enough that it never streamed (`streamState.streamed === false`) has no authoritative stream to adopt, so `postResult` filters + sorts it from scratch there. That branch is fine; the streamed branch must adopt.

**All three terminals adopt** when `streamed`: flat adopts `lastFlatResult.indices`, transform adopts `lastTransformResult.chains`, and the tuple/group terminal ([`postResult`, worker.js](../site/src/engine/worker.js) `laneKind !== 'single'`) adopts `lastGroupedResult.groups` — each incremental merge used a *total* comparator, so the streamed order equals a from-scratch sort. The histogram, stats, and summaries are adopted too (the emitter accumulates them onto the retained result each batch). The non-streamed path is the one legitimate compute-at-completion, via the shared `deriveSlot` → `deriveFlatResult`/`deriveGroupResult`/`deriveTransformResult` builders — so a re-derived result is structurally identical to a streamed one. A cross-run **cache hit** rides this exact same non-streamed derive path (`deriveSlot` over the retained join), which is why a served result equals a fresh finish and carries the terminal-only `capped`/exists/rebind fields.

This authority is what makes **the join / view separation** possible: because the terminal only adopts, the streamed result already *is* the truth, so a later view change (sort / score-range) re-derives the view over the **retained join** rather than re-running the pipeline — see `reproject`.

## Data ownership

The dividing line: **the worker owns the corpus and everything derived from it; the main thread owns `state` and presentation.** The worker is the only place a merged or scoped corpus exists, so its corpus is **rich** — it carries `comment` and source identity, because it feeds rendering directly through the rich rows/atoms it ships.

### Main thread owns

| Data | Shape | Notes |
|---|---|---|
| `state` | sources, scoring (tier labels), search state | the app's root state; never crosses the boundary |
| **My Edits'** `rawEntries` | `[{ norm, display, score, comment }]` | the **only** per-source entries main holds — the seed/optimistic-render source for an edit, mutated every keystroke. Every *other* source is metadata-only on main: not parsed at boot, parsed only transiently on a fetch/import (to write IDB + seed rules) and not retained. The deduped *merge*, any *scoped corpus*, and every non-Edits source's records live only in the worker. Bake and the not-fresh download/mirror fallback re-read a non-Edits source's IDB text transiently |
| shipped per-config summaries | `sourceCounts` (`[{ wordlist, count }]`, merge-winner subset), `sourceTotals` (per-source totals, all sources), `mergedCount`, the all-sources badge axis, the scoped histogram layout | read straight from the worker's `selfReady`/`result`; `getSourceCounts`/`sourceTotal`/`mergedEntryCount` ([`data/merge.js`](../site/src/data/merge.js)) read **only** these — there is no local recompute path |
| score-range view filter, histogram, stats, virtual scroller, rendering | — | the scroller windows the table; **all three tiers** (flat, grouped, transform) arrive pre-sorted and pre-filtered from the worker — main no longer sorts any tier. The score-range filter is the worker's job (it ships filtered survivors); main's local view-filter is the no-op fallback path |
| the pipeline-worker **client** | run-id → promise tracking; the deferred-run queue; flat result → index-backed handoff; rich atom → chain-row decode | [`site/src/ui/pipeline-worker.js`](../site/src/ui/pipeline-worker.js) |

An asset is **evicted the moment its tool leaves the stack** (`evictUnusedAssets`, run when the user stack changes): each run computes the assets its stack still references and `invalidate()`s any loaded asset not among them, reclaiming ~100 MB+ on iOS without a re-fetch on re-add (`invalidate()` drops only the in-memory copy; the IDB record survives). `idbGet`/`idbPut` live in `data/storage.js` (not importable from `engine/`), so the worker opens the **same** IndexedDB DB/store (`grawlix`/`data`, v1) directly — the cache is per-origin. The freshness check probes the cached map's key with `getKey` (never deserializing it) and keeps the content-length validator in a **separate** `sizeIdbKey` record, established on first check for a cache predating it. Also how the worker reads each source's wordlist text (`data_<dbKey>`) and writes the My Edits IDB |
| the My Edits disk-merge **baseline** | `sync_worker_<editsKey>` IDB record `{ baseline }` | the 3-way-merge common ancestor. The worker is its **sole writer** — it reads and advances it in **both** sync directions (`mergeDisk` inbound, `flushEdits` outbound). Main keeps the file-handle I/O + watch loop + conflict dialog (`data/disk-sync.js`) but **never** writes this record; main only **deletes** it (alongside `sync_main_`) on detach teardown, which can't race the worker since a merge runs only while synced and the delete only on teardown |

### Building the corpus

The worker builds its corpus from the same IDB text and the same `engine/` code main would have used, so the result is byte-identical to a main-thread merge. `buildByNorm`/`canonicalNormRow` ([`engine/snapshot.js`](../site/src/engine/snapshot.js)) — the canonical-row selection per norm — are shared with the worker's owned-corpus splice, so case variants (`'CAT'` vs `'Cat'`) can never be resolved two different ways. (Those two functions are all that remains of `engine/snapshot.js`; its old columnar pack/unpack — a *wire* format that shipped the corpus main→worker, then rebuilt objects on arrival — is gone now that the worker owns and builds the corpus itself.)

A non-Edits source's per-entry records are themselves stored columnar at rest (`cols`), distinct from that retired wire pack: the entries never leave the worker, so the columns are read in place through `sourceAccessor` (binary search over the norm-sorted columns, transient views on demand) and never unpacked into a resident object array. The merge runs identically against the views a columnar source yields and the objects My Edits yields.

## Message encoding & packing

**Every message crosses as a small structured-clone object — kept cheap by windowing, not by binary packing.** Each message is a plain object with a `type` discriminator and a handful of scalar fields (`runId`, the serialized `stack`, `sort`, `scope`, …) plus, for a result, a bounded **window** of rich rows and a few summary scalars. There is no transfer list and no typed-array bulk payload: the lever that keeps the laggy case cheap is that **no tier ever ships O(results) data** — the worker owns the full result and serves off-screen windows on demand (`fetchRows`/`fetchGroups`/`fetchTransformRows`). The pathological 1-letter-matches-1M case ships a ~60-row window plus a count and summaries, never a million rows or a 1M-element highlights array.

**Results ship rich, self-contained rows for every tier.** Every tier's atoms cross **rich and self-contained** (`{ norm, display, score, rawScore, comment, sourceId, sourceIds, activeIds }`), and synthetic tool-output atoms travel inline as `{ s: {...} }`. There is no `{ i }` index-only atom encoding and no integer-index survivor list: with no resident main corpus there is nothing to index into. The flat tier ships a scalar `count` (the survivor total main sizes the scroller from) plus an inline window of rich rows; the worker owns the sorted survivor list and serves later windows via `fetchRows`, so main never holds it.

Every rich row/atom carries `sourceId` (the **winning** source's `dbKey`), `sourceIds` (the **set** of every source that contributes the entry, winner included — the entries table's Sources presence-matrix), and `activeIds` (`⊆ sourceIds`, the subset whose values the row actually *shows* — the matrix colors these and mutes the rest). All three are computed **per shipped row** at encode time (`shipContributors`), *not* stored on every corpus entry — eagerly attaching them made load O(corpus) when only the windowed ~hundreds of rendered rows ever need them. The resolver is scope-specific: `mergedContributors` for a merged row (display-aware, in lockstep with the merge's `eligible`; `activeIds` = the score winner + the list supplying the shown spelling + the comment fall-through source, each the single highest-priority source (a same-value duplicate is muted) — so a bare winner and the rich list that spells it both light up, but a redundant copy does not), `scopeSourceIds` for a scoped row (`sourceIds` = norm-level cross-list over enabled sources plus the scoped source, like the provenance panel; `activeIds` = the scoped source alone, since the row shows only its own values). A synthetic `{ s }` atom has no source, so no `sourceIds`/`activeIds`; main defaults them to `[]`.

**All three tiers are windowed, identically in shape.** The flat tier ships a one-level list — an inline first window of rich rows + a `count` + result-level summaries; main fetches later windows on demand (`fetchRows`/`fetchAllRows`). The transform tier ships the same shape — an inline `firstChains` window + `chainCount` + summaries (`fetchTransformRows`/`fetchAllTransformRows`). The grouped tier windows at **two** levels — the first window of group ROWS, each with a `firstChains` window of its chains, plus summaries (`fetchGroups`/`fetchGroupChains`/`fetchAllGroups`). (Transforms self-filter hard — anagram/behead emit only on merged-corpus hits — so the list is usually small; windowing it removes the latent freeze the old fully-materialized path risked if a future transform were less selective.)

### Encoding at a glance

| Payload | Encoding | Transport |
|---|---|---|
| message envelope (`type`, `runId`, `stack`, `sort`, `scope`, `existsQuery`, `scoreRange`, `rebindQuery`) | plain object | structured clone (tiny) |
| flat result: survivor `count` (the size main sizes the scroller from) — describes the **filtered** set when `filtered`, else the full set | number | structured clone (tiny) |
| flat result: column width hints | small `{ maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }` object | structured clone (tiny) |
| flat result: stats (scope-independent) + histogram counts (any scope, **always unfiltered**) + histogram layout (scoped runs only) + `filtered` flag | small `{ stats, histogramCounts, histogramLayout, filtered }` object | structured clone (small) |
| flat result: `existsInScope` | boolean / `null` | structured clone (tiny) |
| flat result: `rebindQuery` echo + `rebindEntry` (rich row / `null`) + `rebindExists` | small object | structured clone (tiny) |
| flat result: `firstRows` (the inline above-the-fold window) | array of rich rows | structured clone (small — bounded by `FIRST_WINDOW`) |
| flat result: `familyStart` (the demarcation-bracket boundary flag) | a boolean **per rich row** (in `firstRows` and every `fetchRows` window) | structured clone (rides each row) — set only under the Entry/family sort, else absent; per-row so the bracket renders mid-stream with no resident array |
| flat result: highlights | **not shipped** for the off-screen rows — re-derived on the worker per `fetchRows` window | — |
| transform-chain atoms | rich atom objects (`{norm,display,score,rawScore,comment,sourceId,sourceIds,activeIds}` or `{s}` synthetic, each with optional `h`/`g`) | structured clone (small) |
| transform result: first window of chains + result-level summaries | `{ firstChains }` (window of encoded chains) + `chainCount` + `{ stats, histogramCounts, histogramLayout, widthHints, filtered }` + `{ existsInScope, rebindQuery, rebindEntry, rebindExists }` | structured clone (small — `firstChains` bounded by `FIRST_WINDOW`) |
| grouped result: first window of group rows + result-level summaries | group summaries `{ key, anchor, _minScore, _maxScore, _count, firstChains }` (window) + `{ stats, histogramCounts, histogramLayout, groupWidthHints, chainCount, groupCount, filtered }` + top-level `capped` (the tuple search hit its result ceiling — the tuple count is a floor, rendered with a trailing `+`; always `false` off the tuple path) | structured clone (small — bounded by `GROUP_ROW_WINDOW` × `GROUP_FIRST_WINDOW`) |
| `rows`/`allRows` reply | array of rich rows, each with an `atoms` array | structured clone |
| `transformRows`/`allTransformRows` reply | array (window / full) of encoded chains | structured clone |
| `groups`/`groupChains`/`allGroups` reply | windowed group summaries / a group's chain window / full groups (`encodeGroupFull`) | structured clone |
| serialize reply (`serialized.text`) | a single serialized wordlist string — merged or single-source (`retry: true` instead when not fresh) | structured clone |

The rule of thumb for a new message: **everything is a small structured-clone object; a result stays cheap by shipping a bounded window plus a count and summaries, never the full list — the worker serves the rest on demand.**

## Messages

Messages on one `Worker` are **FIFO**, which gives ordering for free (a `setScope` or `syncConfig` always arrives before a `run` that depends on it). Every message is a plain object with a `type` discriminator (see *Message encoding & packing* for how its fields and any bulk payload are encoded).

### Main → worker

#### `ping`
`{ type: 'ping' }` — liveness / spawn check. Worker replies `pong`.

#### `run`
`{ type: 'run', runId, stack, sort, scope, existsQuery, scoreRange, rebindQuery }` — **execute the pipeline against the worker's owned corpus.**
- `runId` — monotonic; the supersession key (see *Cancellation*).
- `scope` — `MERGED_ID` when the active scope is the merged view, else the scoped wordlist's `dbKey` (derived from `state.selected`, which is the wordlist object or the `MERGED_ID` string — never a dbKey). The worker executes against `ownedCorpus`, which it keeps built for this scope; the client only dispatches a run once it has confirmed the worker is fresh for `scope` (else it defers — see *The deferred-run queue*). The worker retains `scope` on the flat result and uses it to gate `fetchRows` enrichment.
- `stack` — the serialized tool stack: an array of `{ tool, params, grouped }` descriptors (≈ what the URL encodes), plucked off each `ToolStack.getStack()` row by the client. The worker rebuilds each row via `makeToolRow(tool)` then overlays `params`/`grouped` — the same defaults-then-override order `router.js applyURL` uses, so the executor sees the identical row shape. The tool **code** is looked up in the worker's own copy of the catalog; functions never cross the boundary. An unknown `tool` key is skipped.
- `existsQuery` — the **raw trimmed search text** (or `null` when blank), so the worker can answer `existsInScope` (does the query already exist in the run's scope?). Main sends the raw string and lets the worker `toNorm` it (same `engine/norm.js toNorm` both threads use); it does **not** apply `isLiteralQuery` here — that gate stays at the consumer (`newEntrySeedQuery`).
- `scoreRange` — the **raw range string** (e.g. `'60-80'`, `'30+'`, `'45'`) the global score-range filter is set to, or `null` when no filter is active. Sourced from `app-view.js activeScoreRange()` (the canonical range owner — **not** the scroller's `this.scoreRange`); the worker `parseRange`s it. The worker filters its survivor set against any range that parses, shipping the filtered `count` + window with `filtered: true`; a non-empty range that doesn't parse (a transient typing state like `"60-"`, which `parseRange` returns `null` for — matching main) ships the **unfiltered** set with `filtered: false` so the table shows everything rather than flashing empty. The histogram counts are bucketed **before** the filter (over the unfiltered scores), so out-of-range bars stay clickable. On a `run`, `scoreRange` seeds the initial `viewSpec`; a later score-range change **reprojects** (re-derives the view over the retained join) rather than re-running — see `reproject`.
- `rebindQuery` — `{ norm, display }` of the **open entry panel's re-anchor target**, or `null` when no panel is open (`entryPanelRebindQuery()`). When a new result lands while the panel is open, the table re-anchors it via `EntriesScroller.updateEntries → EntryPanel.rebindEntry → scroller.findResultEntry / resultHasEntry`, which run **synchronously** in the render path — so rather than awaiting the worker there (which would ripple a dual async path through the sync render), the open panel's target **rides the run** and the worker resolves it against `ownedCorpus`, shipping the answer on the same `result` (`rebindEntry`/`rebindExists`). Resolved exactly as main's flat `findResultEntry`+`resultHasEntry` once did — a **full-corpus** `byKey.get(mergeKey(norm,display)) ?? byNorm.get(norm)` lookup that re-anchors even to an entry **filtered OUT** of the visible (range-filtered) view.
- `sort` — `[{ key, dir }]`, the ordered multi-sort list, highest priority first (`AppView.sortList`). A plain header click sends a single-entry list; a modifier-click (Shift/Ctrl/Alt/Cmd) sends several. **Honored for the flat tier:** the worker sorts the survivor indices by the list, so every window it serves (and the inline first one) is already ordered, composing the picks the same way `composeSortAxis` does (each pick's primary at its own direction, then the primary pick's fixed-direction tiebreakers) over its own single-tier `FLAT_SORT_AXES` copy (`entry`/`length`/`score`). Those axes read `corpus.entries[idx].{norm,display,score,family}` + `norm.length` (and `comment` for that axis), all worker-resident. Alphabetical collation is on `display` (via `displayOf`), never the stripped `norm` — `toNorm` drops spaces, so a multi-word base like `lather up` would otherwise sort after `lathers up`. Even `entry`/asc is sorted (it groups by `family` and breaks ties on `display`, unlike the norm-keyed native merge order), so main never re-sorts. The grouped tier honors the list too (`sortGroups` → `composeSortAxis`), and the transform tier honors it as well (`sortChainRows` → `composeSortAxis` over the chain-tier `SORT_AXES` in [`engine/sort.js`](../site/src/engine/sort.js) — the same object-shaped axes main uses to label its headers, so the two can't drift). **No tier sorts on main anymore.** On a `run`, `sort` seeds the initial `viewSpec`; a later sort change **reprojects** rather than re-running or re-sorting on main — see `reproject`.
- **On receipt:** worker sets `latestRunId = runId`, stashes the request as `pending`, and drives a drain-to-latest run loop. A run first **probes the finished cache** at `(scope, stack-signature)`: an identity-valid hit (`cacheEntryValid` — the corpus object it was bound to is still resident) rehydrates the tier's display slot from the retained join, reprojects it to the run's requested sort/score-range (recomputing every score-derived summary — a hit never reuses a stored histogram), and ships a **`result`-shaped message** (the same non-streamed-terminal path, so it carries `capped`/`existsInScope`/`rebind*`; **not** a reproject snapshot) — synchronously, no yield. A miss builds the **prefix `resume` seam** (`makePrefixResume`, probing `prefixCache` for the longest valid prefix of this stack — lengths `userStackLen..1`) and runs `executePipeline(ownedCorpus, stack, signalShim, emit, resume)`: the executor seeds from the longest cached prefix `state` (the whole user stack on a keystroke, a shorter prefix on a tool-row edit), else the bare corpus, and reruns only the rows past the seed — snapshotting each inter-stage state back to `prefixCache` as a tile. It posts `result` — unless superseded first — and, if the finished run cleared the admission rule, **writes its join to the finished cache** on that terminal (never mid-stream, never for a superseded run). The signal shim's `aborted` is `thisRunId !== latestRunId`. **`prefixCache` needs no user-stack-change or corpus-change invalidation hook** (unlike the old pre-search slot): a changed row simply keys a different prefix, and every seed gates on `cacheEntryValid` — the corpus-object identity test — so a tile from a rebuilt corpus is dropped at probe time. Structural edits still purge proactively via the `replaced`-hook (below).

#### `cancel`
`{ type: 'cancel' }` — explicit supersession, for teardown / search-cleared. Optional given that a newer `run` implicitly supersedes (see *Cancellation*).
- **On receipt:** worker advances `latestRunId` past every live run and clears `pending`, so the in-flight shim aborts at its next yield and no run is queued. No reply.

#### `viewport`
`{ type: 'viewport', runId, start, end }` — **the scroller's currently-visible row window for the in-flight streaming run.** A streaming snapshot (`partial`/`partialGroups`) ships *this* window each batch — **viewport-driven streaming** — instead of a fixed top window, so a user scrolled anywhere watches their rows refresh live and never strobes to skeletons. Fire-and-forget; no reply.
- `runId` — the run the viewport names. The emitter honors `pendingViewport` only when `pendingViewport.runId === runId`; a stale viewport from the prior run is ignored, so a fresh run defaults to the top until its own first viewport arrives (and the scroller resets to the top on a new run anyway).
- `start` / `end` — the half-open visible window (already `VS_BUFFER`-padded by the scroller's `_visibleRange`). The emitter clamps it to `[0, total]` and ships `groups.slice`/`buildFlatRows` over it.
- **Sent:** from the scroller's `_render` (`_reportViewport`) whenever a streaming run is active and the visible range changed (deduped, so a batch-driven re-render at an unchanged scroll position doesn't re-post). The worker processes it at a run/scan yield (FIFO, between `partial`s), so the next snapshot reflects it.
- **On receipt:** store `pendingViewport = data`; the next `partial`/`partialGroups` slices its window from it (see `streamWindow`).

#### `reproject`
`{ type: 'reproject', runId, reprojectId, sort, scoreRange, recomputeHistogram }` — **re-derive the view (sort → score-range → window) over the retained join for the displayed run, without re-running the pipeline.** This is the join / view separation's whole point: sort and score-range are *view* refinements, not new joins. Sent from `reprojectMergedScroller` ([`ui/rendering.js`](../site/src/ui/rendering.js)) when the user changes the sort (`applySortList`) or the score-range filter (`setScoreRange`), and from `refreshAfterEdit` for a set-preserving rescore (the corpus is spliced in place, so the join stays valid). `reconcileSort` runs first so an invalid sort key for the tier isn't sent.
- `runId` — the displayed run: `pendingRun?.runId ?? lastResultRunId` (the streaming run mid-stream, else the settled one). A reproject is **not** a run — it does not create a `pendingRun`, advance `runCounter`, or resolve `pipelineIdle`.
- `reprojectId` — monotonic per client; echoed on the reply so rapid reprojects (which all target the same `runId`) match their own reply.
- `sort` / `scoreRange` — the new `viewSpec`, the same shapes the `run` carries.
- `recomputeHistogram` — `true` for a **rescore** reproject (a set-preserving score edit, or a background rescore), where the join's scores changed so the flat histogram must re-bucket. `false`/absent for a pure sort/filter reproject, where the histogram is invariant. Only the **flat** tier honors it — grouped/transform recompute their summaries (histogram included) on every reproject regardless.
- **On receipt (`handleReproject`):** if the retained result's `runId` doesn't match, or the corpus isn't fresh for its scope (the same `fetchResultFresh` discipline), reply `reprojectStale`. Otherwise mutate the shared `viewSpec` **in place** (a still-streaming emitter reads it next batch), re-derive the view + summaries from the retained **join** in place (keeping `join` growing for a mid-stream run — a fresh object would strand rows produced after the reproject), bump `version`, and reply `reprojected`. The flat histogram is **invariant under sort/filter** (it's over the unfiltered join) so it is not recomputed *unless* `recomputeHistogram` — a rescore reproject re-buckets it over the join's new scores, or it would silently lag the edit.

#### `reprojected` (worker → main)
`{ type: 'reprojected', runId, reprojectId, version, … }` — a re-derived view snapshot, shaped like the tier's `partial`/`partialGroups`/`partialChains` (flat carries `firstRows`, grouped `firstGroups`, transform `firstChains`, plus `total`/`windowStart`/stats/histogram/`filtered`). The client (`ingestReprojectToScroller` → `EntriesScroller.ingestReproject`) ingests it **without settling `pendingRun` or the deferred queue**. Mid-stream (the scroller is streaming this `runId`) it rides the continuing-batch path, refreshing the live snapshot in place. Settled, a dedicated `_ingestReprojectSettled` updates the view fields and re-seeds the window cache at the shipped window — it must **not** flow through `_ingestResult`, which clears the stream scalars and would strobe skeletons. The histogram *layout* is invariant under a **sort/filter** reproject, so main keeps its stashed one — but a **rescore** or **refresh-on-consent** reproject re-buckets over a *changed* corpus whose scoped layout can gain/lose slots, so the client **adopts the shipped `histogramLayout`** (present on a scoped run, `null` on merged — which rides the ack's all-sources axis instead). Skipping that adoption leaves a stale-length layout that mismatches the fresh counts and blanks the histogram (`buildStatsBarHTML`'s length guard).

#### `reprojectStale` (worker → main)
`{ type: 'reprojectStale', runId, reprojectId }` — the worker no longer holds the displayed run fresh (a scope/config change since it settled), so it can't reproject. The client resolves `reprojectPipeline`/`repatchPipeline` with `{ stale: true }` and `reprojectMergedScroller`/`repatchMergedScroller` falls back to a full `refreshMergedScroller` re-run.

#### `repatch`
`{ type: 'repatch', runId, reprojectId, stack, sort, scoreRange }` — **re-derive a FLAT result's join over the freshly-spliced corpus and ship it as a `reprojected` snapshot.** This is refresh-on-consent's fast path for the flat tier (see `applyFetched`): a background *structural* auto-update to a flat displayed result refreshes the set in place — no refresh chip — because a flat row matches per-entry, so an add/delete is a cheap re-scan. (Combination tiers — tuple/group/transform — can't; an added entry can partner an existing one into a result an incremental re-scan misses, so they pin + chip instead.)
- Unlike `reproject` (a pure *view* re-derive over the retained join), `repatch` **re-runs the pipeline** to build a fresh join against the current corpus, so it carries the serialized `stack`. It reuses `reproject`'s reply channel: `reprojected` on success, `reprojectStale` when the worker can't (falling `repatchMergedScroller` back to a full re-run). The client (`repatchPipeline`) shares the `pendingReproject`/`reprojectId` slot with `reproject`.
- **Sent:** from `repatchMergedScroller` (`ui/rendering.js`) when `applyWordlistText`'s `viaToast` fork sees the `repatch` flag on the `fetchApplied` ack.
- **On receipt (`runRepatch`):** enqueued into the run loop (`drainRuns`) **only when idle** (no live or queued run) — running its `executePipeline` concurrently with a real run would corrupt the shared retained result and the `prefixCache` it seeds/offers into; a live/queued run already recomputes everything, so a repatch arriving then is moot and dropped (main's `pendingReproject` self-heals on its next view op). It seeds/offers `prefixCache` like a real run (`makePrefixResume`), so a repatch of an expensive filter stack reuses its cached prefix. It does **not** advance `latestRunId`, so a newer `run` supersedes it via the ordinary signal shim. On the same freshness discipline as `handleReproject` (scope/config unchanged since the run), it re-runs the flat pipeline buffered (no emit — one atomic snapshot, not a strobing re-stream), rebuilds `lastFlatResult` with a fresh join against the live corpus (keeping the displayed `runId`, continuing the monotonic `version`, dropping the gap-cover pin), and posts a `reprojected` snapshot; otherwise (not fresh, superseded, or an unexpected tier flip) it replies `reprojectStale` (or, on abort, nothing).

#### `setScope`
`{ type: 'setScope', scope }` — **rebuild `ownedCorpus` for a newly-selected scope** from the resident `ownedBuilt`, synchronously (no IDB read — `ownedBuilt` already holds every source's parsed+rescored wordlist from the last `syncConfig`). Fire-and-forget; no reply.
- `scope` — `MERGED_ID` when the merged view is selected, else the scoped wordlist's `dbKey`.
- **Sent:** from `rendering.js`'s `setScope`, **before** the scope's run dispatch, and **only when the client's freshness mirror is non-null**. FIFO then puts the rebuild ahead of the run, so `ownedCorpus` matches the run's scope before any execution or enrichment, and the client mirrors the new scope synchronously on `sendWorkerScope` (so the run dispatches rather than defers). When the mirror is **null** (a `syncConfig` is reshaping the corpus, or none has landed yet), `sendWorkerScope` does **not** send a bare `setScope` — it escalates to a full `syncConfig` for the now-current scope, because a lightweight `setScope` would leave the deferred scoped run with no drain signal (an in-flight sync's `selfReady` carries *its* scope, not this one) → the run hangs with no backstop. The escalation's `selfReady` drains it. See *The deferred-run queue* § dispatch path.
- **On receipt:** if `ownedBuilt` is null (no `syncConfig` yet) → **inert** (leave `ownedCorpus`/`ownedScope`/`ownedCorpusFresh` as-is). Otherwise rebuild `ownedCorpus` (`ownedMerged` for a merged scope, else `buildScopeCorpus(ownedBuilt, scope)`), via `setOwnedCorpus`, which sets `ownedScope = scope ?? MERGED_ID` and `ownedCorpusFresh = true`. The rebuild is synchronous, so it completes the instant the message is processed — before the scope-switch's run arrives. Because it's synchronous and FIFO-before the run, `setScope` needs **no** deferral on the client side.

#### `check-assets`
`{ type: 'check-assets' }` — **freshness-check every owned data asset.** Fired by main once at boot and every `UPDATE_CHECK_INTERVAL` thereafter, **independent** of the wordlist auto-update setting and of whether any wordlist auto-fetches — the worker owns the assets, so their refresh is never gated by the wordlist path (the gap the old corpus-as-passenger check had, where a user with no URL wordlists never got corpus updates). Fire-and-forget; no reply.
- **On receipt (`handleCheckAssets`):** for each asset in `DATA_ASSETS`, probe its **data** record with `getKey` (presence without deserializing the megabytes); **absent ⇒ skip** (never loaded → nothing to keep fresh). Otherwise `HEAD` the asset URL for its `content-length`. If **no size baseline is stored yet** (a cache predating the `sizeIdbKey` record), **establish** it — store the remote size and stop; absence is not a change. If the stored baseline matches, stop. On a difference: `invalidate()` the in-memory copy, **delete** the IDB data + size records, and — **only if the asset was in active use** (`has()`) — `load()` it again now; otherwise leave it cleared for the next on-demand load. Offline / HEAD errors leave the cached asset untouched. The in-memory `invalidate()` is what fixes the cross-thread staleness (the worker's own copy, the one that serves runs, drops on a refresh).

#### `preload-asset`
`{ type: 'preload-asset', asset }` — **warm one data asset.** Fired by main when a tool that declares `def.asset` is added to the stack (Space-out → `'unigrams'`), so the asset is fetching before the first keystroke rather than blocking the first `prepare`. `asset` is the logical key (`DATA_ASSETS[].key`). Fire-and-forget; no reply.
- **On receipt:** `getDataAsset(asset)?.load()` (errors swallowed — surfaced when the tool runs). A no-op if already loaded (the load-promise guard).

#### `fetchRows` (windowed row fetch)
`{ type: 'fetchRows', requestId, runId, start, end }` — **request a window `[start, end)` of the retained flat result.** The flat scroller fetches its visible window + prefetch buffer, renders shimmer skeletons on a miss, and serves ordinary scrolling from a bounded local cache (seeded from the result's inline `firstRows`, so the first paint rarely misses).
- `requestId` — monotonic per client; echoed on the `rows` reply so a stale response (superseded by a newer request) is matched and dropped.
- `runId` — which flat result this window names. The worker retains the **last flat result** only (`lastFlatResult = { runId, version, indices, scope, highlighters }`). A grouped or rich (transform-chain) result nulls `lastFlatResult`, so a fetch for a non-flat result is dropped by the runId guard.
- `start` / `end` — the half-open window into the sorted survivor list. `start` is floored at 0, `end` capped at `length`; a `start` past the end simply yields an empty `rows`. `start | 0` / `end | 0` coerce.
- **On receipt:** dropped silently (no reply) unless the retained result is still **serveable** (`fetchResultFresh`: `lastFlatResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastFlatResult.scope`) — the same supersession discipline as runs. Main re-fetches against the current result on the next run. Otherwise post `rows` with the clamped window, always **rich** (built by `buildFlatRows`), stamped with the current `lastFlatResult.version` (which **climbs mid-stream** as each `partial` re-sorts — see `partial`).

#### `rows` (windowed row fetch reply)
`{ type: 'rows', requestId, runId, version, start, rows }` — reply to `fetchRows`.
- `requestId` / `runId` — echoed for matching.
- `version` — the sorted-array snapshot the window was served at. **Mid-stream** the client drops a reply whose `version` no longer matches its current snapshot — the order has moved past it, so the window would paint stale-order rows mixed into the live snapshot. Ignored post-completion (the client isn't streaming).
- `start` — the floored window start the worker served (`max(0, requested)`; differs from the requested `start` only when it was negative).
- `rows` — an array, one **rich** row per index in the window: `{ norm, display, score, rawScore, comment, sourceId, sourceIds, activeIds, atoms, familyStart? }`. `sourceId` is the winning source's `dbKey`, `sourceIds`/`activeIds` the presence/active contributor sets (see *Message encoding*); `rawScore` is `undefined` for an unrescored row (structuredClone preserves the slot). `atoms` is an **array** — one slot for a plain row, more when stacked highlighting searches produce multiple same-word atom lines — each `{ highlights, glyph }` (`highlights` is the re-derived search-match range array, `null` when no highlighting filter is active; `glyph` is `null`, since flat rows never carry one). `familyStart` is the demarcation-bracket boundary flag (present only under the Entry sort; the worker compares each row's `family` to its predecessor in the sorted array, so it's correct for any window). The client (`_richRowToChain`) rebuilds each row's `wlEntry` from the inline fields and resolves `sourceId → state.sources`.

There is **no** index-only row shape: with no resident main corpus, an index would be un-decodable. The freshness guard above (`fetchResultFresh`) is what makes a rich-only reply sound — a fetch whose corpus changed between the run and the fetch is dropped, not served wrong; main re-fetches on the next run.

#### `fetchAllRows` (full-result row fetch, export)
`{ type: 'fetchAllRows', requestId, runId }` — **request the ENTIRE retained flat result** (no window) so main can format it for **export** (Copy / .txt wordlist / CSV / JSON). It is `fetchRows` with `start = 0, end = indices.length` — same retention, same `fetchResultFresh` guard, same rich row shape (built by the shared `buildFlatRows`, so an export row encodes identically to the same entry's scroller row).
- `requestId` — monotonic per client, in its **own request-id space** (independent of both `fetchRows`' and the run's id spaces), echoed on the `allRows` reply for stale-drop matching; a client-side timeout resolves `null` so main can recover rather than hanging. (Grouped/transform export is **always** local — it formats resident `ChainRow[]`, not a flat result — and never issues this message.)
- `runId` — which flat result to serve; the same `fetchResultFresh` guard as `fetchRows` (drop silently otherwise).

#### `allRows` (full-result row fetch reply)
`{ type: 'allRows', requestId, runId, rows }` — reply to `fetchAllRows`. `requestId`/`runId` echo for matching. `rows` is the **whole** retained result, one **rich** row per survivor index — the *same* row shape and the *same* `buildFlatRows` builder as the `rows` reply, so an export row can't drift from the scroller's windowed row. The client reconstructs a `ChainRow` per row (resolving `sourceId → state.sources`); the result is the `ChainRow[]` the export formatters walk.

#### `fetchGroups` / `fetchGroupChains` / `fetchAllGroups` (windowed grouped result)

The grouped tier windows like the flat tier — but at **two levels**, because a grouped result is a list of group ROWS and each group holds a list of CHAINS, and either dimension can be the size that freezes main. The worker owns, sorts, and filters the grouped result and retains the full sorted+filtered list (`lastGroupedResult = { runId, groups, scope }`, where each `group` carries its FULL `chains`). The `result` ships only the first window of group rows (each with a `firstChains` window); main fetches more group rows on scroll, more of a group's chains on "+N more", and the whole result on export. All three fetches are guarded by `groupedResultFresh(runId)` (the grouped sibling of `fetchResultFresh` — `lastGroupedResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastGroupedResult.scope`), so a fetch whose corpus changed since the run is dropped silently rather than served against the wrong corpus; main re-fetches on the next run.

#### `fetchGroups` (windowed group-row fetch)
`{ type: 'fetchGroups', requestId, runId, start, end }` — **request a window `[start, end)` of the retained grouped result's group ROWS**, the grouped analogue of `fetchRows`. The grouped scroller windows the group-row list: it renders the visible group rows from a bounded local cache (seeded from the result's inline first window), shimmer skeletons on a miss, and fetches the missing window. This is the fix for the grouped-render freeze — main holds only a window of group rows, never decodes the whole list.
- `requestId` — monotonic per client; echoed on the `groups` reply so a stale (superseded) response is matched and dropped.
- `runId` — which grouped result this window names; the `groupedResultFresh` guard drops a fetch for a superseded run or a result that's since been replaced by a flat/transform one.
- `start` / `end` — the half-open window into the sorted group-row list (`start` floored at 0, `end` capped at `groups.length`; `| 0` coerces).
- **On receipt:** dropped silently unless `groupedResultFresh(runId)`. Otherwise post `groups` with the clamped window, each group **encoded as a summary envelope + `firstChains` window** (`encodeGroup`) — *not* its full chains.

#### `groups` (windowed group-row fetch reply)
`{ type: 'groups', requestId, runId, version, start, groups }` — reply to `fetchGroups`. `requestId`/`runId` echo for matching. `version` is the `lastGroupedResult` snapshot the window was served at — **mid-tuple-stream** the client drops a reply whose `version` no longer matches its current snapshot (the order has moved past it), mirroring the flat `rows` reply; ignored post-completion. `start` is the floored window start served. `groups` is an array of **encoded group summaries** (`encodeGroup`): each `{ key, anchor, _minScore, _maxScore, _count, firstChains }` — `key` the tool-derived group key; `anchor` the rich anchor-atom encoding or `null`; `_minScore`/`_maxScore`/`_count` the precomputed group stats (`_count` is the group's **full** chain count, the source for the Count badge and the "+N more" arithmetic, **not** `firstChains.length`); `firstChains` the first `GROUP_FIRST_WINDOW` chains (each `{ atoms: [<atom>, …] }`, the rich atom encoding) for the collapsed row's slot-fill. The client decodes each group, resolving `sourceId → state.sources` per atom.

#### `fetchGroupChains` (windowed per-group chain fetch, "+N more")
`{ type: 'fetchGroupChains', requestId, runId, groupKey, start, end }` — **request a window `[start, end)` of ONE group's CHAINS**, for the "+N more" popover (`GroupMorePopover`) on a group whose chain count exceeds what the collapsed row or the popover's first page shows. The popover paginates `POPOVER_CHUNK` (200) chains at a time as the user scrolls, caching by **absolute** chain index so a cross-window atom edit routes to the right atom.
- `requestId` — monotonic per client; echoed on the `groupChains` reply for stale-drop matching.
- `runId` — the grouped result; `groupedResultFresh`-guarded.
- `groupKey` — which group's chains (the `key` from its summary). The worker finds the group by key in `lastGroupedResult.groups`; an unknown key is dropped.
- `start` / `end` — the half-open window into that group's full chain list (`start` floored at 0, `end` capped at the group's `chains.length`).
- **On receipt:** dropped silently unless `groupedResultFresh(runId)` and the group is found. Otherwise post `groupChains` with the group's `chains.slice(lo, hi)` encoded.

#### `groupChains` (windowed per-group chain fetch reply)
`{ type: 'groupChains', requestId, runId, groupKey, start, chains }` — reply to `fetchGroupChains`. `requestId`/`runId`/`groupKey` echo for matching. `start` is the floored window start served. `chains` is the window of that group's chains, each `{ atoms: [<atom>, …] }` in the rich atom encoding. The popover decodes them into its absolute-index chain cache.

#### `fetchAllGroups` (full grouped-result fetch, export)
`{ type: 'fetchAllGroups', requestId, runId }` — **request the ENTIRE retained grouped result** (every group with its FULL chains, no windowing) so main can format it for **export** (Copy / .txt / CSV / JSON). The grouped sibling of `fetchAllRows`: a one-round-trip full-result walk worker-side, restoring export completeness that windowing would otherwise cut (a windowed group ships only `firstChains`, so exporting from the windowed rows would silently drop every chain past the window).
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `allGroups` reply for stale-drop matching; a client-side timeout resolves `null` so main can recover rather than hang.
- `runId` — which grouped result to serve; the same `groupedResultFresh` guard.
- **On receipt:** dropped silently unless `groupedResultFresh(runId)`. Otherwise post `allGroups` with every group **encoded full** (`encodeGroupFull` — the summary envelope + the group's complete `chains`, not `firstChains`).

#### `allGroups` (full grouped-result fetch reply)
`{ type: 'allGroups', requestId, runId, groups }` — reply to `fetchAllGroups`. `requestId`/`runId` echo for matching. `groups` is the **whole** sorted+filtered group list, each encoded as `{ key, anchor, _minScore, _maxScore, _count, chains }` (`encodeGroupFull`) — the summary envelope plus the group's **complete** chains. The client decodes the full groups and the export formatters walk them; the per-group `chains` here are exhaustive, so a >`GROUP_FIRST_WINDOW`-chain group exports every member.

#### `fetchTransformRows` (windowed transform-chain fetch)
`{ type: 'fetchTransformRows', requestId, runId, start, end }` — **request a window `[start, end)` of the retained transform result's chains**, the transform analogue of `fetchRows`. The scroller windows the chain list: visible rows render from a bounded local cache (seeded from the result's inline `firstChains`), shimmer skeletons on a miss, and the missing window is fetched.
- `requestId` — monotonic per client; echoed on the `transformRows` reply so a stale (superseded) response is matched and dropped.
- `runId` — which transform result this window names; the `transformResultFresh` guard drops a fetch for a superseded run or a result since replaced by a flat/grouped one.
- `start` / `end` — the half-open window into the sorted chain list (`start` floored at 0, `end` capped at `chains.length`; `| 0` coerces).
- **On receipt:** dropped silently unless `transformResultFresh(runId)`. Otherwise post `transformRows` with `lastTransformResult.chains.slice(lo, hi).map(encodeChain)`.

#### `transformRows` (windowed transform-chain fetch reply)
`{ type: 'transformRows', requestId, runId, version, start, chains }` — reply to `fetchTransformRows`. `requestId`/`runId` echo for matching. `version` is the `lastTransformResult` snapshot served — **mid-stream** the client drops a window whose `version` the order has moved past (mirrors the flat `rows`/`groups` guards); ignored post-completion. `start` is the floored window start served. `chains` is the window of encoded chains (`{ atoms: [<atom>, …] }`). The client decodes each into a `ChainRow` (atoms' `sourceId` → `state.sources`) and the scroller caches them by absolute index. A reply for a superseded run (`runId !== lastResultRunId`) is dropped client-side so a stale window can't paint.

#### `fetchAllTransformRows` (full transform-result fetch, export)
`{ type: 'fetchAllTransformRows', requestId, runId }` — **request the ENTIRE retained transform result** (no windowing) so main can format it for **export**. The transform sibling of `fetchAllRows`/`fetchAllGroups`: a one-round-trip full-result walk, restoring export completeness windowing would otherwise cut.
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `allTransformRows` reply for stale-drop matching; a client-side timeout resolves `null`.
- `runId` — which transform result to serve; the same `transformResultFresh` guard.
- **On receipt:** dropped silently unless `transformResultFresh(runId)`. Otherwise post `allTransformRows` with every chain encoded.

#### `allTransformRows` (full transform-result fetch reply)
`{ type: 'allTransformRows', requestId, runId, chains }` — reply to `fetchAllTransformRows`. `requestId` echoes for matching. `chains` is the **whole** sorted+filtered chain list, encoded. The client decodes them into `ChainRow[]` for the export formatters.

#### `serializeFor` (corpus serialize, download + disk mirror)
`{ type: 'serializeFor', requestId, scope, format }` — **serialize a worker-owned corpus to wordlist text** so a download or disk mirror needs no main-thread corpus read. `scope` discriminates the target: `MERGED_ID` serializes the deduped merge (`ownedMerged`) for the merged download (`downloadMergedWordlistFromPanel`) / merged disk mirror; any other `scope` is a **source `dbKey`**, serializing that one source's full rescored entry list for the individual download (`downloadSourceWordlist`) / per-source disk mirror (`MirrorSync._serialize`). A download and a disk mirror are the same artifact — a wordlist file for one scope + format — so they serialize **byte-identically**; there is no sort flag, the output is always `sortedEntries(...)` (norm asc, then score desc so a consumer that keeps the first line per norm gets the highest-scored variant).
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `serialized` reply for stale-drop matching; a client-side timeout resolves `null` (distinct from the worker's `retry`).
- `scope` — `MERGED_ID` for the merge, else a source `dbKey`.
- `format` — the output-format object (`{ spaces, punctuation, accents, comments }`, from `getOutputFormat()`) that `serializeEntries` applies. Main sends the resolved format so the worker doesn't read localStorage.
- **On receipt:** `serializeEntriesForScope(scope)` resolves the entries — guarded by `ownedCorpusFresh`; `MERGED_ID` → `ownedMerged.entries`, else the matching `ownedBuilt` source via `sourceAccessor(wl).collectRescored()` (the columnar store materialized to transient rescored views, in norm-sorted order). A miss (not fresh, or no such source) returns `null` and replies **`retry: true`** — *never* `text: ''`, because a consumer that wrote that empty string would clobber the synced file to 0 bytes. A fresh-but-empty merge is a real `[]` (all sources disabled), distinct from the `null` miss, so it still serializes to an honest `""`. The per-source path serializes the source's **full rescored entry list undeduped** — NOT `buildScopeCorpus`, whose dedup/variant-collapse would diverge from main's `getRescoredEntries`-based bytes. Otherwise `text = serializeEntries(sortedEntries(entries), format)` and replies `serialized`. The disk-sync seam (`configureMirrorSerializer`, `data/disk-sync.js`) keeps the data layer off `ui/`: it hands disk-sync a `(scope, format) → { text } | { retry } | null` worker attempt and disk-sync owns the fallback. The merge has no resident main corpus, so on a `retry` its mirror skips the write and re-arms (and the download re-asks, bounded) rather than mirroring empty; a source still holds its bytes (`rawEntries` or IDB), so its fallback serializes locally (sorting identically, so the bytes match).

#### `serialized` (corpus serialize reply)
`{ type: 'serialized', requestId, text }` **or** `{ type: 'serialized', requestId, retry: true }` — reply to `serializeFor`. `requestId` echoes for matching. `text` is the serialized wordlist string (always sorted; merged or single-source per `scope`), present whenever the corpus was fresh (an all-disabled merge serializes to `""`). `retry: true` replaces it when the worker wasn't fresh / no source matched `scope`, signalling the caller to ask again rather than write the absence as empty.

#### `fetchEditSeed` (entry-panel seed)
`{ type: 'fetchEditSeed', requestId, norm, display }` — **resolve the All Wordlists merge winner for a clicked `(norm, display)`** so the inline entry panel can seed without a main-thread corpus read. Called only from an **editable** scope: from **My Edits** (the one editable non-merged scope), where the winner may be a *different, higher-priority* wordlist main can't reach without its corpus, and from any **route open** (deep link / Back-Forward, which has no clicked row). An All Wordlists direct click seeds locally (the clicked row IS the winner); a **read-only foreign scope** doesn't call this at all — it shows the scoped list's *own* value, resolved locally from its rescored entries.
- `requestId` — monotonic per client, in its **own request-id space, independent of the run's `runId`** (a panel query must not interfere with run supersession). Echoed on the `editSeed` reply so a stale response is matched and dropped; a client-side timeout resolves `null` so main falls back to the clicked atom.
- `norm` / `display` — the clicked atom's norm and display (`null` for a bare click).
- **Target is `ownedMerged`, never `ownedCorpus`** — the seed is the merged winner regardless of the active scope. **On receipt:** if `ownedMerged` is present **and** `ownedCorpusFresh` (the latter stands in for an `ownedMerged`-specific freshness flag — a `syncConfig` clears it synchronously and only a committed `syncConfig` or an edit command re-sets it, so `fresh ⇒ ownedMerged` is current), resolve the winner via the shared `resolveEditSeedWinner(ownedMerged, norm, display)` — `byKey.get(mergeKey)`, then the **bare-display quirk** (a bare click with no bare merged row picks the first-alphabetical spelled variant, else `byNorm.get(norm)`). Reply `editSeed` with `winner = { norm, display, score, comment, sourceId }` (`sourceId` = the winning source's `dbKey`, so main resolves it to `state.sources` and applies the My-Edits raw-score adjustment locally — that adjustment stays on main, where `edits.rawEntries` is resident). When the norm is **absent from the merge**, or the worker isn't fresh, reply `winner: null` and main falls back to the clicked row (`row._wlEntry`).

#### `editSeed` (entry-panel seed reply)
`{ type: 'editSeed', requestId, winner }` — reply to `fetchEditSeed`. `requestId` echoes for matching. `winner` is `{ norm, display, score, comment, sourceId } | null`.

#### `fetchFamily` (entry-panel related entries)
`{ type: 'fetchFamily', requestId, norm, display, boundNorm, boundDisplay }` — **the entry's relatives** for the panel's Related-entries list: its word-family siblings (`cat`/`cats`) **and** the differently-spelled entries that share its norm (`Boney M.`/`Boney M`/`boneym` — kept navigable here even when a concrete click scopes them out of the provenance table; a bare click lists them there too). Fired at open **and re-fired per entry-text keystroke** (like the provenance query), so `norm`/`display` (the **query**) may be typed text not yet in the corpus; `boundNorm`/`boundDisplay` name the entry the panel is **bound** to (what was opened/clicked), equal to the query except mid-rename. Resolved against **`ownedMerged`** (the full enabled merge), *not* the active-scope `ownedCorpus` — Related entries **ignores scope**, so a single-list scope still surfaces every relative across the merged wordlist (same source as `fetchEditSeed`). Its own request-id space; a timeout resolves `[]`.
- **On receipt:** guarded by `ownedMerged && ownedCorpusFresh` (the freshness rule the edit-seed fetch documents). Compute the query's family `familyKey(display ?? norm, ownedMerged.vocab)` — re-keyed from the query, *not* read off a looked-up row, so a live rename's not-yet-saved spelling resolves its own family — resolve the **bound** row (`byKey.get(mergeKey(boundNorm, boundDisplay))` ?? `byNorm.get(boundNorm)`), scan `ownedMerged.entries` for `e.norm === norm || e.family === family` (a per-query O(n) scan, no persistent index — the norm clause catches same-norm spellings whose token-derived family differs), and reply `family` with the members. The **bound entry is the `current`** (bold-highlighted) while the query still names it — so the list stays stable as the user clicks between siblings — but is **dropped from its own relatives once the query diverges** (a live rename): the old spelling would unify into the new one on save, so it is not a sibling of it. Sorted by display.

#### `family` (entry-panel related-entries reply)
`{ type: 'family', requestId, members }` — reply to `fetchFamily`. `members` is `[{ norm, display, score, comment, sourceId, current }]`, empty when the corpus isn't fresh or the entry has no relatives. `comment`/`sourceId` carry the merged winner's comment and winning-source `dbKey` so a click navigates the panel onto the sibling's **real winner row** — seeding score/comment and the My-Edits adopt link exactly like a table-row click, with no synthetic seed to refine.

#### `fetchProvenance` (entry-panel provenance + preview)
`{ type: 'fetchProvenance', requestId, typedRaw, previewRaw, clickedNorm, clickedDisplay }` — **resolve the panel's live preview (the merge row for the typed/seed text) and its cross-wordlist provenance table** so the inline entry panel does no main-thread corpus read. The two targets the worker holds: `ownedMerged` for the preview (the merge winner), and `ownedBuilt` (the all-sources rich wordlists, enabled **and** disabled) for the provenance walk — disabled/non-winning lists must still surface.
- `requestId` — monotonic per client, in its **own request-id space, independent of both the run's `runId` and the edit-seed lane**. Echoed on the `provenance` reply; a client-side timeout resolves `{preview:null,rows:null}`.
- `typedRaw` — the raw text driving the **provenance target** (the entry-input value per keystroke; `''` at the initial open so the target falls to the clicked atom). `previewRaw` — the raw text driving the **footer preview** (the input value per keystroke; the seed entry at open). The two diverge **only at the initial open**, where the synchronous code uses two different targets — `previewWlEntry(seed.entry)` for the footer but the clicked atom for the table — which a single raw string can't express; per keystroke both are the input value.
- `clickedNorm` / `clickedDisplay` — the clicked atom's norm and **raw** spelling (a bare entry stays `null`, not its norm), the provenance target's fallback when `typedRaw` is blank. A **concrete** `clickedDisplay` scopes the walk to that spelling (rival spellings move to Related entries, `fetchFamily`); a **bare** click (`clickedDisplay` null) is a wildcard — the walk lists every spelling of the norm. Collapsing a bare click to its norm (the old `displayOf`) silently dropped the concrete siblings it unified with.
- **On receipt:** guarded by `ownedMerged && ownedBuilt && ownedCorpusFresh`; a miss replies `{preview:null, rows:null}`. Otherwise it reproduces main's logic verbatim:
  - **preview** = `previewRaw.trim() ? (ownedMerged.byNorm.get(toNorm(previewRaw)) || null) : null`, shipped as `{ norm, display, score, comment, sourceId }` (lean; main re-resolves `sourceId → state.sources`) or `null`.
  - **provenance target**: norm = `(preview-for-typedRaw)?.norm ?? (typedRaw.trim() ? toNorm(typedRaw) : clickedNorm)`; display = `typedRaw.trim() ? null : clickedDisplay` — a concrete click scopes to its spelling; a bare click (`clickedDisplay` null) and a rename/new-entry typing case both leave display `null`, keeping the whole norm.
  - **rows**: for each source in `ownedBuilt` order (= `state.sources` order), each entry in `sourceAccessor(wl).rescoredForNorm(targetNorm)` whose spelling matches the target — mirroring the merge's display eligibility (`concreteDisplay`/`isDistinguishing`, § corpus.js `mergedContributors`): a bare entry (null display) unifies with any spelling, a concrete one must equal `targetDisplay`; a `null` `targetDisplay` (a bare click, or the typed case) keeps the whole norm. When a concrete click scopes the walk, the differently-spelled siblings it drops surface in the panel's Related entries (`fetchFamily`). Each row is `{ sourceId: wl.dbKey, enabled: wl.enabled !== false, entry: { norm, display, score, rawScore, comment } }`. Main resolves `sourceId → state.sources` and renders through the same body builder, so the table HTML is byte-identical to a local build.

#### `provenance` (entry-panel provenance + preview reply)
`{ type: 'provenance', requestId, preview, rows }` — reply to `fetchProvenance`. `preview` is `{ norm, display, score, comment, sourceId } | null`; `rows` is the ordered provenance array `[{ sourceId, enabled, entry: { norm, display, score, rawScore, comment } }]` (`rawScore` is the source's pre-rescore score, `undefined` when that source's rules didn't remap it — the panel's provenance table always renders a raw → rescored arrow from it, unlike the entries table whose arrow is gated on the open rescore editor), or `null` when the worker wasn't fresh. A `null` `rows` means "worker didn't answer" → main keeps its last-good render. Main holds the last shipped `rows`/`preview` per open panel and re-renders only when a newer reply lands (a monotonic token drops stale replies, never cleared to empty mid-flight — so the table/footer don't flash).

#### `planEdit` (entry-edit planner)
`{ type: 'planEdit', requestId, mode, clicked, typed, trashScore }` — **plan a My Edits write-set for the entry panel / a save**, so main needs no resident foreign rescore indexes. `planEntryWrite` ([`engine/edit-plan.js`](../site/src/engine/edit-plan.js)) walks every enabled source's `getRescoredByNorm`/`computeMergedBucket` to decide deletes / keep-copies / foreign-downscore / the "already exists" block — data only the worker holds. Modeled on `fetchProvenance` with its own request-id lane; a client timeout resolves `null` so the panel keeps its last-good plan and a save retries then bails.
- `requestId` — monotonic per client, in its **own request-id space**, echoed on the `editPlan` reply for stale-drop matching.
- `mode` — `'create'` or `'edit'` (rename/override/adopt/rescore all plan through `'edit'`).
- `clicked` — the edit baseline, **leaned to `{ norm, display }`** (the only two fields `planEntryWrite` reads) — a raw wlEntry's `wordlist` back-reference would structured-clone the whole source. `null` for a create.
- `typed` — `{ raw, score, comment }`, the panel's current values. `score`/`comment` are folded into `upserts` but **never branch** the plan, so a structural plan is reused across score/comment changes; the preview re-injects the live values locally and a save sends a fresh `planEdit` with the real ones.
- `trashScore` — `getTrashScore()` (localStorage-derived, worker-inaccessible), the foreign-downscore value.
- **On receipt (`handlePlanEdit`):** guarded on **`ownedBuilt` alone** (NOT `ownedCorpusFresh`) — `planEntryWrite` reads only the per-source rescore indexes, which `releasePriorCorpus` spares across a `syncConfig` gap, so `plan: null` is reported only in the genuine pre-first-sync `ownedBuilt === null` window. Otherwise `planEntryWrite({ mode, clicked, typed, sources: ownedBuilt, trashScore })` and reply `editPlan`.

#### `editPlan` (entry-edit planner reply)
`{ type: 'editPlan', requestId, plan }` — reply to `planEdit`. `requestId` echoes for matching. `plan` is `{ blockedReason, primary, deletes, upserts, notes }` (the `planEntryWrite` shape) or **`null`** when `ownedBuilt` was absent. Main caches the structural plan for the open panel (preview / Save-gate / "already exists" note read it synchronously) and re-fetches on entry-text / mode / seed changes; a save consumes a fresh plan's `deletes`/`upserts`/`primary` directly.

#### `editEntry` (My Edits in-place write-set)
`{ type: 'editEntry', editId, writes }` — **mutate the worker's owned corpus in place for one My Edits gesture**, in O(affected norms), so a My Edits change no longer forces a full `syncConfig` rebuild. The worker also **writes the My Edits IDB itself** (main holds no `rawEntries`-to-serialize beyond the seed and skips its own write).
- `editId` — monotonic per client; echoed on the `editAck` reply for ack-matching. Edits apply in FIFO order.
- `writes` — the **resolved write-set** main's planner produced (`engine/edit-plan.js`), applied verbatim — the worker never re-plans, so one gesture (a plain edit, a rename, a rename-plus-downscore, a create, a create-plus-keep-copy) ships its whole set of writes at once. `applyEditsWriteSet` (shared by main and the worker, so both stay byte-identical) applies it:
  - `deletes` — `[{ norm, display }]`, entries to remove, matched by `(norm, displayOf)`.
  - `upserts` — `[{ norm, display, score, comment }]`, entries to add-or-update, matched by `(norm, displayOf)`. `display` is `null` for a bare wildcard (a downscore trash override or a keep-bare copy), else the verbatim entry text (a typed entry or a keep-rich copy).
  - `primary` — `{ norm, display }`, the entry the panel re-anchors to (the renamed/created entry, never a side-effect write).
- **On receipt:** **bump `latestSyncToken` at the top** — an older in-flight `syncConfig` build (started before this edit, reading pre-edit `rawEntries`) then discards via its commit guard rather than overwriting the edit with stale data. Then: if there's no resident data at all (`!editsWordlist()`/`!ownedBuilt`, i.e. before the first `syncConfig`), reply a no-op `editAck` (so the bridge's await resolves). Otherwise — **first `ensureOwnedCorpus()`: rebuild the merged/scoped corpus from `ownedBuilt` if a `syncConfig`'s async-rebuild gap freed it** (`releasePriorCorpus` nulls `ownedMerged`/`ownedCorpus` but spares `ownedBuilt`; the top-of-handler token bump makes the superseded in-flight build discard, so the edit isn't lost to the gap). Then:
  1. **Apply the write-set to the My Edits source's `rawEntries`** (the `type: 'edits'` source in `ownedBuilt`) via the shared `applyEditsWriteSet` — the same function main runs, so the two threads' My Edits never drift. Invalidate that source's rescored caches.
  2. **Affected norms** = the dedup of every norm across `writes.deletes` + `writes.upserts` — one or two for a plain edit/rename, more when a downscore or keep copy adds a side write.
  3. **Splice `ownedMerged`** per affected norm (`spliceOwnedCorpus`): recompute the bucket via the **rawScore-dropping** `computeMergedBucket(norm, ownedBuilt)` (a full merge drops `rawScore`, so the splice must too), then splice `entries`/`byKey`/`byNorm` and shift `sourceCounts` by the winner delta — **counted per merged row, not per distinct winning source** (a multi-variant norm one source wins several times contributes one merged entry *per variant*, so the decrement iterates the old rows symmetrically with the per-row `winners` increment; a `Set` would drift `sourceCounts` from a rebuild's by the duplicate-winner count). When an affected norm's `(norm, display)` row set is unchanged — a score/comment edit, or a winner flip keeping the same spellings — `spliceOwnedCorpus` reconciles the resolved fields onto the **existing** row objects in place instead of swapping in fresh ones, preserving the identities the prefix cache's tiles hold by reference.
  4. **When scoped to My Edits** (`ownedScope === editsDbKey`, so `ownedCorpus !== ownedMerged`), splice `ownedCorpus` too — a single-source recompute (`recomputeScopedBucket`) that **ignores `enabled`** and **carries `rawScore`** (a scoped corpus keeps `rawScore` for the rescore-preview arrow). For MERGED scope `ownedCorpus === ownedMerged`, already spliced.
  5. **When any affected norm reshaped its variant set** — a *replacing* splice swaps row objects and shifts later indices — **restamp every entry's `_i`**; the replacing splice's `purgeCacheForCorpus` also drops the prefix tiles that held the old objects by reference. A run of pure in-place reconciles skips both, so the next run reuses the cached tool output (e.g. Umiaq's tuple search) instead of re-running the stack. This same `replaced` signal rides the `editAck` (below): a `false` (set-preserving) ack lets main **reproject** the displayed result — the join stays valid, so the view re-derives with the new scores — rather than re-running.
  6. **Set `ownedCorpusFresh = true`** — the in-place mutation leaves the owned corpus coherent, so a subsequent run/`fetchRows` serves fresh rich rows with no resync.
  7. **Recompute the per-config summaries** — bump `ownedConfigVersion`, recompute `ownedAllSourcesAxis`, gather fresh `sourceCounts`/`mergedCount` — since `editEntry` skips the `syncConfig` that would otherwise refresh them; carry them on the ack.
  8. **Post the `editAck` first, then `await` the IDB write** (`idbPut('data_' + edits.dbKey, serializeEntries(sortedEntries(edits.rawEntries)))` — byte-identical to main's old `persistEdits` write), so ack consumption isn't delayed by disk I/O. **Then bump `latestSyncToken` again** — a `syncConfig` that read the pre-write IDB text (started between the ack and the write landing) discards too.

#### `editAck` (My Edits edit/add reply)
`{ type: 'editAck', editId, replaced, axis, counts }` — reply to `editEntry`. `editId` echoes for matching.
- `replaced` — `true` when any affected norm reshaped its variant set (step 5), `false` for a pure in-place reconcile (score/comment, or a same-spelling winner flip). A `false` ack is **set-preserving**, so `refreshAfterEdit` **reprojects** the displayed result instead of re-running: the corpus was spliced in place, so the retained join stays valid and a reproject re-derives the view (new scores, re-sort if score-sorted, re-filter) on **any tier, mid-stream or settled**, with no re-join. A `true` ack (structural) shifts the join, so it re-runs. Absent on a no-op ack.
- `axis` — the refreshed all-sources histogram layout (`{ mode, slots, min, max }`), same shape/role as `selfReady`'s `axis`.
- `counts` — `{ sourceCounts: [{ sourceId, count }], sourceTotals: [{ sourceId, total }], mergedCount, mergedWidthBound, version }` — the refreshed per-config summaries (`sourceTotals` is the per-source total, distinct from the merge-winner `sourceCounts`; `mergedWidthBound` keeps the column-width floor current when an edit changes the merge; see `selfReady`).
- **On receipt:** `actions.js`'s `applyConfigAck` consumes it: `setShippedAllSourcesAxis(axis, counts?.version)` + `setShippedConfigCounts(sourceCounts, sourceTotals, mergedCount, mergedWidthBound, version)` (version-guarded, mirroring `selfReady`'s consumption), then `refreshDerivedDisplays()` to repaint the X-of-Y meta + scoring legend with the fresh shipped values — so a per-entry edit needs no resync to keep those summaries current. The edited row itself updates instantly via the optimistic `applyEditsChange` path; the ack lands a few ms later to settle the steady state.

#### `deleteEntry` (My Edits in-place delete)
`{ type: 'deleteEntry', editId, norm, display }` — **remove one My Edits entry in place from the worker's owned corpus**, the removal-only sibling of `editEntry`. Runs the *same* O(affected-norms) owned-corpus update for the deleted norm, splices **only** the owned corpus, and writes the My Edits IDB itself.
- `editId` — monotonic per client (shares `editEntry`'s id counter); echoed on the `editAck` reply. Applies in FIFO order.
- `norm` / `display` — the `(norm, display)` to remove. The worker **re-derives the rawEntries index itself** (`findIndex(e => e.norm === norm && displayOf(e) === display)`) against its **own** copy of the source's `rawEntries` — it does not accept a caller-supplied array index, since the worker owns its own rawEntries order.
- **On receipt:** bump `latestSyncToken` (same edit-race harden as `editEntry`, at the top and again after the IDB write). If there's no resident data (no edits wordlist / `!ownedBuilt`), reply a no-op `editAck`; otherwise `ensureOwnedCorpus()` first (rebuild from `ownedBuilt` if a `syncConfig` gap freed the corpus, as `editEntry`). If the entry isn't found (already gone), reply a no-op `editAck`. Otherwise splice the record out of `rawEntries`, invalidate its rescored caches, then run the **shared owned-edit tail** (`applyOwnedEdit`): affected norms = `[norm]`; recompute that norm's merged bucket via `computeMergedBucket` (now without the deleted entry — it may keep other variants/lower-priority sources, or become empty → `byNorm.delete`) and splice `ownedMerged` (and the scoped `ownedCorpus` when scoped to My Edits); restamp `_i` and purge that corpus's prefix tiles **only when a norm reshaped its variant set** (a winner handoff that keeps the same spelling reconciles in place and keeps the tiles); recompute the per-config summaries; set `ownedCorpusFresh = true`. Reply `editAck`, **then `await` the IDB write**.

#### `editAck` (delete)
A `deleteEntry` replies with the **same `editAck` shape** as `editEntry` — `editId` echoes; `axis`/`counts` carry the refreshed summaries. `applyConfigAck` consumes the axis/counts identically. (A delete is always structural, so its `replaced` is unused — the delete path re-runs rather than reprojecting.)

**Undo needs no new command.** Both delete-undo and edit/create-undo are just another `editEntry` write-set: `deleteFromEdits`'s undo re-adds the record via `sendEditEntry({ upserts: [record], primary })`, and a multi-write gesture's undo ships the **inverse** write-set `applyEditsWriteSet` returned at save time (re-add deleted originals; delete added entries; restore changed values). Because the corpus **sorts** everywhere it's built or serialized and `getRescoredByNorm` is a map, a re-added record's position in `rawEntries` (a plain `push`) is irrelevant — the post-undo corpus is byte-identical to the pre-edit corpus, including for a multi-variant norm.

#### `mergeDisk` (My Edits inbound disk merge)
`{ type: 'mergeDisk', requestId, fileText, conflictChoice? }` — **run the My Edits 3-way disk merge on the worker.** When a watched My Edits file changes underneath the sync, `disk-sync.js`'s `reconcile()` (main) reads the file and hands its text to the worker, which holds both the My Edits corpus and the 3-way-merge **baseline** (the common ancestor). Main keeps the file-handle I/O, the watch loop, and the conflict dialog; the *merge itself* — and ownership of the `sync_worker_<editsKey>` baseline record — lives on the worker. `requestId` rides its own request-id lane (independent of the run's `runId`), echoed on the `mergeResult` reply; a client-side timeout resolves `null` so `reconcile()` leaves the file alone rather than wedging the sync loop.
- `fileText` — the raw text last read from the synced file (the **file side** of the 3-way merge), or whatever `reconcile()` read; the worker `parseWordlist`s it.
- `conflictChoice` — `'file' | 'device' | undefined`. **Undefined** is the first (phase-1) call: report conflicts, apply nothing. **Defined** is the phase-2 call after main's dialog resolves: re-merge and apply with the choice (`'file'` swaps each conflicting norm to the file side — `if (c.file) resolved.set(c.norm, c.file); else resolved.delete(c.norm)`; `'device'` keeps the device default already in `resolved`).
- **On receipt (`handleMergeDisk`):** **bump `latestSyncToken` at the top** (the same edit-race harden as `editEntry` — an older in-flight `syncConfig` build then discards via its commit guard rather than overwriting the reconciled corpus with stale data). If there's no resident data (`!ownedCorpusReady`, now ‘`ownedBuilt` present’ — true only before the first `syncConfig`), reply a no-op `mergeResult` (`mergedText: null, corpusChanged: false, conflicts: []`) and main leaves the file alone. **Mid-`syncConfig`-gap the merged/scoped corpus may be freed, but `ownedBuilt` is not — so the merge proceeds and rebuilds from it (below) rather than no-opping and dropping a pending divergence (the device-side optimistic edit main has already applied).** Otherwise read the worker-owned baseline (`idbGet('sync_worker_' + editsKey)`, `?? ''` for an absent record), `threeWayMergeEdits(parseWordlist(baseline), parseWordlist(fileText), edits.rawEntries)`, then:
  - **Phase 1 (`conflicts.length && conflictChoice === undefined`):** reply `mergeResult` with the `conflicts` and **apply nothing** (no corpus mutation, no IDB write). Main raises the dialog and re-posts with the choice. Re-running statelessly in phase 2 is sound because baseline/fileText/corpus are stable while main's modal dialog is open — the worker holds **no** pending merge state between the two calls.
  - **Phase 2 / no conflicts:** apply `conflictChoice === 'file'` to `resolved` (as above), then `merged = [...resolved.values()]`, `outText = serializeEntries(sortedEntries(merged))`, `corpusChanged = !sameEditsEntries(merged, edits.rawEntries)`. **If `corpusChanged`:** set `edits.rawEntries = merged` and rebuild the owned corpus **WHOLESALE** from `ownedBuilt` (a reconcile may rewrite arbitrarily many norms — a per-norm splice would silently desync; the wholesale rebuild mirrors the `syncConfig` commit body, synchronous off the resident `ownedBuilt`), then persist the corpus (`idbPut('data_' + editsKey, outText)` — exactly what an edit's `persistEditsCorpus` writes). **If unchanged but a gap freed the corpus, `ensureOwnedCorpus()` rebuilds it anyway** — the top-of-handler token bump discarded the in-flight build, so without this the worker would be left corpus-less. **Always** advance + persist the baseline (`idbPut('sync_worker_' + editsKey, { baseline: outText })` — the baseline advances to the synced state every reconcile, conflict or not). **Bump `latestSyncToken` again** after the IDB writes (the second half of the edit-race harden). Reply `mergeResult` with `mergedText: outText, corpusChanged, conflicts: []`, plus `rawEntries`/`axis`/`counts` when `corpusChanged`.

#### `mergeResult` (My Edits inbound disk merge reply)
`{ type: 'mergeResult', requestId, mergedText, corpusChanged, conflicts, rawEntries?, axis?, counts? }` — reply to `mergeDisk`. `requestId` echoes for matching.
- `mergedText` — the serialized merged text (`null` on a not-ready no-op, or on a phase-1 conflict report). `reconcile()` writes it to the file via `_ownWrite` when it differs from `fileText`.
- `corpusChanged` — `true` when the merge changed the corpus (so main calls `applyReconciledSeed(edits, rawEntries)` to seed its resident My Edits copy for the editor/legend — **main does NOT write the `data_` IDB; the worker already did**).
- `conflicts` — the phase-1 conflict list `[{ norm, device, file }]` (non-empty only on the phase-1 reply); `[]` otherwise. When non-empty, `reconcile()` raises the dialog and re-posts `mergeDisk` with the user's `conflictChoice`.
- `rawEntries` — the merged My Edits entries (present only when `corpusChanged`), so `applyReconciledSeed` re-seeds main's resident copy. `axis`/`counts` — the refreshed all-sources axis + per-config summaries (present only when `corpusChanged`), same shape/role as the `editAck`'s.

#### `flushEdits` (My Edits outbound disk flush)
`{ type: 'flushEdits', requestId }` — **serialize the My Edits corpus for the synced file and advance the baseline.** When a local My Edits edit lands, `disk-sync.js`'s `_flushWrite()` (main, debounced) asks the worker to serialize its current corpus; the worker owns the same `sync_worker_<editsKey>` baseline it owns for `mergeDisk`, so the outbound direction advances it too. `requestId` rides its own lane; a timeout resolves `null` so the flush leaves the file alone.
- **On receipt (`handleFlushEdits`):** if the My Edits source isn't present, reply a no-op `flushResult` (`text: null, changed: false`). Otherwise `text = serializeEntries(sortedEntries(edits.rawEntries))`, read the baseline (`idbGet('sync_worker_' + editsKey)`, `?? ''` — an absent record means the connect-seeded empty baseline, so a first flush against an empty ancestor still dedups). **If `text === baseline`** reply `flushResult { text, changed: false }` and write nothing (the dedup that suppresses a redundant file write). Else `idbPut('sync_worker_' + editsKey, { baseline: text })` and reply `flushResult { text, changed: true }`. (No corpus rebuild and no `data_` write here — the local edit that triggered the flush already persisted the corpus via the `editEntry`/`deleteEntry` path; `flushEdits` only serializes + advances the baseline.)

#### `flushResult` (My Edits outbound disk flush reply)
`{ type: 'flushResult', requestId, text, changed }` — reply to `flushEdits`. `requestId` echoes for matching. `changed` is `true` when the serialized corpus differs from the baseline (so `_flushWrite` mirrors `text` to the file via `_ownWrite`); `false` on the dedup short-circuit (or the not-ready no-op), in which case `_flushWrite` writes nothing.

#### `applyFetched` (fetch/import content-diff)
`{ type: 'applyFetched', requestId, sourceId, text, background }` — **apply a re-fetched/re-imported source's new text to the owned corpus in place**, scaling the cost with the *diff* rather than the wordlist, so a periodic update (a maintainer adds some entries and retunes some scores; the bulk is untouched) leaves the running pipeline, scroll, and search undisturbed. Replaces the full `resyncWorkerConfig` (which re-read **every** source from IDB and re-merged the lot) for a pure content update of an already-populated, config-unchanged source; `applyWordlistText` posts this **instead of** bumping `cacheVersion$`.
- `background` — `true` for an unattended background auto-update (`checkForUpdates` → `viaToast`). Gates **refresh-on-consent**: a background *structural* update to a **flat** result replies `repatch` (main re-derives it in place, no chip), and to a **combination-tier** result pins it + replies `stale` (main raises the refresh chip) — either way not the bare re-run a user-initiated fetch triggers (below). Absent/`false` for a user-initiated fetch/import, which re-runs as before.
- `requestId` — monotonic per client, in its own request-id lane; echoed on the `fetchApplied` reply; a client-side timeout (generous — the worker parses the whole text synchronously) resolves `null` so `applyWordlistText` falls back to a full resync rather than wedging.
- `sourceId` — the changed wordlist's `dbKey`. The worker finds it in `ownedBuilt`; its resident store (columnar `cols` for a regular source, `rawEntries` for My Edits) is the **previous** version the new text is diffed against (the diff carries no old version — the worker already holds it).
- `text` — the **raw new text** (the bytes main fetched/read), shipped whole as a structured-clone string. Main also **owns the `data_` IDB write** of this text (it preserves the original formatting for Download original) — the worker does **not** write IDB here (unlike `editEntry`, where the worker is the sole writer); it only updates its in-memory corpus.
- **On receipt (`handleApplyFetched`, SYNCHRONOUS):** bump `latestSyncToken` at the top (edit-race harden — an older in-flight `syncConfig` build reading pre-fetch IDB text discards via its commit guard). If `ownedBuilt` has no such source, or no `ownedMerged`/`ownedCorpus` (no build yet, or a brand-new source the last `syncConfig` didn't carry), reply `fetchApplied { applied: false }` — main falls back to a full `resyncWorkerConfig`. Otherwise materialize the old raw entries through `sourceAccessor(source).collectRaw()` (transient views over the current store) **before** replacing it, `parseWordlist(text)`, then rebuild the store — `source.cols = columnsFromEntries(newEntries, rescoreRules)` for a regular source, `source.rawEntries = newEntries` for My Edits — and invalidate its rescored caches. The old views are read by the diff while the new store is built. Then:
  - **`wasEmpty` (`oldEntries.length === 0`)** → **`rebuildOwnedFromBuilt(ownedScope)`**, reply `wasEmpty: true` + `newCount` + `diffId: null`, and **skip the diff entirely**: a first population shows only a "Loaded N" toast, which reads no `affectedNorms` and no samples, so the O(n) diff scan over ~600k new entries would be pure waste.
  - Otherwise compute the diff via `diffForFetch`, a thin lean-mapping wrapper over the **exported, unit-tested** `diffWordlistEntries` ([`corpus.js`](../site/src/engine/corpus.js)) — one keyed pass (entry identity `mergeKey(norm,display)`) yielding `affectedNorms` (every changed norm **including comment-only changes** — the comment is shown, so the bucket must recompute), the **full** sorted `added`/`deleted`/`rescored` arrays, and counts (= lengths; rescored = SCORE changes only, the dialog's notion). `diffWordlistEntries` is the single core: the dialog and the unit test exercise the same function the worker runs.
  - **The ADD+DELETE count exceeds `ADD_DELETE_REBUILD_CAP`** (256) → **`rebuildOwnedFromBuilt(ownedScope)`** — a wholesale merge rebuild off the resident `ownedBuilt` (still cheaper than `syncConfig`: the *other* sources aren't re-read from IDB or re-parsed).
  - **Else** → **`applyOwnedEdit(source, affectedNorms)`** — the *same* in-place per-norm splice tail `editEntry`/`deleteEntry` use, batched over the affected norms: re-merge each via `computeMergedBucket` over **all** sources, splice `ownedMerged` (and the scoped `ownedCorpus` when scoped to this source), restamp `_i` and purge that corpus's prefix tiles **only when a norm reshaped its variant set** (score-only changes reconcile in place and keep the tiles), set `ownedCorpusFresh = true`, recompute the per-config summaries.
  - **Refresh-on-consent fork (background structural only).** **Before** the splice, if `background` and a **flat** result is displayed in a scope this update affects (`MERGED`, or scoped to `sourceId`), snapshot `ownedCorpus.entries.slice()`. After applying, when the change was **structural** (`rebuild`, or `applyOwnedEdit` returned `replaced`), `refreshFork` splits by tier: a **flat** displayed result sets `repatch: true` and binds the snapshot to it (`pinnedCorpus`) — the pin here only bridges the gap until main's `repatch` re-derives it (a `fetchRows` against the shifted positions in that window would silently tear); a **combination-tier** result (grouped/transform, which hold entry-object refs and freeze on their own) sets `stale: true`. A pure rescore is set-preserving (`replaced: false`) → neither flag — main reprojects it live.
  - **The rebuild threshold counts ADDS + DELETES, never rescores, and is absolute.** A rescore splices in place — an equal-length array overwrite, no tail shift, O(1) — so any number of rescores stays on the splice path; only adds/deletes shift the merged array (O(n) each), making the batch O(structural × n). The cap is absolute, not a fraction of the list: a fraction would permit O(n²) work and freeze on large lists. The `mode` field on the reply (`'splice' | 'rebuild'`) records which path ran.
  - **Retain + window the diff.** When the diff has any change, mint a monotonic `diffId`, store the **full** lean `{ added, deleted, rescored }` in `retainedDiffs` (below), and ship `diffId` + the inline first window (`.slice(0, DIFF_SHIP_CAP)`, 500/section) + the true counts. The update dialog windows past the inline samples via `fetchDiffRows`, so a full-replace re-import never re-materializes its ~600k rows on main. A no-change diff (a reformatted-but-identical re-import) mints no `diffId` (it would have no owner to free it — main shows the "up to date" alert).
  - The handler stays **synchronous** (no IDB write to await) so the splice fully lands before the run main posts next — an `await` here would let that run interleave against the un-spliced corpus and ship stale rows. Reply `fetchApplied` with the diff payload (below).

#### `fetchApplied` (fetch/import content-diff reply)
`{ type: 'fetchApplied', requestId, applied, mode?, stale?, repatch?, diffId?, axis?, counts?, rescoreInputs?, wasEmpty?, oldCount?, newCount?, added?, deleted?, rescored?, addedCount?, deletedCount?, rescoredCount? }` — reply to `applyFetched`. `requestId` echoes for matching.
- `applied` — `true` when the worker applied the diff (splice or wholesale rebuild); `false` when it had no resident build for the source. On `false`, `applyWordlistText` calls `resyncWorkerConfig()` (which reads the just-written IDB text) and reports the loaded count from its own transient parse.
- `stale` — `true` when a **background structural** update pinned a **combination-tier** displayed result (refresh-on-consent, above): main defers the re-run and raises the refresh chip. Mutually exclusive with `repatch`; absent/`false` otherwise.
- `repatch` — `true` when a **background structural** update hit a **flat** displayed result: main re-derives it in place (`repatchMergedScroller` → `repatch` message), no chip. Mutually exclusive with `stale`; absent/`false` otherwise — a user-initiated update, or a set-preserving background rescore, re-runs/reprojects as before.
- `mode` — `'splice' | 'rebuild'` when `applied` (which path ran), absent otherwise. Diagnostic; the client stashes it for the threshold-path test (`lastFetchMode`).
- `diffId` — the retained-diff key (monotonic) when the diff has a viewable change, else `null` (`wasEmpty`, no resident build, or a no-change re-import). Main owns its lifetime: the update dialog (or, for an auto-update, the toast) frees it via `freeDiff` when it ends; the update dialog windows the full diff via `fetchDiffRows(diffId, …)`. `null` ⇒ nothing retained, nothing to free.
- `wasEmpty` — `oldEntries.length === 0`; main drives the toast off it (a first population shows a loaded count, an actual update shows the diff). The **source of truth** now that main holds no old entries.
- `oldCount` / `newCount` — the source's entry totals before/after (the update-summary title's `X → Y`).
- `added` / `deleted` — the **inline first window** (≤`DIFF_SHIP_CAP`) of sorted `{ norm, display, score, comment }`; `rescored` — the first window of `{ entry, oldScore, score }`. The dialog seeds its scroller cache from these and fetches the rest (`fetchDiffRows`) past the window. Absent for `wasEmpty`/no-build replies.
- `addedCount` / `deletedCount` / `rescoredCount` — the **true** totals (the dialog's headers + pills read these, never the inline array lengths).
- `rescoreInputs` — the refreshed per-source distinct `(score, length)` pairs for the bake gate (the changed source's content changed; see `selfReady`). Consumed by `setShippedRescoreInputs` (update-when-present, not version-gated).
- `axis` / `counts` — the refreshed all-sources axis + per-config summaries (`{ sourceCounts, sourceTotals, mergedCount, mergedWidthBound, version }`), same shape/role as `editAck`'s. **On receipt:** `applyConfigAck` consumes them exactly as it does an `editAck` (version-guarded `setShippedAllSourcesAxis` + `setShippedConfigCounts` → `configSummary$` repaints), so a content update needs no resync to keep the X-of-Y meta + badge axis + scoring legend current.

#### `fetchDiffRows` (windowed update-diff row fetch)
`{ type: 'fetchDiffRows', requestId, diffId, section, start, end }` — **request a window `[start, end)` of one section of a retained diff.** The update-summary dialog windows the added/deleted/rescored lists (each up to the source's full size) the way the flat scroller windows results, so the dialog renders the *complete* diff without main holding more than the visible window + per-section caches.
- `diffId` — which retained diff (from the `fetchApplied` reply). `section` ∈ `'added' | 'deleted' | 'rescored'`.
- `start` / `end` — half-open window into that section's sorted array; `start` floored at 0, `end` capped at the section length (`| 0` coercion).
- **On receipt (`handleFetchDiffRows`):** dropped silently (no reply) unless `retainedDiffs` still holds `diffId` (the analogue of `fetchResultFresh` — a freed/respawn-lost diff just leaves the dialog on its inline window). Otherwise post `diffRows` with the clamped window.

#### `diffRows` (windowed update-diff row fetch reply)
`{ type: 'diffRows', requestId, diffId, section, start, rows }` — reply to `fetchDiffRows`. `requestId`/`diffId`/`section` echo for matching; `start` is the floored window start served; `rows` is the section slice — lean `{ norm, display, score, comment }` (`added`/`deleted`) or `{ entry, oldScore, score }` (`rescored`), the **same** shape as the inline seed so the scroller fills its cache without a decode step. The client renders them directly — no `state.sources` lookup, since a diff row carries no source identity.

#### `freeDiff` (release a retained diff)
`{ type: 'freeDiff', diffId }` — fire-and-forget, **no reply**: `retainedDiffs.delete(diffId)`. Main posts it when the diff's owning affordance ends — the update dialog on close, an un-clicked auto-update toast on timer expiry, or a late `fetchApplied` whose owner main already abandoned (the `sendApplyFetched` timeout path keeps its listener alive precisely to free that orphan). Deleting an absent key is a no-op, so a duplicate/stale free is harmless. This is the **only** way `retainedDiffs` shrinks besides worker respawn (which drops it whole) — runs and `syncConfig` never touch it.

#### `syncConfig` (self-build)
`{ type: 'syncConfig', configId, scope, sources }` — hand the worker the config it needs to **independently load+parse+rescore+merge** its own corpus. This is how the worker gets its corpus — it never receives the corpus as bulk data.
- `configId` — monotonic per client; echoed verbatim on the `selfReady` reply so each in-flight `syncConfig` awaits **its own** reply (correlation, below). Multiple syncs are routinely concurrent — the completeness hook fires one and a post-write re-sync fires another before either build settles.
- `sources` — an array in **merge-priority order** (`sources[0]` highest). Each: `{ sourceId, enabled, type, rescoreRules }`, where `sourceId` is the wordlist's `dbKey`, `type` is `'edits'` for My Edits (else `null` — carried so the `editEntry` handler can find the My Edits source in `ownedBuilt`), and `rescoreRules` are stripped to the **four editor fields** (`input`, `length`, `output`, `note`) — the worker recompiles them. No display name rides along: the worker keys every source by `dbKey` and never needs the human label.
- `scope` — the **active scope** at sync time (`MERGED_ID` or the scoped wordlist's `dbKey`). It determines which corpus the worker builds into `ownedCorpus`; the merged build (`ownedMerged`) is built unconditionally and feeds the config summaries regardless of `scope`.
- **Sent:** from production boot (`init()`, after `propagateDefaults` but **before** the main-thread wordlist parse, so the worker's build overlaps it); **re-sent on every config change** (`resyncWorkerConfig`); and by the test bridge (`syncWorkerConfig`). Because the parse no longer precedes it, the boot `selfReady` may land **before or after** the first paint's run is registered; `init()` awaits the captured `syncConfig` promise alongside `firstPaint` either way (see below).
  - **The re-send on config changes (completeness).** A config change must always re-sync, or `ownedCorpus` goes stale-but-fresh and the worker enriches rows from stale data — silent corruption of every rendered row. Trigger sites: (1) the **completeness hook** — `resyncWorkerConfig()` in `rendering.js`'s render-effect cache branch, firing on every `cacheVersion$` bump (rules/enable/order/bake); (2) **post-IDB-write re-syncs** — `resyncWorkerConfig()` after the `Storage.writeWordlist` in the `ingestFile` My-Edits-combine branch and the non-edits `bakeRescoring` write, reading **fresh** IDB text. A per-entry My Edits edit/delete instead refreshes via the `editEntry`/`deleteEntry` command + `editAck`, and a re-fetch/re-import of a populated source via the `applyFetched` content-diff (above) — both in place, neither bumping `cacheVersion$` nor resyncing (the fetch path falls back to `resyncWorkerConfig` only when the source's config *also* changed — an enable flip or an auto-seeded rule — or the worker has no build for it yet). A **first population is no longer a separate fall-back trigger**: the worker handles empty→full via its own rebuild path inside `applyFetched` and reports `wasEmpty` on the ack, so main posts `applyFetched` for it too (unless an enable flip / rule seed makes it config-changed). A completeness-hook resync that also does a post-write re-sync fires *prematurely* (before the write lands → stale text), made harmless by supersession (below).
- **On receipt:** worker stores `selfConfig = data`, captures a fresh **`latestSyncToken`** (supersession key, below), clears `ownedCorpusFresh` synchronously (so a run dispatched in the rebuild gap defers rather than running against the stale corpus), and asynchronously builds the all-sources wordlists from IDB (retained as `ownedBuilt`). When the build settles **and is still the latest** (token guard): bump `ownedConfigVersion`, compute `ownedAllSourcesAxis`, eager-build `ownedMerged` (the enabled-only deduped merge — feeds the config summaries), and `setOwnedCorpus` for the active scope (`ownedMerged` when merged, else `buildScopeCorpus(built, scope)`). A superseded build discards its result (`ownedCorpusFresh` stays `false`). A build **failure** in the latest sync nulls `ownedBuilt`/`ownedMerged`/`ownedCorpus`. Either way the `.finally` replies `selfReady` (echoing `configId`) once the build settles — even when superseded or failed (so the bridge's `await` always resolves).
- **Supersession (`latestSyncToken`).** A single config change can fire two re-syncs — the premature completeness hook (stale text) and the post-write re-sync (fresh text). Each `syncConfig` captures `const myToken = ++latestSyncToken` synchronously at handler start, and the build's `.then`/`.catch` guard their commit with `if (myToken !== latestSyncToken) return`. Only the **latest** sync's build commits; a stale build discards. Because the post-write re-sync is always posted after the premature hook one (FIFO), the committed build always read fresh IDB text. (The same token guard is what makes an in-flight stale build lose to a concurrent `editEntry`, which also bumps the token.)
- **Reply correlation (`configId`) — load-bearing.** `selfReady` is consumed on the **persistent** worker listener (`handleSelfReady`), never a per-call listener. `configId` keys the `_configWaiters` map so each `syncWorkerConfig`'s returned promise resolves on **its own** reply; the freshness/axis/counts processing runs for **every** `selfReady` that arrives. A superseded build still posts a `selfReady` carrying the *currently-committed* `version`, but `setShippedAllSourcesAxis`/`setShippedConfigCounts` ignore a repeat version, so its late reply is a no-op rather than a stale overwrite. (The prior design used per-call listeners torn down on a 5 s timer; a build slower than the timer orphaned its `selfReady` — freshness, axis, and counts all dropped — leaving the worker fully built but the UI parked on an empty result with no error. Durable consumption is the fix: a slow build self-heals whenever it lands, however long it takes.)
- **The all-sources axis (`axis` + `version`).** Per-config (rides this handshake, **never** the per-run `result`), the worker computes `getHistogramLayout(<union of every configured source's rescored scores>, 'all')` — the union over **all** sources (enabled **and** disabled, **not** deduped). This is the **scope-stable badge-gradient axis** main's `scoreColor` reads (`allSourcesHistogramLayout()`), equal to the merged scope's histogram layout. It must be computed **only** here, never per run or per scope — a per-run recompute would silently shift badge colors on every keystroke. The worker invalidates its histogram-layout cache (key `'all'`) before computing, so a later `syncConfig` with changed scores doesn't return a stale axis.

#### `dumpCorpus` (test-only)
`{ type: 'dumpCorpus', scope }` — build a corpus from the synced `selfConfig` and post it back for fixture comparison.
- `scope` — `MERGED_ID` for the merged build (enabled sources only), or a `sourceId` for a single-source scoped build (regardless of `enabled`).
- **On receipt (`corpusForScope`):** `MERGED_ID` dumps the held `ownedMerged` (no rebuild). A scope equal to the active owned scope (`ownedScope === scope && ownedCorpusFresh`) dumps the live, in-place-spliced `ownedCorpus` directly — so an `editEntry` splice is observable. Any other scope builds on demand from IDB. Replies `corpusDump`. Requires a prior `syncConfig`.

#### `queryEntry` (test-only)
`{ type: 'queryEntry', requestId, scope, norm, display }` — a single-entry `byKey`/`byNorm` lookup against a scope's owned corpus. Used by the test-api `getMergedEntry`.
- `requestId` — monotonic per client; echoed on the `entry` reply for matching; a client-side timeout resolves `null`.
- `scope` / `norm` / `display` — the lookup target. `display !== undefined` → `corpus.byKey.get(mergeKey(norm, display))`, else `corpus.byNorm.get(norm)`.
- **On receipt:** resolve the scope's corpus (`corpusForScope`, building from IDB if it's not the live owned scope), look the entry up, and reply `entry` with the tuple `[norm, display, score, rawScore, comment, sourceId]` (or `null`).

#### `__testFailNextBuild` (test-only)
`{ type: '__testFailNextBuild' }` — forces the next `syncConfig` build to throw, so the suite exercises the build-failure `selfReady` (`built: false` → the client settles the deferred run errored, no-hang settle path 4). Sibling of `__testCrash`.

#### `__testPatchTool` (test-only)
`{ type: '__testPatchTool', tool, method, message }` — the suite breaks a tool to exercise the error path, but the worker has its own `TOOLS` realm a page-side patch can't reach, so it patches the worker's copy (`message == null` restores the original).

#### `__testCrash` (test-only)
`{ type: '__testCrash' }` — throws uncaught, firing the parent `Worker`'s `error` event (the real crash signal the client's recovery path keys on).

#### `__testYieldInterval` (test-only)
`{ type: '__testYieldInterval', intervalMs }` — `configureExecutorYield({ intervalMs })`, so the suite can shrink the executor's yield interval. A small test corpus finishes before the shipped ~30 ms yield and so streams a **single** `partial` (the post-loop flush); dropping the interval makes even a small flat scan cross many yield boundaries and stream **multiple** snapshots, so a test can exercise the incremental re-sort + scroll. The client wrapper is `setWorkerYieldIntervalForTest`; the streaming specs drop to 1 ms to force a multi-batch stream and restore 30 afterward.

### Worker → main

#### `pong`
`{ type: 'pong' }` — reply to `ping`.

#### `result` (all three tiers)
`{ type: 'result', runId, laneKind, atomCount, ranAgainstOwned, payload }` — **pipeline output.** Always carries `ranAgainstOwned: true` (the worker always runs against its own corpus; main keys export/rebind eligibility on it).
- `runId` — main **drops stale results** whose `runId` isn't the latest dispatched.
- `laneKind` — the **result-shape discriminator** that selects `payload`'s tier, one of `'single'` (a flat filter/transform result — one lane per row), `'set'` (a group cluster — equivalence-class lanes, trimmable, count varies per row), `'record'` (a tuple — fixed positional lanes, all-or-nothing). Orthogonal to `atomCount` (M = chain depth). Both the worker (tier selection) and the client (decode path) branch on it: `laneKind !== 'single'` rides the grouped path. The render `sortTier` and `streamPlan().tier` keep their own vocabulary (`flat`/`single`/`multi`/`group`/`tuple`) — `record` ⇔ the `tuple` tier, `set` ⇔ the `group` tier — because those enums additionally carry the atom axis and the streaming strategy.
- `atomCount` — atoms per row (the scroller also derives this from the stack alone, so row heights don't block on the result).
- The **atom encoding** — the shared unit of the transform/grouped tiers. An atom is a small tagged object, exactly one of:
  - `{ norm, display, score, rawScore, comment, sourceId, sourceIds, activeIds }` — a **corpus atom**, shipped rich/self-contained (the same field set `buildFlatRows` emits), so main decodes it with no resident corpus. `sourceId` is the winning source's `dbKey`, `sourceIds`/`activeIds` the presence/active contributor sets (see *Message encoding*); `rawScore` is `undefined` for an unrescored row.
  - `{ s: { norm, display, score } }` — a **synthetic** atom: a tool output that exists in no wordlist (`wlEntry.wordlist === null`). Inline and self-contained, **not** looked up by norm on receipt.
  - plus optional `h` (the atom's `highlights`, omitted when null) and `g` (its `glyph`, one of `'→' | '↔' | '⊃'`, omitted when null).
- `payload` — tiered:
  - **filter/search** (the common, laggy case): **no off-screen highlights, no per-row objects** beyond the inline first window, no transfer. `payload = { count, widthHints, stats, histogramCounts, histogramLayout, existsInScope, rebindQuery, rebindEntry, rebindExists, filtered, firstRows }`.
    - `count` is the survivor total — **the size main lays the scroller out from**. The worker owns the sorted survivor `indices` (into `ownedCorpus.entries`, **already sorted** by the run's `sort` axis/dir) and serves rich windows from them via `fetchRows`; main never receives the index list. `filtered` is `true` when the worker applied the score-range filter itself, in which case `count`/`widthHints`/`stats` describe the **filtered** survivor set (the windowed scroller fetches filtered positions directly); `false`/absent otherwise. `histogramCounts` is **always** the unfiltered distribution.
    - `widthHints = { maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }` — the one-pass column-width summary the scroller needs to size its grid tracks without scanning all rows. `maxRawDigits` is the rescore-preview arrow's raw-score column width, which main can't scan the full result for; main applies it only when the preview is active. The scroller takes the **max of these per-result hints and the per-config `mergedWidthBound` floor** (see `selfReady`), so a filter-only result — always a subset of the merge — renders at the stable floor width rather than resizing the columns to its own narrower set.
    - `firstRows` — the **first window's rich rows** (`buildFlatRows(0, min(FIRST_WINDOW, length))`), shipped inline with every flat result so main paints the above-the-fold rows instantly instead of flashing skeletons until a `fetchRows` round-trip lands. The scroller seeds its window cache from it.
    - **per-result stats summaries** (`stats` + `histogramCounts` any scope; `histogramLayout` scoped runs only): `stats: computeStatsRaw(scores)` (`{count,min,max,distinctScores}`). The order is load-bearing — `histogramCounts` is computed **first, over the unfiltered scores** (so out-of-range bars stay clickable); **then** a filtered run narrows `indices`/`scores`; **then** `stats` is computed **last, over the (now filtered) scores**. So `stats` describes the filtered set when `filtered`, the full set otherwise. `histogramCounts` buckets against a **scope-appropriate axis**: a merged run against `ownedAllSourcesAxis` (already on `selfReady`); a scoped run against `getHistogramLayout(ownedCorpus.entries, 'scoped:'+scope)`, shipped alongside as `histogramLayout` (merged ships `histogramLayout: null`). The client stashes the shipped layout in `data/derived.js`'s scope-keyed holder (`setShippedScopedLayout`), re-stamped on **every** flat result so a scope switch can't leave a previous scope's layout behind; `scopedHistogramLayout()` trusts it only while its scope-key still equals `state.selected?.dbKey`.
    - **per-result `existsInScope`**: a boolean for the run's `existsQuery`. `existsInScope = ownedCorpus.byNorm.has(toNorm(existsQuery))` (the active scope's norms) feeds the add-entry FAB seed (`newEntrySeedQuery`) — open blank when the query exists, pre-fill it when it doesn't. `null` when `existsQuery` is blank.
    - **per-result panel re-bind answer**: for the open entry panel's `rebindQuery`, the payload carries `rebindEntry` (a **rich row** `{ norm, display, score, rawScore, comment, sourceId }` or `null`) + `rebindExists` (boolean) + an echoed `rebindQuery`. The worker resolves them the same way the flat `findResultEntry`+`resultHasEntry` do — `rebindEntry = ownedCorpus.byKey.get(mergeKey(norm,display)) ?? ownedCorpus.byNorm.get(norm)` (a **full-corpus** lookup, so it re-anchors even to a range-filtered-out entry), `rebindExists = ownedCorpus.byNorm.has(norm)`. All `null` when no panel was open. Main rebuilds the rich `rebindEntry` into a `wlEntry` (`sourceId` → `state.sources`) and stashes the trio on the scroller; `findResultEntry`/`resultHasEntry` return the shipped answer when `ranAgainstOwned` and the stashed `_rebindQuery` matches the requested `(norm,display)`.
  - **transform** (windowed): `payload = { firstChains: [<chain>, …], chainCount, stats, histogramCounts, histogramLayout, widthHints, filtered, existsInScope, rebindQuery, rebindEntry, rebindExists }`. Fires when any row is *rich* — carries a glyph, spans more than one word, or holds a synthetic — i.e. the flat index encoding would be lossy. The transform result is **windowed like the flat tier** (a one-level list of chain rows): `firstChains` is the **first window** only (`sorted.slice(0, FIRST_WINDOW)`, each `{ atoms: [<atom>, …] }`); the worker retains the full sorted+filtered list as `lastTransformResult` and serves later windows via `fetchTransformRows` / the export result via `fetchAllTransformRows`. `chainCount` is the total surviving chain count — **the size main lays the scroller out from** (the shipped `firstChains` length is the window, not the count). The result-level summaries (`stats`, `histogramCounts` always unfiltered, `histogramLayout` scoped-only, `widthHints`, `filtered`) and the panel re-bind answer (`existsInScope`/`rebindQuery`/`rebindEntry`/`rebindExists`, resolved exactly as the flat tier's full-corpus lookup) are computed worker-side over **all** chains, since main holds only a window. `widthHints` extends the flat shape with `maxGlyphDisplayLen`, so main reconstructs the glyph-prefixed entry slot it can't measure worker-side. Structured-cloned.
  - **grouped** (`laneKind !== 'single'` — a `'set'` cluster or a `'record'` tuple, windowed): `payload = { groups: [<group window>], stats, histogramCounts, histogramLayout, groupWidthHints, chainCount, groupCount, filtered }`. The grouped result is **windowed at both levels** (mirroring the flat tier), so `groups` is the **first window** of group ROWS only — `sorted.slice(0, GROUP_ROW_WINDOW)`, *not* the whole list — and within each, the chains are windowed too. The worker retains the full sorted+filtered group list as `lastGroupedResult` and serves later windows via `fetchGroups`/`fetchGroupChains` (above).
    - each group in the window is `encodeGroup(g)` = `{ key, anchor, _minScore, _maxScore, _count, firstChains }`. `key` is the tool-derived group key. `anchor` is `null` or the rich atom encoding (never `h`/`g`) for the group's anchor entry. `_minScore`/`_maxScore`/`_count` are the precomputed group stats — `_count` is the group's **full** chain count (the Count badge and "+N more" arithmetic read it, **not** `firstChains.length`). `firstChains` is the first `GROUP_FIRST_WINDOW` chains (`{ atoms: [<atom>, …] }`), wide enough that a collapsed group row never needs a chain fetch to fill its slot.
    - the result-level summaries are computed worker-side over **all** groups (main holds only a window, so it can't): `stats` (`computeStatsRaw` over the survivor scores), `histogramCounts` (always the **unfiltered** distribution, so out-of-range bars stay clickable), `histogramLayout` (the scoped layout on a scoped run, `null` on merged), `groupWidthHints` (the column-width summary the scroller sizes from without scanning every group), `chainCount` (total surviving chains across all groups), `groupCount` (total group rows — **the size main lays the scroller out from**; the shipped `groups` length is the window, not the count), and `filtered` (`true` when the worker applied the score-range filter — `groups`/summaries then describe the filtered set; histogram stays unfiltered). Structured-cloned.
- **On receipt:** the client checks the `runId` is the latest dispatched (else drop). For the **flat tier** it returns `{ flat: true, count, widthHints, stats, histogramCounts, histogramLayout, existsInScope, rebindQuery, rebindEntry, rebindExists, filtered, ranAgainstOwned, firstRows, atomCount }` (the tier is carried by `flat: true`/`transform: true`/grouped-else, not by a result-shape flag on this object) — and the scroller stores the `count` + hints + shipped summaries, seeds its window cache from `firstRows`, and fetches off-screen windows via `fetchRows`. Like the transform/grouped tiers it holds **no resident row data**, only the window cache and the worker's summaries. The shipped `histogramLayout` is stashed in `data/derived.js`'s scoped-layout holder. For the **grouped tier** it decodes the inline first window of group rows and seeds the grouped scroller's window cache from it, then lays the scroller out from the shipped `groupCount` (not the window length) and fetches off-screen group-row windows via `fetchGroups`, a group's later chains via `fetchGroupChains` on "+N more", and the whole result via `fetchAllGroups` on export — the result-level `stats`/`histogramCounts`/`histogramLayout`/`groupWidthHints`/`chainCount`/`filtered` ride alongside so main needs no full group list. For the **transform tier** it decodes the inline `firstChains` window, seeds the scroller's window cache from it, lays the scroller out from `chainCount`, and fetches off-screen windows via `fetchTransformRows` (and the whole result via `fetchAllTransformRows` on export) — mirroring the flat tier. Decoding a group or chain walks each atom — a rich corpus atom → a `wlEntry` rebuilt from its inline fields (`sourceId` resolved via a `state.sources` Map built once per decode pass), `{s}` → a freshly built synthetic `wlEntry` (`{ norm, display, score, comment: '', wordlist: null }`, **not** norm-resolved) — reattaching `h`/`g` and the group `key`/`anchor`/stats. Either result settles the run's pending promise; `runPipeline` decrements the in-flight counter that gates `pipelineIdle()`. The score-range view filter then runs on main as a **no-op** when the worker already filtered (`_workerFiltered`); a score-range change **reprojects** (the worker re-derives the view over the retained join and ships a `reprojected` snapshot) rather than re-running, and windowing stays engaged.

#### `partial` (streaming flat snapshot)
`{ type: 'partial', runId, version, windowStart, total, firstRows, widthHints, stats, histogramCounts, histogramLayout, filtered }` — **a SORTED snapshot of the flat survivors so far**, posted as the executor finds them so the table paints a climbing, correctly-sorted result during a scan rather than waiting for the whole `result`. **One run posts one or more `partial`s followed by exactly one terminal `result`** (the same `runId`). Posted for any non-empty flat-eligible run (filter-only, ungrouped): a slow scan posts several as it crosses yield boundaries, a fast scan posts a single one (the executor's post-loop flush emits the tail). A transform or group-cluster run never streams; a **tuple producer** streams via `partialGroups` instead (below). `executePipeline`'s `streamPlan(stack)` decides which stage produces a streamed tier and threads `emit` to it.
- `runId` — the in-flight run; the supersession key. The worker drops a `partial` from a clearly-superseded run (`signal.aborted`) before posting, and the client drops any `partial` whose `runId` isn't the latest *dispatched* (`pendingRun.runId`, the same guard the `result` branch uses) so a stale stream can't paint over the current result. A `partial` **never settles `pendingRun`** — only `result`/supersession do, or `pipelineIdle()` would resolve mid-stream and break the pipeline-idle contract the suite gates on.
- `version` — a per-run monotonic snapshot counter, bumped each time a batch merges in (so positions reshuffle). It is the **stale-window drop key**: the `rows` reply carries the version it was served at, and the client drops a window whose version no longer matches its current snapshot — without it a mid-stream scroll could paint a window from a snapshot the order has moved past (a torn, mixed-snapshot view). FIFO ordering makes the drop sound: the worker posts `partial`-V *before* it can serve a `fetchRows` at version V, so the client (processing in order) reaches `_streamVersion ≥ V` before that `rows` reply — it can never accept a window *newer* than its current snapshot.
- `stats` / `histogramCounts` / `histogramLayout` / `filtered` — **cumulative** summaries over the survivors so far (stats over the in-range set, histogram over the unfiltered distribution — the same split the terminal `result` makes), recomputed each batch and shipped whole. They cross cumulative, not as a delta, because the client holds no resident scores to accumulate into; it consumes them straight into `_workerStats`/`_workerHistogramCounts`/`_workerFiltered` so the stats bar tracks the streamed-so-far set. This makes a `partial` byte-shaped like a `partialGroups`/`partialChains` snapshot — one streaming-render path for all three tiers. **No `indices` or per-row scores cross**: the worker owns the sorted survivor list and serves windows via `fetchRows`. When a score-range filter is active, out-of-range rows are dropped per batch (matching the terminal `result`); an all-filtered batch posts nothing.
- `total` — the **cumulative** in-range survivor count after this batch (climbs monotonically). The scroller sizes from it (`_streamTotal`).
- `windowStart` / `firstRows` — the **SORTED viewport window** for *this* snapshot: `firstRows = buildFlatRows(windowStart, …)` over the client's reported viewport (`streamWindow`), or the top `FIRST_WINDOW` before this run's first `viewport` arrived. Rebuilt and shipped **every** `partial` (the window's contents change as better rows arrive). Same rich shape as the `result`'s inline `firstRows`. The client seeds these into its window cache **at `windowStart`** and **does not clear the cache** mid-stream (only on a new run), so the visible window is always current with zero flicker *and* a scroll between batches holds its prior rows (stale-while-revalidate) instead of blanking to a skeleton — see the render narrative below.
- `widthHints` — the **cumulative** column-width summary (`{ maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }`) over all survivors so far, via the shared `makeWidthHintAcc` (the same reductions the terminal `result` computes), so columns reach the completion widths by the final `partial` and never jump when the `result` settles.
- **`lastFlatResult` stays sorted during a stream.** The first `partial` seeds `lastFlatResult = { runId, version, indices, scope, highlighters }` (the sorted batch); each later `partial` **merges** its batch into the running sorted `indices` (two-pointer merge by the run's comparator) and bumps `version`. A mid-stream `fetchRows` serves a correctly-sorted window from it (guarded by `fetchResultFresh` as always). At completion, the terminal `postResult` **adopts** this array as final unchanged — see below.
- **The `result` is the reconciling truth.** The terminal `result` carries the full `stats`/`histogram`/`widthHints` and an inline `firstRows`. A client may **ignore every `partial`** and still get a correct final result; the partials are a progressive-paint optimization, not the source of truth.
- **Completion is seamless (no reshuffle).** Because the flat comparator is **total** (`flatComparator` tiebreaks down to the unique index, so the incremental merge is batch-order independent and equals a from-scratch sort), the terminal `postResult` for a streamed run **adopts the already-sorted `lastFlatResult` as final** rather than re-sorting — the `result` (its rows carrying the per-row `familyStart` flag, still only under the Entry sort) ships the exact order the stream painted. A non-streamed run (only an empty flat result, since any non-empty one streams) builds and sorts from scratch.
- **The client renders the stream.** `onWorkerMessage`'s `partial` branch decodes the batch and routes it to the live scroller's `appendStreamBatch` (through `streamFlatBatchToScroller`, a ui-layer seam). The scroller treats each `partial` as a **snapshot**: it sets `_streamTotal`/`_streamVersion`, adopts the cumulative `stats`/`histogramCounts`/`filtered` summaries (for the live stats bar), **seeds the viewport window into the position-keyed cache at `windowStart`** (clearing the cache only on a *new* run, not per batch), and re-renders — so the table shows a climbing, correctly-sorted result that reshuffles each batch, *at whatever scroll position the user is viewing* (the scroller's `_reportViewport` keeps the worker informed). Because the cache isn't cleared per batch, a scroll between snapshots holds its prior rows until the next viewport-driven snapshot refreshes them, rather than strobing to skeletons. The terminal `result` adopts the worker's final set via the ordinary flat path (`updateEntries`) and clears the streaming state; the final order matches the last snapshot, so the swap is seamless.

#### `partialGroups` (streaming tuple snapshot)
`{ type: 'partialGroups', runId, version, windowStart, laneKind, atomCount, total, chainCount, firstGroups, groupWidthHints, stats, histogramCounts, histogramLayout, filtered }` — **a SORTED snapshot of the tuple producer's tuples so far**, the grouped-tier sibling of `partial`. Umiaq (≥2 patterns) emits tuples as the join finds them; each batch merges into the running sorted `lastGroupedResult.groups` and posts a snapshot. **One run posts one or more `partialGroups` followed by exactly one terminal `result`** (the same `runId`). Posted when the tuple producer is the **last non-inert tool**, or when only stream-safe filters follow it — `streamPlan` returns those as `downstream` stages that run per-batch in its emit path, so each `partialGroups` snapshot is already filtered. A group-cluster run never streams (buffered-out); a transform streams via `partialChains` (below).
- `runId` — the in-flight run; the supersession key. Same discipline as `partial`: the worker drops a batch from a superseded run (`signal.aborted`), the client drops a `partialGroups` whose `runId` isn't `pendingRun.runId`, and it **never settles `pendingRun`** (only `result`/supersession do).
- `version` — a per-run monotonic snapshot counter, bumped each batch (the order reshuffles as tuples arrive). The **stale-window drop key**: the `groups` reply carries the version it was served at, and the client drops a mid-stream group window whose version the order has moved past — the same FIFO-sound mechanism the flat `partial`/`version` documents.
- `laneKind` / `atomCount` — `laneKind` is always `'record'` here (only a tuple producer streams `partialGroups`); `atomCount` is the per-row atom depth (`currentAtomCount(stack)`, 1 for a pure tuple run). The scroller sets its tuple shape (`sortTier='tuple'`) on the first batch — the result is a record because nothing else streams this message.
- `total` — the **cumulative** tuple (group-row) count after this batch (climbs monotonically). The scroller sizes from it (`_workerGroupCount`). `chainCount` — the cumulative lane count (filtered), the Entries readout source.
- `windowStart` / `firstGroups` — the **SORTED viewport window** of group rows (`groups.slice(windowStart, …).map(encodeGroup)`) for *this* snapshot, over the client's reported viewport (`streamWindow`) or the top `GROUP_ROW_WINDOW` before this run's first `viewport`. Rebuilt every batch. The client seeds these into `_groupWinCache` **at `windowStart`** and **does not clear it** mid-stream (only on a new run), so the visible tuple rows are always current *and* a scroll between batches holds its prior rows instead of strobing to skeletons.
- `stats` / `histogramCounts` / `histogramLayout` / `groupWidthHints` — **cumulative** summaries recomputed over the tuples so far (stats over the filtered lane scores, histogram over the unfiltered ones — the same split `groupSummaries` makes). Shipped per batch because main holds no resident lane scores to recompute from (the flat `partial` ships its cumulative summaries the same way); the scroller consumes them straight into `_workerStats`/`_workerHistogramCounts`/etc. so the stats bar tracks the streamed-so-far set. `filtered` mirrors the flat `partial`'s — `true` when a score-range filter is active (each batch drops a tuple unless **all** its lanes are in range, via `applyScoreRangeToRows`, matching the terminal).
- **`lastGroupedResult` grows during a stream.** The first batch seeds it (`{ runId, version, join, groups, viewSpec, laneKind, stack, summaries, scope }`); each later batch appends the produced groups to the unfiltered `join` and **merges** its sorted, filtered batch into the running sorted `groups` (two-pointer merge by `groupRowComparator` — the group axes plus the unique `g.key` total tiebreak). A mid-stream `fetchGroups` serves a correctly-sorted window (guarded by `groupedResultFresh`). **Completion adopts** `groups` + `summaries` unchanged (the total comparator makes the streamed order equal a from-scratch sort) — like the flat and transform tiers, no re-sort.
- **The client renders the stream.** `onWorkerMessage`'s `partialGroups` branch decodes the window groups and routes them to `appendGroupStreamBatch` (through `streamGroupBatchToScroller`). The scroller sets `_streamRunId`/`_streamVersion`/`_workerGroupCount`, seeds `_groupWinCache` from `firstGroups` at `windowStart` (clearing only on a new run), and re-renders at the user's scroll position (kept current by `_reportViewport`); the terminal `result` adopts the worker's final set via the ordinary grouped path (`updateEntries`) and clears the streaming state.

#### `partialChains` (streaming transform snapshot)
`{ type: 'partialChains', runId, version, windowStart, laneKind, atomCount, total, firstChains, widthHints, stats, histogramCounts, histogramLayout, filtered }` — **a SORTED snapshot of the transform's surviving chains so far**, the transform-tier sibling of `partial`/`partialGroups`. The executor emits raw transform rows per batch; the worker folds mirror pairs **online** and merges surviving in-range rows into the running sorted `lastTransformResult.chains`. **One run posts one or more `partialChains` followed by exactly one terminal `result`** (the same `runId`). Posted only when a transform is the **last non-inert tool**; a filter after a transform stays buffered (v1).
- `runId` / `version` — same supersession + stale-window-drop discipline as `partial`/`partialGroups`; the client never settles `pendingRun` off a `partialChains`.
- `laneKind` — always `'single'` (a transform is one lane per row). `atomCount` is the per-row atom depth (`currentAtomCount(stack)`).
- `total` — the **cumulative** surviving (in-range, folded) chain count. It climbs monotonically: the online fold promotes a mirror's glyph to `↔` **in place** rather than appending a row then collapsing, so the painted count never snaps smaller.
- `windowStart` / `firstChains` — the SORTED viewport window of chain rows for this snapshot (already decoded by the client into `ChainRow`s). Seeded into `_winCache` at `windowStart`, kept across batches.
- `stats` / `histogramCounts` / `histogramLayout` / `widthHints` / `filtered` — cumulative summaries via `transformSummaries` (histogram over the unfiltered survivors, stats over the filtered ones), since main holds no resident chain scores.
- **The mid-stream survivor *direction* is already canonical.** The fold keeps the lexicographically-smaller norm-join direction directly — the corpus emits in norm order, so that direction (the one `unify` would keep) always arrives first, and the later mirror only flips the kept row's glyph to `↔`. So the stream is **exact-final**: completion `postResult` **adopts** `lastTransformResult.chains` unchanged (no re-derive, no word-order flip, no cache re-seed), and the streamed FINAL result is byte-identical to a buffered run.
- **The client renders the stream.** `onWorkerMessage`'s `partialChains` branch routes the decoded batch to `appendTransformStreamBatch` (through `streamTransformBatchToScroller`): sets `_streamRunId`/`_streamVersion`/`_workerChainCount`, the `'multi'` chain shape, and `_winCacheRunId` (so `_invalidateWinCacheIfStale` no-ops and the `windowStart` seed isn't clobbered), then re-renders.

#### `error`
`{ type: 'error', runId, stackRowIndex, message }` — a tool threw (a `ToolStageError`). `stackRowIndex` is the row's position in the run's stack (or `null` if it can't be located).
- **On receipt:** the client sets `stack[stackRowIndex]._error = message` → the red `⚠` row marker + `ErrorPopover`, and settles the run's promise with the errored shape (`{ aborted: false, errored: true, rows: [], atomCount }`). Main owns the per-run `_error` *reset* too — the client clears stale marks on every row at dispatch.

#### `selfReady`
`{ type: 'selfReady', configId, scope, count, built, axis, version, sourceCounts, sourceTotals, rescoreInputs, mergedCount, mergedWidthBound }` — reply to `syncConfig`.
- `configId` — echoes the request's `configId` so the bridge resolves each `syncConfig`'s own reply (see `syncConfig` § *Reply correlation*).
- `scope` — echoes the build's own scope (`scope ?? MERGED_ID`), so the durable `handleSelfReady` keys freshness off the message rather than a per-call closure.
- `count` — the number of synced sources.
- `built` — `ownedCorpusFresh && ownedScope === (scope ?? MERGED_ID)`, read at settle (the **currently-committed** state, not this build's own outcome). It is the **deferred-run drain gate** on the client: `true` ⇒ a usable owned corpus committed for this sync's scope, so a deferred run for that scope can dispatch (no-hang settle paths 1/3); `false` (build failed, or this build was superseded by one for a different scope) ⇒ the client does **not** mark the worker fresh — for a genuinely failed *latest* build it settles the deferred run errored (path 4), for a superseded build it ignores the reply (a newer sync will drain).
- `axis` — the per-config **all-sources histogram layout** (`{ mode, slots, min, max }`); see `syncConfig`. The scope-stable badge-gradient axis (`== the merged histogram layout`).
- `version` — `ownedConfigVersion`, monotonic, bumped once per committed `syncConfig`. Main caches `axis`/`sourceCounts`/`mergedCount` keyed by it, each ignoring a repeat version.
- `sourceCounts` — per-config **merged contribution counts**: `[{ sourceId, count }]`, one per configured source (`dbKey`, merge-priority order), `count` = how many merged entries that source *wins* (the "X" in the scope selector's "X of Y entries"). Derived from `ownedMerged.sourceCounts` — **always the merged build, never the active-scope `ownedCorpus`**. `null` on a build failure. Per-config, never per-run.
- `sourceTotals` — per-config **per-source totals**: `[{ sourceId, total }]`, one per configured source (`dbKey`, merge-priority order), `total` = that source's full entry count (`sourceAccessor(wl).count` — the columnar `cols.n` or My Edits' `rawEntries.length`). Distinct from `sourceCounts`, which is the merge-*winner* subset (a disabled or fully-shadowed source is absent there, but present here) — so it's derived from `ownedBuilt` (every source), not `ownedMerged`. It's the "Y" in the scope selector's "X of Y entries" and the count shown in the scope dropdown / Manage dialog / download gates, read via `sourceTotal(wordlist)` ([`data/merge.js`](../site/src/data/merge.js)). `null` on a build failure (main keeps its last-good map). Per-config.
- `rescoreInputs` — per-source distinct `(score, length)` pairs (`[{ sourceId, pairs: [[score, len], …] }]`, every source). The minimal sufficient input for main's `rescoringChangesScores` bake gate (`rescoreEntry` reads only a row's score + norm length): main applies the **live editor draft** to the pairs locally, so the gate stays correct while the user edits rules the worker hasn't re-synced. Shipped only here and on `fetchApplied` (never the per-edit `editAck`); consumed by `setShippedRescoreInputs` (update-when-present, **not** version-gated — only full-content events carry it, so it can't stale-overwrite). `null` on a build failure (main keeps its last-good map). Per-config.
- `mergedCount` — `ownedMerged.entries.length`, the deduped merged total (the "All Wordlists" entry total, the download-button gate, the Help dialog's merge-diagram count — all reading `mergedEntryCount()`). `null` on a build failure. Per-config.
- `mergedWidthBound` — `computeCorpusWidthBound(ownedMerged)` = `{ maxDisplayLen, maxLenDigits, maxScoreDigits, maxRawDigits }` over **every** merged entry. The client (`mergedWidthBound()`) **floors** the flat and transform tiers' column widths against it (with `mergedCount` as the count-column floor), so the table holds one set of widths across every scope/filter/stream — a filter-only result is a subset of the merge, so its own hints never exceed the floor; only a result that genuinely exceeds it (a multiplying tool, a scope-to-a-disabled-list-bigger-than-the-merge) grows past it. `null` on a build failure / before the first build. Per-config.
- **On receipt (main):** the **persistent** `handleSelfReady` (not a per-call listener) **always** applies `axis`/`version` via `setShippedAllSourcesAxis` and `sourceCounts`/`sourceTotals`/`mergedCount`/`mergedWidthBound`/`version` via `setShippedConfigCounts` — these are the only source for those displays. Each set bumps the `configSummary$` signal so the async-arriving counts repaint their consumers (the merged-count/X-of-Y/badge-axis displays subscribe to it; bumping `cacheVersion$` there would loop the re-sync). Then `applySelfReadyFreshness` uses `built` (+ the echoed `scope`) to drain or settle the deferred run, and the matching `_configWaiters` resolver settles the `syncConfig` promise. Durable consumption is load-bearing: a build slower than any timeout still establishes freshness whenever it lands, so a slow boot self-heals instead of orphaning the handshake.

#### `corpusDump` (test-only)
`{ type: 'corpusDump', scope, entries, error? }` — reply to `dumpCorpus`. `entries` is an array of tuples `[norm, display, score, rawScore, comment, sourceId]` (the **oracle contract**). `rawScore` is `undefined` for a row no rescore rule changed. On a build error, `entries` is `[]` and `error` carries the message.

#### `entry` (test-only)
`{ type: 'entry', requestId, entry }` — reply to `queryEntry`. `requestId` echoes for matching. `entry` is the tuple `[norm, display, score, rawScore, comment, sourceId]` (same shape as a `corpusDump` row) or `null`.

## The deferred-run queue

With no resident main corpus to fall back on, a run whose owned corpus isn't yet fresh for its scope **can't dispatch** — there's no snapshot, no main-thread engine, nothing to run against. So the client **defers** the run and drains it when the worker becomes fresh for that scope. The triggers for a not-yet-fresh run: boot's first paint (before the boot build lands); a config-change re-sync gap; a My-Edits edit window; an import/fetch. (`setScope` is **not** a trigger — the worker rebuilds `ownedCorpus` synchronously from `ownedBuilt`, FIFO-before the run, so the run that follows finds the worker fresh.)

### The client's state (`ui/pipeline-worker.js`)

- **`deferredRun = { stack, sort, scope, resolve }`** — a single latest-wins deferral. A new deferral replaces the prior one (settling the replaced one aborted).
- **`ownedFreshScope`** — a **synchronous** mirror of the scope the worker's owned corpus is fresh for; `ownedFreshFor(scope)` is the race-free gate. `syncWorkerConfig` clears it synchronously at post time (mirroring the worker clearing `ownedCorpusFresh` at `syncConfig` handler start), so a run dispatched in the rebuild gap defers rather than running against the stale corpus. `sendWorkerScope` (setScope) optimistically re-sets the mirror to the new scope when it's already non-null (the worker rebuild is synchronous + FIFO-before the run); when the mirror is **null** it instead escalates to a `syncConfig` for the new scope, whose `selfReady` drains the deferred run — a bare `setScope` would leave the run with no drain signal and hang. `onWorkerCrash` clears it (forcing in-flight/incoming runs to defer until the respawn's `selfReady`).

### The dispatch path

`runOnWorker(stack, sort)` computes `scope` from `state.selected`; if `ownedFreshFor(scope)` it dispatches immediately (`dispatchRun`), else it **defers** — replacing any prior deferral (settling the replaced one `{aborted:true}`). The deferral has **no wall-clock backstop**: it waits for the build's `selfReady`, however long the build takes. `drainDeferred` fires on a fresh `selfReady` (or a `setScope` mirror update) and dispatches the deferral, but only re-checks `ownedFreshFor` against the deferral's **own** scope, so a `selfReady` for a different scope leaves it deferred. The boot run repoints through this naturally — and since `syncConfig` now posts *before* the boot parse, the boot `selfReady` can arrive before the first paint's run is even registered: if it has, `ownedFreshScope` is already set and the run dispatches immediately; if not, the run defers and drains on that `selfReady`. Either ordering settles `init()`'s `await Promise.all([firstPaint, workerReady])` (the captured `syncConfig` promise).

### The no-hang guarantee

A hung deferred promise wedges `_pipelineRunning` → `pipelineIdle()` → the whole Playwright suite, so **every non-deadlock** outcome settles the deferred promise via one of five paths. There is deliberately **no wall-clock backstop**: a same-page worker goes silent only by crashing (path 5) or a code deadlock — the latter a bug we let surface (Playwright's per-test `timeout` fails the test) rather than mask by aborting the run and parking the UI on an empty result. A merely-slow build is not a failure; the run waits for its `selfReady`.

1. **Normal drain.** A `selfReady` with `built: true` → `applySelfReadyFreshness` sets `ownedFreshScope` → `drainDeferred` dispatches → the `result` resolves it.
2. **Superseded before dispatch.** A replacing `runOnWorker` (a newer run) or a `setScope` resolves the prior deferral `{aborted:true}` before it ever dispatched.
3. **Build commits → drain dispatches.** Same as path 1 from the build side; a crash-respawn's re-registration also lands here (the respawn's `selfReady` drains the re-registered deferral).
4. **Build fails.** A failed `syncConfig` build still posts `selfReady`, but with `built: false` (`ownedCorpus` null). The client settles the deferred run **errored** (the `erroredResult` shape `{aborted:false, errored:true, rows:[], atomCount}`), not waiting. **Critical nuance:** a *superseded* build also reports `built: false`, so the client only settles errored when the failing `selfReady`'s `configId` is still the latest (`configId === configRequestId`) **and** its scope matches the deferral — a superseded build's reply is ignored, because a newer `syncConfig` is in flight that will drain the deferral. Getting this wrong either hangs (settling nothing) or prematurely fails a run a later build would serve.
5. **Crash while deferred.** `onWorkerCrash` handles `deferredRun` in **both** branches: below `MAX_CRASHES` it re-registers via `runOnWorker` (which re-defers and drains on the respawn's `selfReady`); at `MAX_CRASHES` it latches `workerUnavailable` and settles the deferred run errored.

## Cancellation / supersession

Single thread → **at most one run executes at a time**. Supersession is message-driven:

1. Each `run` carries a monotonic `runId`. The worker stores `latestRunId` (written by its own `onmessage`, so no shared memory).
2. A **newer `run` implicitly supersedes** an older one — no explicit `cancel` needed for the fast-typist case. `cancel` exists only for teardown / search-cleared.
3. The worker's yielder, at each due point, does a **macrotask yield** so a queued `run`/`cancel` message can fire, then checks `if (thisRunId !== latestRunId) throw AbortError`. The throw unwinds the superseded run; a tiny scheduler then starts whatever run is latest.

**The yield must be a macrotask, and `setTimeout(0)` is the one to use** — empirically confirmed to preempt an in-flight run within one yield window on all three engines, and (a fresh callback per call) naturally **re-entrant**. Re-entrancy matters because superseding runs overlap by construction. A *microtask* yield (`queueMicrotask`) drains only microtasks and **never** delivers the `message` task. `scheduler.yield()` is **forbidden** in the worker: its boosted-priority continuation **starves** the `message` on Chromium (preempts on Firefox, absent on WebKit), so relying on it would silently break cancellation on the dominant engine.

**A superseded run sends NO reply** (it throws `AbortError` internally and moves on). The main client therefore **must settle that `runId`'s pending promise itself** (as aborted) on dispatch of the newer run — otherwise `pipelineIdle()` (which the whole Playwright suite awaits after a keystroke) dangles. **Reap superseded runs by `runId`, not by waiting for a terminal message:** an abandoned run's terminal event can arrive *after* the winner's `result`, or never, so the client tracks the in-flight `runId` and settles the stale one when it dispatches the newer one.

The worker yields **coarsely** (~30 ms) — it has no UI to keep at 60 fps, so it yields only often enough to honor cancellation, which also makes the compute faster than the main thread's ~6 ms cadence.

## Worker lifecycle

- **Spawn:** lazily via `getWorker()` on first use, one worker per tab — but that first use is the boot-time `syncConfig`, so in practice it comes up at boot. Spawned via `new Worker(new URL('./engine/worker.js', baseURL), { type: 'module' })`, where `baseURL` is **`main.js`'s `import.meta.url`**, injected at boot through `configurePipelineWorker({ baseURL })`. (Anchoring on `main.js` is load-bearing — bundling inlines the `new URL` literal verbatim without rewriting its relative path, and the client module sits at a different depth than the bundle, so a client-anchored URL is dev-passing/prod-404.)
- **Memory:** the worker holds the only corpus copy — roughly **1× peak corpus memory** in the worker (rich `entries` + `byNorm`/`byKey`, plus the separate `ownedMerged` when scoped away from merged). Main holds no merged/scoped corpus, only My Edits' `rawEntries`.
- **Crash → respawn → rebuild → re-dispatch.** A worker crash — the parent `Worker`'s `error` / `messageerror` event, **distinct from a tool `error` *message*** (which the worker posts cleanly over a live connection) — has no main-thread engine to fall back to, so recovery is *respawn + rebuild-from-IDB + re-dispatch*:
  - **Crash detection.** The client wires `error` and `messageerror` listeners on the `Worker` at spawn, both → `onWorkerCrash`. (Both are catch-alls for a dead worker; neither carries a usable recovery payload.)
  - **Teardown.** `onWorkerCrash` removes the dead worker's listeners, `terminate()`s it, nulls `worker`, **clears `ownedFreshScope`** (so in-flight/incoming runs defer until the respawn's `selfReady`), and increments `crashCount`.
  - **Below `MAX_CRASHES` (respawn path).** Capture and clear both `pendingRun` and `deferredRun`, call `syncWorkerConfig(state.sources)` — which respawns the worker (`getWorker()`) and posts `syncConfig` so the fresh worker **rebuilds its owned corpus from IDB** — then re-dispatch the in-flight run **and** re-register the deferred run through the normal `runOnWorker(stack, sort)` path, chaining `.then(resolve)` onto each **original** awaiter. Re-dispatching through `runOnWorker` (not a bespoke post) is load-bearing: it keeps supersession intact (a newer run advances `runCounter` and settles this rescue `{aborted:true}`) and re-defers each run via the freshness mirror, so they drain on the respawn's `selfReady`.
  - **At `MAX_CRASHES` (graceful latch).** There's no corpus to rescue onto, so latch `workerUnavailable = true` and resolve both the in-flight `pendingRun` and the `deferredRun` with the **errored shape** `{aborted:false, errored:true, rows:[], atomCount}`. `runOnWorker` short-circuits every subsequent run to that errored result on its first lines (also settling any prior deferral), so latched runs **settle gracefully and never hang**. The errored/empty result flows through the normal render path to an empty scroller.
  - **`MAX_CRASHES = 2`** — a hard ceiling on a crash → respawn → recrash loop.
  - **State.** `pipelineWorkerState()` returns `{ workerUnavailable, crashCount }`.
  - **Test hooks.** `crashWorkerForTest()` posts `__testCrash` (exercises the real `error`-event wiring); `forceWorkerCrashForTest()` calls `onWorkerCrash` directly (deterministic); `failNextWorkerBuildForTest()` posts `__testFailNextBuild` (exercises the build-failure `selfReady`).

## Invariants (do not break these)

1. **`byNorm` cannot drift.** The worker builds `byNorm` via the one shared `buildByNorm(entries)` ([`engine/snapshot.js`](../site/src/engine/snapshot.js)) — canonical row = the **code-unit-minimum** display per norm. The per-norm splice path uses the sibling `canonicalNormRow(rows)`, which applies the **same** rule to one norm's rows; the owned-corpus splice routes through it, so it can't disagree on case variants (`'CAT'` vs `'Cat'`). Never reimplement the canonical-row selection on one side.
2. **Each entry's `_i` stays paired with `ownedCorpus`.** It is stamped once per corpus rebuild (never per run) and restamped wholesale on every splice; a desync silently indexes one corpus into another and corrupts every rendered row. The flat result's indices name `ownedCorpus.entries` (or its frozen `pinnedCorpus` snapshot when pinned — refresh-on-consent, `corpusFor`), so a `fetchRows` is served only against a still-fresh, scope-matched corpus (`fetchResultFresh`). The grouped result's retained `lastGroupedResult` holds chains that reference *that* run's corpus by entry identity, so its windowed fetches carry the same freshness discipline: `groupedResultFresh` (`lastGroupedResult.runId === runId` **and** `ownedCorpusFresh` **and** `ownedScope === lastGroupedResult.scope`) gates `fetchGroups`/`fetchGroupChains`/`fetchAllGroups`, dropping any fetch whose corpus changed since the run. The transform result's retained `lastTransformResult` holds chains that likewise reference *that* run's corpus, gated by `transformResultFresh` for `fetchTransformRows`/`fetchAllTransformRows`. `lastFlatResult`, `lastGroupedResult`, and `lastTransformResult` are mutually exclusive — every result branch sets one and nulls the other two — so a fetch addressed to the wrong tier is dropped by the runId mismatch.
3. **Worker = the corpus; main = presentation.** The worker is the only place a merged/scoped corpus exists, and its corpus is **rich** — it carries `comment` and source identity because it feeds rendering directly through the rich rows/atoms it ships. `engine/` stays DOM-free (enforced by `tests/unit/engine-dom-free.test.js`): the worker reasons about norms/displays/scores/comments and resolves `sourceId` to a `dbKey`, but never renders or touches the DOM. Anything view-only (HTML, the resolved `wordlist` object, the My-Edits raw-score swap) is reconstructed on main.

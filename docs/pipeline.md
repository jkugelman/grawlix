# Pipeline

The pipeline turns the tool stack into the rows the entries table shows. The user builds a stack of tools in the gallery ([`design.md`](design.md) § *Tool gallery & stack*); the worker runs it over the selected corpus, streaming chain rows (one entry and the atoms each transform appended to it) or group rows (entries a group tool clustered under one key) back to main as they're found. This doc covers how a run executes, how it yields and is superseded, how results stream, how rows sort, and how matches are highlighted. The message contract between main and the worker is [`worker-protocol.md`](worker-protocol.md); the tool catalog is [`tools.md`](tools.md).

## Pipeline execution

`executePipeline(mergedWordlist, stack, signal)` works in one shape end-to-end: a list of **groups**, each `{ key?, chains: Chain[] }`. The seed is a single group with `key === undefined` holding one chain per merged entry (a cached array — [`design.md`](design.md) § *Caches*); a group tool partitions that single group's chains across K keys. Flat pipelines are the degenerate case — the whole run is one giant group that gets unwrapped at exit. The executor walks the stack rows in order, running each non-group tool over every group's chains; the only branch is at exit, where a never-grouped run returns its single group's `chains` as the `rows` array and a grouped run returns the group list itself. This is what keeps the same `runToolStage`, `unify`, and chain-bookkeeping code paths working for both modes — there is no separate "flat" executor.

The corpus it receives is the full merged (or scoped) view: the score range is a **post-pipeline filter** applied to the chain rows the pipeline emits, not a pre-pipeline trim. The pipeline runs against every entry, then `applyViewFilterToRows` drops any chain whose journey touched an out-of-range atom; for grouped pipelines the drop is per chain inside each group, and a group stays while at least two chains survive — and, when a grouped filter is active, while at least one of those survivors is one of its matches. That second clause closes a gap the group-as-row model opens: a cluster survives if *any* member matches (§ group-row model), but the score range then trims members, so without the gate a cluster could outlive the very match that justified it — a `zzz` search leaving a cluster whose only `zzz` sat below the bracket, displayed as its *other* members with nothing highlighted. The gate (a per-member `matched` flag the grouped filter sets, read here) drops it instead. Crucially it runs *here*, after the histogram is bucketed over the unfiltered output, so that below-bracket `zzz` still shows as a faded, clickable bar — widen the range and the cluster returns; the alternative (deciding survival up in the executor) would erase it from the histogram too. Two things drive the choice. First, the stats bar's histogram is *honest* about what dragging the range narrower will trim — it sources from the unfiltered pipeline output and fades the cut bars in place, instead of showing only what's already past the bracket. Second, an "all atoms in range" rule reads as "this row is fully valid under the current range," conservative and predictable; a "bottom-line only" rule would surface rows that relied on out-of-range source words. The cost is that heavy tools (anagram on a 500K wordlist) lose the ability to use the range as a pre-trim for performance — accepted, since tightening the range to manage tool perf was an indirect path users probably weren't reaching for. Since the worker owns the result and windows it (§ *Cooperative runtime*), the filter is applied **worker-side**, and a range change **reprojects** — the worker re-derives the filtered view over the retained (unfiltered) join and re-windows, never re-running the join (§ Streaming results) — with the histogram still bucketed over the unfiltered scores, so out-of-range bars stay clickable.

A tool's `run(entry, prepared, wordlist)` is a **per-row pure function** — it sees one entry's text and returns a per-row decision; the system owns the outer loop, cooperative yielding, abort, atom construction, and chain bookkeeping. Filter and transform tools carry a `run`; a group tool carries a `group` instead and is dispatched separately by `executePipeline`.

- **Filter** (`kind: 'filter'`) keeps or drops the row. `run` returns `null`/`false` (drop), `true` (keep), or a `Range[]` (keep, highlighting the match); a highlighting filter's kept rows gain a same-word atom carrying those ranges.
- **Transform** (`kind: 'transform'`) emits 0+ new entries; each output branches the row into a new chain row with an atom appended. `run` returns `TransformOutput[]` of `{ entry, coined?, inputHighlights?, outputHighlights? }`, where `entry` is a string (looked up in the merged wordlist's `norms` index) or `[string, score]` for a tool-synthesized entry not in any wordlist, and `coined` marks a synthesized entry whose score is carried but not shown.

An optional `async prepare(params, ctx, input)` runs **once per stage**, after every upstream stage has finished; its return value is handed to `run` in place of the params. It's where a tool compiles a regex or pre-sorts letters once instead of per row — Search compiles its match pattern, Anagram pre-sorts its target letters — or builds an index for a heavier tool. Tools without a `prepare` get the normalized params object.

`ctx` is the tool's view of the run. `ctx.wordlist` is the merged-wordlist cache (`{ entries, sourceCounts, norms, byKey }`; `norms`, a `Set<norm>`, is the membership index that ships today, with sorted-letter and length indexes to land as tools demand them). `ctx.grouped` tells a `prepare` whether the row is in all-mode, so a function-`kind` tool can branch on it (Caesar's `prepare` returns a rotate-every-entry transform when all-mode carries a shift). `ctx.forEach` / `ctx.times` / `ctx.due` / `ctx.yield` / `ctx.throwIfAborted` / `ctx.progress` are the cooperative-yield surface (§ *Cooperative runtime*); `ctx.progress(done, total)` — and, for free, any `ctx.forEach`/`ctx.times` over a sized collection — reports a 0..1 progress fraction the worker forwards to drive a determinate progress ring, so a long non-streaming pass fills the ring instead of showing the indefinite spinner (see [`worker-protocol.md`](worker-protocol.md) § `progress`). Its consumers are the grouped result's cluster pass (`bucketize`'s `ctx.forEach` over the surviving chains) and the spacing table's build ([`segmenter.md`](segmenter.md) § *The spacing table*), a `prepare`-time sweep of every entry. `ctx.cache` (`get(toolKey)` / `take(toolKey)` / `put(toolKey, value, bytes, { patch, elapsed })`) is the seam onto the worker's prepare-artifact cache: a `prepare` retains whatever it computes from the corpus alone, so a run with different params reuses it (see [`worker-protocol.md`](worker-protocol.md) § `artifactCache`). Outside the worker it is a no-op, so a tool calls it unconditionally. `prepare` is `async`, and carries those helpers, because indexing the wordlist is real O(N) work that has to be chunked and yielded or it freezes the tab. `run` stays narrow by contrast — synchronous, per-row, no `ctx` — so the executor keeps sole ownership of the loop, its yielding, and abort; a tool's `run` can't stall or re-drive the run.

The stage's working set arrives as the **third `prepare` argument**, `input` — a lazy, read-only view of the previous stage's output as entry strings, resolved on access so a tool that ignores it pays nothing and the executor's chain rows never leak into the tool surface. It lets a `prepare` index the surviving working set, not only the wordlist. It's a separate argument rather than a `ctx` field on purpose: a `prepare` that reads the input declares it in its signature, and `streamPlan` reads that arity (≥ 3) to keep an input-dependent `prepare` out of a tuple producer's streaming emit path (§ *Streaming results*), where the input isn't available yet — its pre-run value would diverge from the terminal pass. Caesar's `prepare` reads only `ctx.grouped` (a stable row property), so it streams after a tuple producer; a future input-reading `prepare` would not.

Param strings get lowercased at the executor boundary (raw flag opts out for regex patterns), so tools see canonical input on both sides without per-call ceremony.

**Runtime input routing.** `matchOn` on a tool definition selects what `runToolStage` feeds the tool's `run` (and, via `bucketize`, its `group.key`): the default gives `wlEntry.norm` (letter tools); `'display'` gives `displayOf(wlEntry)` (Initialisms, whose grouped mode needs word boundaries); `'both'` hands over the whole `wlEntry` so the tool can test norm and display itself (Search, Regex — see *Dual-arm search*). The flag also sets the default coordinate space (`norm` or `display`) tagged onto any ranges the tool emits, so the renderer can project at paint time without each tool having to think about coordinates — and a `'both'` tool tags each range itself, since its hits straddle both spaces.

## The chain-row model

A **chain row** is `{ atoms: Atom[] }`; an **atom** is `{ wlEntry, highlights, glyph }`. Each atom is one view of a word as it moves through the pipeline — the originator entry, a new word per transform, and a same-word repeat carrying each additional highlight — and the entries table stacks them vertically, sharing column widths, so a row reads top-to-bottom as one entry's journey (`RELEARNING → ELEARNING → LEARNING → EARNING`). One shape covers a one-atom result, a two-atom pair, and any longer chain — there's no separate row type per output shape. (Worker-internally, an *undecorated* row — the pipeline's common case, a plain merged entry no tool has highlighted or transformed — is the bare `wlEntry` itself, not a `{ atoms: [oneAtom] }` wrapper; the executor promotes it to a chain only when a tool decorates it. That keeps a filter-only run from materializing a chain object + atoms array + atom per corpus entry — see [`design.md`](design.md) § *Caches*. The shipped/encoded row is always `{ atoms }`, so this is invisible past the worker boundary.) `highlights` is the atom's flat list of `{ kind, start, end }` ranges — or `null` when the atom is not a highlight slot (see § Highlights pipeline).

A regular atom's `wlEntry` references the merged wordlist (same identity as the source entry, so EntryPanel edits route correctly). A **synthetic** atom — built from a tool's `[string]` output for an entry in no wordlist — has `wlEntry.wordlist === null` and a `score` that reads live off the input entry, or a fixed one when the tool supplies `[string, score]` (Optional letters computes the min across the pair it marks); `EntryPanel` suppresses open on it, since editing a synthetic's score wouldn't write back anywhere.

**A synthetic's score comes from the real entries that justify it.** One parent gives that parent's score, live (Space out, Rebus); two give the lower (Optional letters) — the weakest-link rule downloads apply to a whole chain. Those three *re-render* a scored entry — respaced, a symbol standing in, a letter circled — so the score is still about the thing on screen and its badge shows. A **coined** synthetic is a different string the source's score says nothing about: Search/Regex replace with **Allow unlisted** emits `coined: true` on every off-list output, the executor stamps it on the synthetic `wlEntry`, and the entries table draws a faint em dash in place of that atom's score badge (`buildScoreCellHTML`) — a dash rather than a blank, because Score is the one column a real entry never leaves empty, so a blank there reads as a rendering glitch. A coined atom is *judged* as the atom directly above it and *written* at the trash score. Judged: the `wlEntry` still carries its parent's score, live, so the score range passes it exactly when it passes the parent, whose badge is showing, and it never moves the chain's min or max — nothing invisible acts on its own. It can't carry the trash score instead, because the score range judges every atom and the default range is trash + 1 (`defaultScoreRange`): ticking Allow unlisted would then show a new user nothing. Written: the wordlist download is the one place a coined atom is forced to be a number, and `buildWordlistText` writes `getTrashScore()` there — default 0, the mark most wordlists use for an unvetted or junk entry — instead of the chain minimum a real tail gets. So a list downloaded under a `1+` range can hold `;0` lines: the range kept those rows for the entries they came from. There is no same-letters exception: an output is either a real entry with its own score or coined and unscored, so `\s` → `-` is coined like any other rewrite. The histogram and stats bin each chain's *last* entry and keep coined ones in — drop them and Entries undercounts the rows while the score bracket trims rows no bar shows. `coined` is a tool declaration rather than something derived from the norm, because Rebus changes the norm too and keeps its badge.

**A row can hide the side it came from.** `input`/`output` are tri-valued — `'highlight'`, `'plain'`, `'hidden'` — rather than the pair of booleans they started as, because the interesting states are per-side and mutually exclusive: "hidden but highlighted" is meaningless, and expressing it as two booleans made it *representable*, so both the emit path and `currentAtomCount` had to defend against it separately and agree. One field per side makes it unrepresentable instead. `'hidden'` on the input drops the originator entirely, so the row is the tool's output alone — Optional letters uses it, because its output is the same word wearing a mark and showing the unmarked source beside it says nothing. (Note the deliberate name collision with a `run` result's `inputHighlights`/`outputHighlights` *range arrays*: those are per-result data, these are static per-tool declarations. Renaming the declarations is what separated the two.) `'hidden'` on the output is legal and unused: it would mean "run the transform but show only the input", i.e. keep the entries it produced something for.

**A side can depend on the row's params.** A declaration is either one of the three strings or a `params => side` function, resolved by the stack row (`inputSide()`/`outputSide()`), which is what every reader goes through. Search and Regex declare their replace `output` this way: `'highlight'` when the replacement can color something, `'plain'` when it never can — a deletion (empty replacement), or literal text beside capture groups, where the echoes claim the coloring. The reason is the fold rule below: a slot that is always empty is still a slot, so a chained tool's mark on the same word can't fold into it, and two chained deletions would show every intermediate word twice (`CARTS` / `→ CART` / `CART` / `→ CAT`). Declared plain, the output atom takes the next tool's mark and the row reads `CARTS` / `→ CART` / `→ CAT`. `replacementMarksOutput` answers from the same per-token test `runReplace` colors with, so the declaration can't promise a slot the run never fills or drop marks it does produce.

**Atom count is static.** Every row in a given pipeline has the same atom count, derivable from the catalog records and the stack rows' params alone — `currentAtomCount(stack)` simulates the executor's emit-then-unify over the active tools (not inert) without inspecting any row. The originator is one atom; each transform appends a new-word output atom; each highlighting tool (a search, or a transform marking its input via `input: 'highlight'`) appends a same-word atom that `unify` folds into the tail unless the tail is itself a highlight slot — so the originator and the first search collapse to one atom, while three searches on one word leave three. `atomCount` is the resulting count; the renderer and the virtual scroller read it, so the scroller knows every row's height (`atomCount` × row height) without measuring. An empty Search row is *inert* — it reports `isInert(params)` and `executePipeline` skips it, so an empty search bar adds no atom.

**Transforms emit per directed pair.** A transform writes the dumb thing — one row per `(input, output)` it produces. Semordnilap emits a row whenever the reverse is also an entry, in *both* directions; the unification pass cleans that up afterward (§ Symmetric unification). The relation `glyph` (`→`, `↔`) is a static field on the tool, not a character the tool body picks.

## The group-row model

A **group row** clusters the merged wordlist rather than transforming it entry by entry, then runs the rest of the pipeline as a *per-group* sub-pipeline. Groupable tools today: Anagrams (letter multiset), Letter bank (distinct-letter set — POST, STOP, SPOT, TOPS cluster under `opst`), Consonantcy (consonant skeleton), Vowelcy (vowel skeleton), Caesar shift (shift-invariant key — STEEDS and TUFFET cluster), Cryptogram (letter-pattern key — LEVEL and ROTOR cluster), Initialisms (word-initial letters of multi-word displays), Dead center (the centered core), and Rhymes (the rhyming part).

**All-mode is a flag on the stack row, not a separate tool.** A flat tool declares groupability by adding a `group: { key, columns }` sub-object — `key(entry)` returns the equivalence's canonical string — or an array of them, when one entry reads several ways (Rhymes' pronunciations, Dead center's cores) — and `columns` declares the per-group attributes that surface in the row. Two `✱` affordances drive it: a one-click button in each groupable card's top-right corner (calls `pick(key, { grouped: true })` to add the tool in all-mode in a single step), and a toggle anchored to the right of the row's input (flips `row.grouped` on an existing row in place). The two are wired to the same one-at-a-time rule, the same tooltip vocabulary, and the same state via `refreshGalleryActive` / `refreshOtherAllToggles`. `✱` means *run over all inputs* — usually, but not always, *group*. For a static-`kind` tool `row.kind()` promotes the grouped row to `'group'` and its `params` are ignored (its input is the whole upstream row set); a tool with a function `kind` decides instead, reading `row.grouped` — Caesar's `✱` is a `'group'` with no shift but a rotate-every-entry `'transform'` with one, so its Shift param stays live in all-mode to switch between them (and its `prepare` branches on `ctx.grouped`). The one-at-a-time rule still keys off the `✱` flag, not the resolved kind, so a Caesar transform-in-all-mode counts against it like any group. URL representation: `?letter_bank=SPOT` is the flat tool; `?letter_bank&all` is the grouped row. `all` is a reserved positional keyword — the decoder treats it as a flag on the preceding row when that row's tool declares a `group:` sub-object.

**Why the input-anchored toggle.** The earlier affordance was a labeled "Grouped" button on the gallery card itself, decided flat-vs-grouped at add time. The wide button conflated *picking a tool* with *picking its operating mode*, and its absolute-positioning overlapped long tool names on narrow cards. The replacement is two `✱` affordances pointing at the same concept: a small button in each groupable card's top-right corner (one-click "add this tool already in all-mode") and a toggle anchored at the right edge of the tool row's input (flip an existing flat row into all-mode, or back). Both wear the same `✱` symbol, both use the same tooltip vocabulary (*Show all values* / *Show one value* / *Already showing all values* / *Only one ✱ tool at a time*), and both gate on the one-at-a-time rule. The corner button gives the gallery the same one-shot affordance the old Grouped button had — without the alignment problem of a labeled button — while the in-row toggle handles the "I added this flat, now I want all values" path and serves as the live state indicator. When the row is in all-mode the input clears, takes a `var(--surface)` disabled-style background, shows an accent-colored `all` placeholder, and `pointer-events` go to none — the field still reads as a text box but is clearly inert until toggled off. The user's typed value is preserved in `row.params` across the toggle and restored on exit.

`bucketize(chains, def, ctx)` takes the inbound chain list and returns the K groups. Not a partition: a multi-key tool files one chain under each of its keys. A group is `{ key, chains, anchor? }`: `key` is the equivalence key (`def.group.key(entry)` against the chain's *tail* entry — what the upstream pipeline transformed it into), `chains` carries the bucket's members **with their atoms intact**, and `anchor` (optional) is the wlEntry the cluster pivots around when the tool declares one. This is what lets a flat transform upstream of the group survive: Head off → Vowelcy clusters the shortened forms but each chain still reads `AAMILNE → AMILNE`, the upstream Head off atom carried forward so the chain matches the height `currentAtomCount` reserves for it. Clusters of fewer than two members are dropped by the bucketizer, not the executor — a downstream tool may legitimately thin a cluster to one survivor, so the executor never imposes the rule. A *member* for that floor is a distinct word, not a distinct merged row: the merge emits one row per `(norm, display)`, so the several spellings of one entry (`going ape` / `goingape` / `GOINGAPE!`) count as one, and an all-one-word bucket is no cluster and drops. Only the keep/drop gate dedups — a surviving cluster still shows every spelling as its own chain (and its `Count` enumerates them, so Count counts entries while the floor counted words). Identity for the gate is the whole chain, not just the tail, because a transform upstream of the group can land two genuinely different words on the same tail (`wheat`/`cheat` → `heat`), which must stay separate members. **Redundant groups drop last.** Filing a chain under each of its keys buckets one cluster once per key its members happen to share — nine copies of `in the mix` / `in the sticks`, one for every way to say `in the` — so a group repeating another's member set, or sitting wholly inside a larger one, is dropped. Only against a group that *renders* the same, though: an anchored tool shows its key, and Dead center's `Center: ABC` and `Center: B` over one pair of entries are two answers rather than one row twice. Clusters that merely overlap both survive, which is what keeps a two-pronunciation word in each family it rhymes into. A tool can be a highlighting filter in flat mode yet a group producer in all-mode (Dead center marks its center span when filtering, clusters longer words under their center entry when grouped). The flat-mode `input: 'highlight'` setting is inert when the tool is the group producer — `chainProducesMultiAtom` and `currentAtomCount` ignore it for a group-kind row. A group producer opts into per-member highlights separately, via `group.memberHighlights(member, key) → ranges`: bucketize stamps each member a highlight atom (the center span, derived purely from `member` and `key` — no re-match) and pre-collapses it to a single highlighted atom. Pre-collapse, rather than appending a slot for the post-pass `unify`, is deliberate — a group's members are an equivalence set, and unify's cross-row mirror-fold would merge reverse members (`rat`/`tar` in one cluster), so the pure-group path must skip unify. `currentAtomCount` counts the member-highlight slot only when `memberHighlights` is declared.

**Optional `group.anchor(key, wordlist)` hook + `group.anchorLabel`.** Returns the wlEntry that anchors the cluster (or `null` to drop it); the label names what that anchor is for the user. Initialisms declares `anchor: (key, wordlist) => bestRowForNorm(wordlist, key)` and `anchorLabel: 'Initialism'`, so a `TIS ⇄ the IRS` cluster only survives when `TIS` itself is in the wordlist — the value is the bidirectional pair, not the one-way coincidence. Dead center declares the same pair with `anchorLabel: 'Center'`. The anchor's score also gates the score-range filter (`applyViewFilterToRows` drops a group whose anchor falls outside the bracket, alongside its chain-atom check), so dragging the range narrower trims initialisms whose anchor leaves the band even when the expansions wouldn't have been cut on their own. The histogram source (`bottomLineAtoms` of the unfiltered pipeline output) still reflects chain atoms only — the anchor score isn't bar-counted, so an anchor-driven cut isn't visualized by the histogram. Initialism anchors typically land in the same score band as their expansions, so the cosmetic gap is rare.

The anchor is **first-class on the row**: when `anchorLabel` is set, the group row renders a dedicated slot between Count and the chains, drawn as a real atom (mono entry text + colored score badge — the same `.atom-entry`/`.atom-score` spans chain atoms use). Click anywhere on it and EntryPanel opens on the anchor's wlEntry, so editing it is exactly like editing any other atom and routes into My Edits. The slot also drives **three derived sort axes** keyed off the anchor: `entry` (alphabetical by `anchor.norm`, label tracks `anchorLabel` — "Initialism" rather than "Entry"), plus added `length` (anchor letter count) and `score` (anchor score). For unanchored group tools (Anagrams, Letter bank, Consonantcy, Vowelcy) nothing changes — the slot is omitted and the standard group axes apply.

**Group columns appear as row attributes and sort axes.** Each entry in `group.columns` carries `{ label, value(g), sort?, tiebreaker?, tiebreakers? }`. The label becomes a column header alongside Count; `value(g)` (called with the group object — `key` and `chains` available) renders once per row, aligned to the first atom-row of the row's chains. Each column also registers a sort axis under its own label (`Letters`, etc.) unless `sort: false`. When that column is the primary sort, its `tiebreakers` (an explicit `[{ project, dir }, ...]` matching the static axis shape) drives the cascade; if omitted, the fallback is count desc, min score desc, max score desc, then chain seeds alphabetical — equal-on-the-column groups surface bigger clusters first, then order by the quality of their worst member, then their best member. The `tiebreaker: false` flag separately opts a column out of contributing to *other* axes' cascades.

**Each chained tool runs on every group's chain list, independently.** Head off chained after Letter bank (grouped) runs Head off on each cluster's members — each surviving chain gains a new output atom, each non-surviving chain drops. A **transform** branches a group's chains like any flat transform (`runToolStage`). A **filter** behaves differently once grouped: the cluster *is* the row, so a filter is a predicate on the whole group — it survives intact when *any* member matches and drops only when none do (`runGroupFilterStage`), never trimming to just the matching members. A partial cluster would misrepresent the equivalence it stands for: the value of a Letter-bank or Cryptogram cluster is the whole set sharing its key, so searching to *locate* a cluster reveals all of it, not only the search term. A highlighting filter (Search, Regex) marks the matchers and hands every other member an empty highlight slot, so the cluster keeps the uniform atom height `currentAtomCount` reserves. Groups whose chain list empties drop (the never-bucketized flat group is the one exception — an empty result is still a flat result, not a vanished one). This is the one spot flat and grouped diverge — a filter trims per *chain* when flat (chain = row) but keeps-or-drops the whole *group* when grouped (group = row); `runToolStage` and `unify` otherwise run identically over each group's chain list, since the flat seed is itself a group of K chains. (The score range, applied post-pipeline by `applyViewFilterToRows`, is the exception that still trims members per chain — it's a score-validity lens, not a locate filter, so an out-of-range member is genuinely excluded from the cluster; and if the range hides *every* member that matched the grouped filter, the cluster drops rather than lingering on an invisible match — see § Pipeline execution.)

**At most one group tool per pipeline.** A second has nothing well-defined to cluster — the first already replaced the entries with group rows — so the `✱` toggle on every other groupable row greys out once one is active, the toggle handler refuses to flip a second on, and the URL decoder ignores group tools past the first.

## Length filter

A second stats-bar filter beside the score box, sharing its `parseRange` syntax (`7`, `5+`, `5-7`) and its post-pipeline, worker-side, reproject-on-change plumbing — it rides the same `viewSpec`, so changing it re-derives the view over the retained join rather than re-running. Length is `norm.length`, the grid-square count the entries table's Length column and the `length` sort axis already show, so the filter agrees with what's on screen.

**It judges the bottom line, where the score range judges every atom.** This asymmetry is the design, not an oversight. Score's "every atom in range" rule reads as *this row is fully valid under the current range*, and a chain that relied on an out-of-range source word genuinely isn't. Length can't work that way, because a large class of tools **change length** on purpose: Head off, Back off, Remove string, Kangaroos, Joeys, Hidden anagram, Dead center, Initialisms, Weave, Rebus, Optional letters. Under an every-atom rule, `Head off "s"` with a length of 4 asks the 5-letter seed `swing` to also be 4 letters and returns nothing — the filter would read as broken on precisely the tools worth filtering. Judging the last atom instead asks the question the user is actually asking: *does the thing this row produced fit my slot?* Length-preserving tools (Anagrams, Caesar, Cryptogram, Space out) behave identically under either rule, so the divergence costs nothing where the rules agree. Chain rows render one line per atom with its own length, so a Head-off row showing `swing 5` above `wing 4` under a length-4 filter is self-explaining rather than surprising.

**Cluster rows trim; tuple rows opt out.** A `'set'` cluster (Anagrams, Rhymes, Consonantcy in all-mode) is a set of **alternatives** — any member could go in the slot — so filtering its members by length is exactly what the filter means, and it trims per member and drops the cluster below two survivors, mirroring score. It does *not* gate on the cluster's anchor the way score does: the anchor is the seed the cluster was found from, not a candidate answer, so gating it would drop every cluster whenever the seed's own length missed — the same trap the bottom-line rule avoids for chains. A `'record'` tuple (Umiaq `AB;BA`, Weave) is the opposite case: its lanes are **simultaneous**, one solution needing all of them at once, so "is this row 7 letters" has no answer. Every candidate rule answers a different question, and trimming lanes would render a row below its arity — the one thing the tuple filter path refuses to do. So the filter is **disabled** there rather than guessed at: the control greys out (`chainSortTier(stack) === 'tuple'`, read off the stack so it greys the moment the tool is added, not a run later) with a tooltip saying why.

Disabled means **inert everywhere**, enforced at a single chokepoint — `activeLengthRange()` returns `''` when the tier is tuple, so the worker never receives a range the greyed control is still displaying, and rows, counts and histogram are all untouched. The value itself survives: it stays in the field and in the URL, so adding a Umiaq row and taking it back off restores the filter instead of destroying what the user typed.

**It narrows the histogram, where the score range doesn't.** The score bracket is drawn *over* the bars, so bucketing score-filtered scores would erase the very bars the user drags the bracket across — hence the histogram's unfiltered-by-score source. Length has no such overlay, so nothing is hidden by applying it, and the narrowed reading is the more useful one: *of the 7-letter entries, here is the score spread*, which is what you want when picking a cutoff for a specific slot. The consequence is that the flat histogram is no longer invariant across a view change, so a length change has to force the recompute that sort and score-range don't.

## Inverting a filter

**Invert is a flag on the stack row, like all-mode — not a tool, and not a param.** `row.invert` negates a filter's verdict: `grep -v` for the pipeline. The engine owns it end to end; no tool's `run` knows it exists. In `runToolStage` the filter branch keeps the rows `run` rejected instead of the ones it accepted, and carries them through **bare** — a non-match has no ranges, so an inverted row opens no highlight slot however the tool declares `input`. `currentAtomCount` and `chainProducesMultiAtom` agree via the same `row.inverted()` accessor, which is what keeps the static atom count matched to the emitted shape (a mismatch overlaps rows in the scroller with no error).

**Only filters invert**, and `row.inverted()` — not `row.invert` — is the gate every reader goes through. (Reversing a transform's *direction* is a separate, shipped feature — the converse relation under a different flag; see § *Inverting a transform's direction*.) A transform's *negation* — "keep the inputs it produced nothing for" — flips the row's kind, and a record's lanes are positional, so those two remain open ([`design.md`](design.md) § *Non-features* has the reasoning). Because Search, Regex, and Caesar derive `kind` from their params, a row can *leave* filter kind under the flag — typing a replacement makes Search a transform. `inverted()` folds the kind test in, so a stray flag from a hand-written `?search=a&replace=b&not` is inert everywhere rather than honored by one reader and ignored by another. `decodeRows` normalizes it away after the whole query is parsed (not at the `not` key, which is read before the later `replace=` lands), and the UI clears it whenever a row leaves filter kind — so a `not` in a shared URL always describes what actually ran.

**Grouped filters negate the stage, not the member.** `runGroupFilterStage`'s plain contract is *keep the cluster if **any** member matches*; inverted, it drops any cluster the tool touched — De Morgan on the stage. Negating per-member instead reads `any(!match)`, which is true of nearly every cluster and would filter nothing while the row looked active. Every survivor is then a non-matcher, so the members carry `matched: true` to opt out of the score-range orphan gate (there is no match left for the range to hide).

Nothing else moves: an inverted filter is still `kind: 'filter'`, so `streamPlan` picks the same flat tier and the worker protocol is untouched. `invert` rides the wire in `serializeStack`, which puts it in the prefix-cache key for free (`resultCacheKey` is `JSON.stringify(serialized)`) — omit it there and toggling would silently reuse a stale tile.

**The affordance is a dedicated button, redundantly cued.** Invert is a standalone icon button — a `⊘` ban glyph (`#icon-ban`) — in the row's right-side cluster, just left of the remove `✕`; it's a real button (focusable, `aria-pressed`, tooltip), and the tool's label is inert. A visible control is the whole point: the mode reads at a glance instead of hiding behind a gesture on the label. It stays unobtrusive — faint at rest, red (`#e53935`) when active, hover only shifting the icon color, no border or fill — and that red echoes a **second, redundant cue** on the tool's own icon, where a row-level `.inverted` class draws the same red slash and desaturates the glyph. (The slash is the icon's `::after` and the grayscale sits on an inner `.tool-row-icon-glyph` span, so the desaturating filter doesn't grey the slash — put both on one element and the red goes grey.) The button renders on every filter-*capable* tool and greys when params currently make the row a transform; `syncInvertState` flips its `active`/`disabled` state and the row's `.inverted` class in place per keystroke rather than re-rendering, so the search bar keeps focus. The permanent Search bar has no remove, so it reserves that column with an invisible `.tool-row-remove-placeholder`, landing every row's invert button on one vertical line — and since a user-added Search/Regex row already carries both an invert button and a real `✕`, that reserved column is no new worst-case width. On a tight phone the bar's input floors to `minmax(64px, auto)` so the button stays on-screen, and the invisible placeholder is the first thing to clip.

## Inverting a transform's direction

**A word-argument tool denotes a binary relation, and `reverse` runs its converse.** Add-a-prefix and remove-a-prefix are the same relation read two ways, so they collapse to one tool with a `row.reverse` flag — the companion to filter-invert's `row.invert`, but flipping *direction* (a→b becomes b→a) rather than *sense* (keep→drop). A tool opts in with `reversible: true`, and `row.reversed()` gates on it so a stray flag on a non-reversible tool stays inert, exactly as `inverted()` gates on kind. The flag threads through the same readers `inverted()` does — `currentAtomCount`, `chainProducesMultiAtom`, the emit path, `flat-highlight.js` — plus `ctx.reversed`, which a tool's `prepare` branches on. It rides `serializeStack` (so the worker runs the right direction and the prefix-cache key can't reuse a stale tile); the URL names the direction with the tool's reverse slug (below).

**Reversing swaps which side highlights.** The converse of a front-cut that marks the removed span in its *input* is a front-grow that marks the added span in its *output*, so `inputHi()`/`outputHi()` on the row return the swapped `def` sides when reversed — the atom-count math reads those, never `def.input` directly, or it reserves a slot on the wrong atom and rows overlap. A reversed transform is still a transform and a reversed filter still a filter, so `streamPlan` and the worker protocol are untouched.

**Invertible means an endo-relation on the wordlist — the engine doesn't enforce it.** Each tool checks `norms` before it emits, so both ends of the relation are real entries; that is what makes the converse walkable. Rebus and Search/Regex-with-Allow-unlisted synthesize outputs that needn't be in the list (`executor.js` falls back to a synthetic wlEntry on a `norms` miss), so they have no clean converse and aren't reversible. A second bar: the input has to be a direction-independent *parameter* (the affix pattern), not one of the relation's operands — a subsequence tool like Kangaroos, whose input is the small word one direction and the big word the other, would silently change what it means on a flip, so it stays one-directional.

**Head off and Back off take a full Search pattern, which is what merged them with the affixes.** A count is just N `?`s, so "remove N letters" and "remove the string *can*" are one operation over a `buildSearchPattern` argument — `can`, `???`, `c??`, `*`, `[bpt]`, `@`. Cut matches the pattern against the front (or back) segment, removes it, and keeps the remainder if it is an entry; a `*` makes cut multivalued (several prefix lengths match). The reverse — growing the word — builds a reverse index over the corpus once in `prepare`, each word keyed by the entry it would grow *from*, so `run` is an O(1) lookup, with `*` the heavy path (every split, not one fixed length). This collapses the four pre-merge prefix/suffix tools into **two** cards (Head off ⇄ Head on, Back off ⇄ Back on), the reduce-the-gallery goal. Back off keeps the plural→singular skip for a wildcard cut but not a literal `s` (the user asked for that character). There is no default pattern — an empty Head off is inert, like Search.

**The affordance is a dedicated ⇄ button.** A reversible tool's row shows a swap button in the same row slot a filter's invert 🚫 button takes — they never collide, since every reversible tool is a transform and invert is a filter affordance — styled like it and accent-colored when active. Clicking toggles direction: the row's name swaps to the reversed pair (Head off ⇄ Head on, Back off ⇄ Back on) while its icon (🍈, 🍑) stays put — the icon marks the tool, the name its direction — and the tooltip names the direction the click would switch to. **URL: two tool names, not a flag.** A reversed row encodes under its reverse slug — `?head_on=can`, `?back_on=s` — so the link reads as the direction on screen, and decode maps that slug back to (tool, reverse); a forward row keeps the base slug (`?head_off=can`). The retired pre-rename slugs live on as decode aliases — the count keys `behead`/`curtail`, plus `add_prefix`/`remove_prefix` → `head_off` and `add_suffix`/`remove_suffix` → `back_off`, each with its direction — so links shared before the rename still resolve; the count keys digit-migrate (`?behead=3` → `???`) while the affix values ride through literal (bare integers are literal patterns now).

## Cooperative runtime — supersession and yielding

`runPipeline(mergedWordlist, stack)` wraps `executePipeline` with supersession and a slow-run indicator. Refresh sites (keystroke in a tool input or the search bar, view entry, gallery click) call it fire-and-forget; the promise resolves to `{rows, atomCount, aborted}` and a caller that sees `aborted: true` drops the result silently.

**Supersession.** A module-level `AbortController` tracks the in-flight run. Each new call aborts the previous controller before starting its own, so a fast typist's stale runs unwind at their next yield point and only the latest reaches the scroller.

**One yield gate per run.** `makeYielder` builds a cooperative-yield gate at the start of each run, shared by every O(N) pass it covers — the per-row loop, the `unify` pass, and a tool's `prepare` (through `ctx`). `due()` is a cheap synchronous check; once it reports the run has held the thread past ~6ms — about half a 60Hz frame — the caller `await`s `yield()`, which returns control to input and paint via `scheduler.yield()` (with a `setTimeout(0)` fallback) and abort-throws if the run was superseded, so a stale run unwinds without per-call bail-out code.

`due()` can't afford to read `performance.now()` every iteration, so it samples the clock once per `stride` calls and retunes `stride` after each sample to keep the sampling interval near 1ms — a hot loop of cheap iterations samples rarely, an expensive one every iteration, with nothing for a caller to tune. Time-based rather than iteration-count: a heavy predicate and a trivial one take wildly different time per row, and pinning yields to wall-clock keeps the yield rate sane across both — a fixed iteration count would yield every ~1ms on a cheap 500K filter, burning hundreds of ms of pure overhead. `run` sees none of this — it's synchronous and per-row — but a `prepare` doing heavy work drives the same gate itself, via `ctx.forEach`/`ctx.times` or `ctx.due()`/`ctx.yield()`.

**Slow-run indicator.** One global signal: the entries panel gains `.pipeline-running` at the start of every run and loses it on completion or abort. The visible effects — fading the result list (`#vs-host`) to 0.55 opacity, revealing a spinner over the panel, and reserving 96px of vertical room for it — each carry a 100ms CSS `animation-delay`, so a run that adds and removes the class inside that window cancels the animations before they start and nothing flashes on fast keystrokes. CSS-driven rather than a JS `setTimeout` because `scheduler.yield()`'s continuations outrank lower-priority tasks and starve a JS-driven slow-indicator timer on CPU-bound runs; the browser's render pipeline ticks between yields regardless of task priority, so an animation-delay reveal triggers on wall-clock time even when the executor is hot. The threshold is the *whole run total*, not per-step — a long pipeline of individually-fast tools that sum past 100ms still trips it. One signal for the whole run rather than a per-tool spinner badge: the user cares that *results* are stale, not which row is slow. The dim lands on `#vs-host` rather than the panel itself so the spinner overlay stays at full opacity while the rows behind it fade.

**Tool errors.** Two channels feed one `⚠` affordance. An **execution error** — a thrown `def.prepare` / `def.run` / group key — is caught at the per-stage boundary in `executePipeline`, wrapped in a `ToolStageError` carrying the offending stack row, and re-thrown; `runPipeline` translates it into `{ errored: true, rows: [] }` so the caller clears the stale results rather than continuing to show them, and the failing row's `_error` field holds the message. A **parse error** — an invalid query the tool can't run, like a stray `.` in Umiaq or an unterminated group in Regex — is reported synchronously from params by an optional `def.error(params)` accessor (Umiaq hands back its parser message; Regex its `SyntaxError` reason, stripped of V8's `Invalid regular expression: /…/:` echo, which only repeats the pattern the user can already see), known *before* the row runs — which it won't, since the same invalidity also reports `isInert`. `ToolStack.refreshRowMarks()` runs after every pipeline run and shows the row's effective message (`_error || error()`) on the `⚠` icon — always rendered, hidden by default, anchored at the input's right edge (the input is pinned to its grid column so a caret-less tool doesn't strand the icon off to the right). On a hover device the message rides the button's `title`; on touch a click opens `ErrorPopover` (positioned on click, dismissed on outside-click or Escape). No debounce gates the reveal: the parser's deliberate `empty`-vs-`error` split already keeps a half-typed query (`AB;` → `empty`) quiet, so the icon tracks each keystroke without flashing while composing. A successful run clears `_error` at the top of `executePipeline`, and a fixed query drops `error()` to null, so the icon clears on the next run either way.

**First-paint covers the corpus build, not the tool pipeline.** The splash exists to cover the one thing main can't render around: the worker reading IndexedDB, parsing, rescoring, and merging the corpus. It should *not* cover the URL's tool pipeline — those tools have the slow-run spinner, and holding the splash through them kept it up for the entire run of a slow boot-URL tool (Space out, a heavy regex). So `renderMergedDetail` mounts the panel, *starts* the run, and fires `_signalFirstPaint()` immediately — before awaiting the result. The splash-drop is gated on `Promise.all([firstPaint, workerReady])`, so moving firstPaint ahead of the await makes `workerReady` (corpus built) the real gate: the splash lifts the moment the corpus is ready and hands off to the slow-run spinner, which is already revealed underneath. (`mountPanel` runs and `runPipeline` adds `.pipeline-running` while the splash is still up, so the spinner's reveal animation finishes behind it during the build — when the splash lifts the spinner is already there, no empty-with-no-spinner frame. Gating on corpus-ready rather than a fixed timer is what guarantees this: a timer could fire before the corpus and its spinner exist.) It drops onto an empty table with a spinner, not the unfiltered base list: a base-then-results swap would flash misleading content and force a base-tier sort reconcile that overwrites the link's sort. firstPaint stays **unconditional** — firing before the await means a slow or broken URL tool can only error inside the spinner-covered run, never strand the user on a forever-spinning splash. The one cost is a brief empty-table-with-spinner window between corpus-ready and first results on every boot; the 0.3s splash fade overlaps it on fast boots, and it's the honest "working" state on slow ones.

**Test bridge.** `__grawlixTest.pipelineIdle()` resolves when no run is in flight; `getVisibleEntries` awaits it before reading the DOM so test assertions after a keystroke don't race a not-yet-finished refresh.

**The pipeline runs in a web worker.** Cooperative yielding keeps the main thread *responsive* between chunks, but the compute still costs: a per-keystroke search or filter over a merged corpus of hundreds of thousands of entries is genuine work, and on real hardware it lagged typing — yielding hid the freeze but not the felt latency between keystrokes. Moving that work off-thread is what removes it. The whole executor (`executePipeline` and every tool's `run`/`prepare`/`group`) lives behind the worker boundary, importing the same DOM-free `engine/` the main thread would; in the steady state the main thread runs no pipeline code at all.

**The worker owns the corpus; main is a thin, asynchronous view.** The worker is the *sole* owner of the wordlist data — it reads each source's text from IndexedDB, parses, rescores, and merges it, builds every scoped view, runs the pipeline, and computes the stats/histograms. Main holds **no** merged or scoped corpus: only `state` (the small per-wordlist config — metadata, rescore rules, scoring tiers, enabled/order), the DOM, and the per-config summaries the worker ships. It syncs the config the worker needs (`syncConfig`) and **requests the rows it needs to render**. Because there is exactly one owner, there's no two-copy synchronization problem — the silent-divergence danger a "both sides keep a full copy" model carries simply doesn't exist; a mutation is a *command* to the one owner (`editEntry`/`deleteEntry`), not a reconciliation between two authorities. This is what removed the three freezes a main-resident corpus left behind: cold boot no longer reads/parses/merges every wordlist on main (the splash covers the worker doing it), a scope switch no longer re-ships a corpus across the boundary (the worker rebuilds the scope from its resident sources synchronously), and a fetch/import no longer freezes the tab rebuilding on main (the worker absorbs the change off-thread — splicing just the changed norms in place for a typical update, see *A re-fetch costs the diff* below). It also empties main's heap of the bulk data, relieving the stale-tab GC jank — a *main-thread* problem, since GC pauses freeze the UI — at the cost of roughly **1×** peak corpus memory living in the worker, where GC doesn't jank the UI. (Total cross-thread footprint is about unchanged; main's is what matters.) The standing risk this design takes on is that rendering is now **asynchronous** — the scroller can't read a local array, it fetches windows — so getting the prefetch-and-placeholder behavior smooth is the central engineering task, addressed by the windowing below.

The design sidesteps the costs that sank the naïve "ship the whole corpus" version, and never ships the corpus as bulk data at all. No result crosses as bulk either — **every tier is windowed, in one uniform shape**: the worker owns the full sorted result and ships only a count plus an inline first window of rich rows, serving later windows on demand, so even a one-letter query matching the whole corpus returns ~60 rows and a number, not a million. There is no special binary transport for any tier. A worker **crash respawns + rebuilds from IDB + re-dispatches** — there is no main-thread engine fallback, because main holds no corpus to run against. The interface contract — data ownership, every message, the cancellation/supersession rules — lives in [`worker-protocol.md`](worker-protocol.md).

**All three result tiers are windowed off the worker.** The flat scroller renders only its visible window of rows, fetched from the worker (`fetchRows`) into a bounded local cache seeded from an inline first window the result ships, with shimmer skeletons on the rare miss; export and the entry panel read the owned corpus the same way. The grouped tier windows the same way, but at **two levels**, because a grouped result is a list of group rows and each group holds a list of chains — and either dimension can be the size that freezes main. The freeze the grouped tier had to solve was main decoding *every* group up front: a letter-bank-`*` result over a 300K-entry corpus is ~53k groups (most of them small — only a handful exceed a few dozen chains), so capping the chains *per group* did nothing — the structured-clone and decode of the whole group-row list was the cost. The fix windows the group-ROW list (the worker ships the first window of group rows plus the total group count; main fetches more group rows on scroll, sizing the scroller from the count) *and*, within each group, windows the chains (each shipped group carries a `firstChains` window; the "+N more" popover fetches a group's later chains on demand). The worker owns, sorts, and filters the grouped corpus and retains the full sorted+filtered list to serve those fetches — for the common single-key group **index-packed** (a member kept as a corpus index, rebuilt into a display object only for the fetched window, so the ~53k-group result is tens of bytes per member rather than the eager atom object graph; the "+N more" reveal then defers a group's member *retention*, not just its shipping), see § *Streaming results* — and ships the result-level stats/histogram/width-hints computed over all groups, since main never holds the full list. Within-group chain order is the designed seed order (alphabetical-by-seed under Entry, seed-score-descending otherwise) on every render, filtered or not — the worker sorts groups and chains into final order before windowing. The **transform tier windows like the flat tier** (a one-level chain list): the worker sorts and filters the chains, retains the full list, and ships a `firstChains` window plus a `chainCount` and the result-level summaries, serving later windows via `fetchTransformRows`. Transform results are usually small — they self-filter hard (anagram/head-off emit only on merged-corpus hits) — but the old fully-materialized path rested on that staying true; windowing it removes the latent main-thread freeze a future less-selective transform would otherwise reintroduce, and makes all three tiers uniform (the worker sorts every tier; main sorts none).

Because the worker owns the sort and the filter, a **sort-axis or score-range change is a view reprojection, not a re-run** — the worker re-derives the view over its retained join and re-windows, uniformly across all three tiers, rather than re-sorting a local array on main (main sorts none). See § *Streaming results*, "Sort and score-range are view refinements".

**A re-fetch costs the diff, not the wordlist.** A mutation to the corpus is a *command* to the one owner, not a reconciliation between two copies — and the worker applies it **in place**, splicing only the affected norms rather than rebuilding. A My Edits edit, add, or delete (`editEntry`/`deleteEntry`) re-merges just its one or two norms; a re-fetch or re-import (`applyFetched`) is the same splice batched. The periodic publisher update is the case that pays off: a maintainer adds some entries and retunes some scores, the bulk untouched, and reprocessing the whole list end to end — parse, rescore, re-merge every entry, re-run the pipeline, repaint — was paying list-sized cost for a diff-sized change. Now main ships the new text to the worker, which diffs it against its resident copy in one O(n) pass keyed by entry (added / removed / score-or-comment-changed) and patches only those norms through the splice path. The payoff is as much *not interrupting the page* as raw speed: patching the changed norms in place leaves the current search, scroll, and on-screen rows undisturbed, where a full reprocess re-runs and repaints. A **structural-change cap** keeps it from ever costing more than before. Only *adds and deletes* count toward it: a rescore splices in place (an equal-length array overwrite, no shift, O(1)), so any number of retuned scores stays on the cheap path, but an add or delete shifts the merged array (O(n) each) — so the cost is O(structural × n), and past an *absolute* cap (256 adds/deletes; a *fraction* of the list would permit O(n²) work and freeze on a large one) it falls back to rebuilding the merge wholesale off the *resident* sources, still cheaper than the old path that re-read and re-merged every source from IDB. The diff measures cheaply and bails the instant it crosses the cap — past that point the rebuild ignores the per-norm detail, so finishing the scan would be wasted work. A fresh import has no previous version, so it degenerates to that rebuild behind a near-free check; a config change riding the same import — a first population, an enable flip, an auto-seeded rule — falls back to the full resync that re-sends the changed config. So the common "mostly the same" update gets dramatically cheaper and non-interrupting, while the worst cases match what they cost before.

## Streaming results

A run whose final stage is **streamed-out** paints its results into the table as the worker finds them, instead of blanking until the whole run finishes — a slow flat search over a 750K corpus and a long Umiaq run both accumulate visibly. Whether a run streams is a property of the tool stack, not a per-run flag: each tool *kind* carries fixed input/output modes — a filter or transform is streamed on both sides, a group tool is buffered on both (a bucket isn't final until the whole input is seen), and the tuple producer ([`umiaq.md`](umiaq.md) § *How the tool runs*) is **buffered-in, streamed-out** (once the candidate pool is fixed, every tuple the join finds is final). The rule that falls out: **results stream when the last non-inert tool is streamed-out.** `streamPlan(stack)` reads it off the stack and names the producing stage. Three stages stream in practice — a filter-only flat search (the trailing search bar), a tuple search (Umiaq, Weave), and a transform when it's the last non-inert tool. A transform's catch is that the `unify` mirror-fold (§ Symmetric unification) is a whole-set barrier, so the worker folds **online** instead: as each mirror arrives it promotes the already-painted row's glyph to `↔` in place rather than appending a second row and collapsing later, so the painted count only ever grows. The retained direction is already canonical — the corpus emits in norm order, so the lexicographically-smaller norm-join direction always arrives first, which is exactly the survivor `unify` keeps — so the stream is exact-final and completion **adopts** it (no re-derive, no end-of-stream word-order flip), byte-identical to a buffered run. A filter chained *after* a transform stays buffered (the transform is no longer the last non-inert tool). When a filter follows the tuple search, the tuple producer is still the producer; the filter runs per-batch inside its emit path (`streamPlan` returns it as a `downstream` stage), so each streamed batch is already the filtered set. Because the tuple search is buffered-in, it scans the whole corpus before its first tuple — a visible gap of around a second — so the streaming state (empty table, live dots) is shown from **dispatch** rather than from that first batch; otherwise the prior result would sit on screen, dimmed but readable, looking current for the gap. A streamed-out filter has no such gap (its first survivors stream within a yield), so only the tuple tier triggers the eager clear.

The producing stage emits batches at the executor's cooperative-yield boundaries (§ *Cooperative runtime*), and the worker posts each as a **versioned snapshot** ahead of the terminal `result`: `partial` for the flat tier, `partialGroups` for the tuple tier, `partialChains` for the transform tier. All three carry the **same shape** — a sorted window of rows plus cumulative stats/histogram summaries — so one streaming-render path on main serves every tier. The snapshot is **sorted throughout** — each is the active sort applied to the results-so-far, so the table reshuffles toward the final order as better matches arrive rather than painting arrival order. This is what lets a mid-stream scroll always land on a coherently-ordered window (and is why the scroller drops a fetched window whose snapshot `version` the order has moved past — without it a mid-stream scroll could paint a torn, mixed-snapshot view). Arrival order was the originally-sketched simpler model; it lost because a window fetched mid-stream would reshuffle out from under the user on the next snapshot.

**The streamed window tracks the viewport, and rows reconcile in place.** The window a snapshot carries isn't fixed to the top of the list — the scroller reports its visible range to the worker (a `viewport` message), so each snapshot ships the rows the user is actually looking at. A reader scrolled deep into a long run watches *their* rows fill in, not just the head. Between snapshots the scroller holds its scrolled-away windows (stale-while-revalidate) rather than blanking to skeletons each batch — the cache clears only on a fresh run. And the scroller **reconciles** rather than rebuilds: a row whose rendered HTML is unchanged keeps its exact DOM node across snapshots. That's load-bearing for interaction under a stream — a wholesale clear-and-rebuild swaps a row's node out between a click's mousedown and mouseup, so the click fires on the bare sizer (their common ancestor) and silently resolves to nothing; keeping the node lets the click land, and lets hover and text selection survive too. Only genuinely-changed rows repaint, which also drops the flicker a per-batch rebuild produced.

Completion is **seamless**: the worker merges each batch into a running sorted result with a **total** comparator — the flat tier tiebreaks to the unique corpus index, the tuple and transform tiers to the unique joined atom-norm key (the transform additionally folding each mirror online to its canonical survivor) — so the incremental merge equals a from-scratch sort, and the terminal `result` **adopts** the exact order the stream painted with no end-of-stream reshuffle or recompute. A client may ignore every snapshot and still get a correct final result; the snapshots are a progressive-paint optimization, not the source of truth. The streamed stats bar updates live — every tier consumes the cumulative stats the worker ships per snapshot, since main holds no resident scores to recompute from.

On the main side the settled result **is** the frozen final snapshot: there is one render path for streaming and settled (a 12-entry run is just a one-snapshot stream), and no completion recompute of rows. At completion main **keeps** the stream's window cache for every tier — each stream is already final order, so the cache holds the right rows — rather than re-seeding it from the top window, so a viewport scrolled away from the top doesn't blank to skeletons at the hand-off. One consequence the collapse accepts: because no tier keeps resident scores, the one-frame transient where a scope switch's new histogram layout lands before the run's counts re-stamp renders an all-zero histogram for that frame (the worker's next snapshot or result fills it) rather than recomputing locally. The wire contract for all three snapshot messages is in [`worker-protocol.md`](worker-protocol.md).

**Sort and score-range are view refinements, not new joins.** The expensive part of a run is the *join* — the flat scan, the tuple search, the transform fold. The worker retains it **unfiltered and order-agnostic** (the *join* set) alongside the sorted+filtered projection the table shows (the *view*). A sort click or a score-range change is a pure **view** change: the worker re-derives sort → filter → window over the retained join and ships a `reprojected` snapshot, **never re-running the join** — settled, or mid-stream (the running emitter reads the mutated sort/filter for its later batches too, so the stream keeps climbing under the new view). This is why changing the filter while a slow Umiaq streams no longer restarts it, and why the histogram — bucketed over the unfiltered join — stays put under a sort/filter change (only a *join* change moves it). A set-preserving rescore rides the same path: the corpus is spliced in place, so the join stays valid and the edit reprojects with the new scores rather than re-joining; only a structural edit (a genuinely new or removed row) re-runs. That the terminal only *adopts* the streamed result is what makes this sound — the retained result already is the truth, so there is a stable join to re-project. The wire contract is `reproject` in [`worker-protocol.md`](worker-protocol.md).

**Finished joins survive across runs, not just within one.** Reprojection reuses a join only while it's the *displayed* result — navigate to another tool and back, or re-type the same query, and without a cache the pipeline re-joins from zero. The **finished result cache** extends the retention: the worker keeps an N-entry cache of finished joins that outlives the three display slots, keyed `(scope, stack-signature)`, so re-entering an identical pipeline against an unchanged corpus serves instantly. It is the same join/view machinery — a hit rehydrates a display slot from the retained join and reprojects it to the run's requested sort/filter — so a served result is byte-identical to a fresh finish and rides the same non-streamed terminal path (carrying the terminal-only `capped`/exists/rebind echoes; it is *not* a reproject snapshot). A hit **recomputes** every score-derived summary rather than reusing a stored one, because an in-place score edit can mutate the retained join's scores under it.

The cache is **tool-kind-blind** — flat, grouped, and transform joins are all eligible. The earlier plan to cache the buffered tiers and skip flat was dropped once the properties it stood in for (boundedness, cost, position-coupling) turned out to be per-*tool*, not per-*tier*: a flat run is excluded on cost by the time floor without naming a tier, and its position-coupled indices go stale on exactly the structural change the invalidation model already catches. Admission gates on a **recompute-time floor** (`RESULT_CACHE_MIN_MS`) — but applied to the result's **derive-from-tile cost**, the work *past the longest prefix tile* (the trailing stages plus the display projection, `lastPipelineTailMs`), not the whole run. A result a prefix tile already makes cheap to reproduce — an expensive producer followed by a cheap terminal, the common Umiaq shape — clears the floor on total run time but *not* on this marginal cost, so it is **not** stored a second time: the tile is the single source of truth and the finished result is derived on demand (seed the tile, run the cheap suffix, project). This makes one rule govern tiles and finished results alike — cache a checkpoint only when reaching it from the nearest cheaper cached checkpoint took real time — the same principle the prefix cache's marginal-cost tiling already follows. The per-entry byte ceiling **equals the pool budget**: any entry that fits is admissible (a minute-long join is worth keeping, not jetsam to refuse for its size), and only an entry too large for the pool at all is refused. Under contention a byte-budgeted **GreedyDual-Size** policy (`H = clock + elapsed/bytes`) picks the victim — cost-aware LRU, where an expensive entry earns longevity but a never-revisited one ages out. Eviction is never a correctness concern (a bad choice only forces a recompute), so the policy is a tunable comparator, not load-bearing.

Validity needs **no generation counter and no content signature**. Each entry is bound to the corpus *object* it was built against, and serves only while that object is the resident, structurally-intact corpus — a synchronous identity test (`entry.corpus === ownedMerged`/`ownedCorpus`), scope-precise so a change to one scope never marks another's entry stale. The scope-freshness gate alone is insufficient — an in-scope rebuild passes it while swapping the corpus object — so identity, not the gate, catches the swap. A rebuild (config change, enable, reorder, rescore-rule edit, fetch) mints a new corpus object, which the identity test misses and a proactive purge drops; an in-place splice keeps the object but may swap row objects, so its `replaced` flag drives a keep-or-purge (a score/comment edit reconciles in place and keeps the entry — its next hit recomputes the moved scores; an add/delete restamps indices and purges). This reuses the object identity the worker already computes, which is the decisive reason the cache is **in-memory, not IndexedDB**: an IDB layer would have to design and keep correct a durable content-signature over everything a result is a pure function of (sources, rules, order, scoring, asset versions), and encode/decode a wire format on every access — where in-memory reprojects for free off the live join. IDB's unique wins (survive a reload, serve a single-list result cross-scope) are secondary to the dominant pain (revisit within a session after tab-hopping), so they are parked as a possible later durability layer beneath this one, not built. Two ideas stay deliberately deferred: the **coroutine** form of resuming an abandoned run — continue a suspended scan *without* redo, which pins an unmeasurable working set and would rewrite the "a superseded run posts nothing" invariant — and the pressure-adaptive floor. (The pragmatic form of that first idea — re-run and catch up, which keeps the invariant and a bounded, measurable partial join — ships as the partial-run cache below.) The cache is derived and disposable, so it is exempt from the migrate-don't-wipe policy and is lost whole on worker respawn.

**Editing or reusing a tool row reuses its untouched prefix.** The finished cache helps you *revisit* a query; a sibling **prefix-state cache** helps you *refine a pipeline* — build one expensive stack (a slow `[Umiaq]`, several stacked filters), then add, remove, reorder, revert a row, or type into the search bar, with every change snappy. The pipeline executor is buffered stage by stage, so the inter-stage `state` after every user-stack row exists mid-run; a run snapshots those states as **tiles** keyed by their prefix and seeds from the longest tile matching the current stack, rerunning only the suffix. **Every boundary is a uniform tile — no stage gets a privileged cache.** The state just before the search bar is simply the *longest* tile, admitted and evicted by the same rules as the rest, and that uniformity is exactly what makes the common moves reuse: typing in the search bar seeds the whole user stack (its last tile), adding a row on top seeds the previous stack (now a shorter prefix), editing a middle row seeds the prefix above it, reverting seeds the still-cached original. (This is why there is no separate pre-search slot: a privileged slot for the just-before-search state is dropped whenever the user stack changes, so "one slow tool, add one on top" — the most basic refine — would find nothing cached; the uniform tile is retained across that change and reused.) Tiles self-populate through ordinary incremental building and mid-run for a cold arrival at a long stack; the recompute-time floor keeps the cache inert for cheap stacks (fast to rerun anyway) and holds only prefixes worth reusing — so it doubles as the knob for keystroke latency on an expensive stack.

The load-bearing decision is to store the **executor `state`** (pre-terminal: `{ groups, grouped, laneKind, capped }`), *not* the finished display join. A finished join is post-`unify`/`collapse`/`cacheGroupStats` — a different shape per tier — so seeding a suffix from it would demand reconstructing the executor state and *proving* that reconstruction byte-identical to a cold run, the plan's flagged risk. Storing the raw state instead makes the equivalence **structural**: the seed is literally the object a cold run produces at that boundary, so running the suffix and finishing reproduces the cold result by construction, with no adapter to get wrong (the seed is cloned before the suffix mutates it — copy-on-replace, since a downstream stage replaces `g.chains` rather than editing it in place). Both caches are **`RoleCache`** views over one shared **`GdsCache`** pool (byte budget, GreedyDual-Size eviction, the corpus-object identity test and `replaced`-hook purge above): each role owns its recompute-time floor and per-entry ceiling, but they **share one budget and one eviction order** — a finished result can evict a prefix tile — rather than each hoarding a private allowance; the prefix cache prices `elapsed` as the **marginal** cost of a tile from the prior cut (greedy 1D tiling — cut once accumulated stage time clears the floor, coalescing a run of cheap stages, refusing a cheap trailing one), so a cheap follow-on stage mints no tile and GDS ages a redundant tail out before the prefix it would seed from. Seeding past a streaming producer runs **buffered** (the producer is already in the seed, so there is no per-batch emitter) — correct and fast, forgoing partials for the cheap refined suffix.

**Abandoning a slow streaming run and returning to it resumes where the eye left off.** The finished cache serves a run that *completed*; a third sibling — the **partial-run cache**, a third `RoleCache` view over the same shared `GdsCache` pool — serves one that didn't. When a streaming run is superseded (you judged a query from its first screenful and moved on, or set a slow scroll aside to detour through another tool), the run aborts as always — the "a superseded run posts nothing" invariant is untouched — but on its way out it **stashes its incomplete join** under the same `(scope, stack-signature)` key. Re-entering that exact query paints the stashed partial **instantly** and re-runs from the top, but the re-run's emitter stays **silent** — validating each row it reproduces against the stash and shipping nothing — until it catches back up past the abort point, so the count freezes under the spinner and then climbs rather than rewinding to zero. The re-run is deterministic against the unchanged corpus (the same determinism the finished cache's reproject relies on), so it reproduces the exact partial and continues past it; a row that *disagrees* can't occur once the corpus-identity check passed, so it's treated as corruption — drop the stash, run cold. **One join serves throughout** for the **flat and tuple** tiers, whose joins are append-only in scan order (flat by corpus index, tuple by group key): the stashed partial is a position-wise prefix of the re-run, so the emitter *validates* against a cursor rather than rebuilding, and the painted rows stay fully scrollable (no skeletons) while the count is frozen. The **transform** tier can't cursor-validate — its join is the post-fold survivor *set*, not scan order, and a fold mutates an already-painted glyph to ↔ — so it **rebuilds-and-swaps**: re-fold a transient survivor map behind the frozen paint, verify the set matches the stash at the survivor-count crossover (a mismatch — e.g. a kept score edit that flipped a mirror fold — drops the stash and runs cold), then swap the display to the live map and continue. The survivor *sequence* is deterministic (the corpus emits in norm order), so the swap reshuffles nothing, and a mirror straddling the abort point promotes its glyph live past the crossover rather than flickering on the frozen partial. It saves **perceived** latency, not compute — the re-run pays the full scan; the catch-up is redundant work hidden behind the frozen paint — so it is narrower than the finished cache, which saves the whole recompute. Admission is the **same recompute-time floor** the finished cache uses, which doubles as the gate: a per-keystroke transient aborts in milliseconds, below the floor, so `admit()` refuses the flood and no separate heuristic is needed. The one guard the finished cache doesn't need: because the stash fires *at the abort* — exactly where a reshaping My Edits edit that supersedes the run lands — a run whose corpus generation changed under it **refuses to stash**, since its join would span two corpus states that the object-identity test (same in-place-spliced object) can't tell apart.

## Symmetric unification

Semordnilap emits both `STRESSED → DESSERTS` and `DESSERTS → STRESSED`. The post-executor `unify` pass collapses such mirror pairs — rows that are exact reverses of each other, mirrored entries and mirrored scores — into a single row and promotes its relation glyph to `↔`, the natural glyph for "two one-way rows pointing at each other." (`unify` also does the within-row collapse of redundant same-word atoms — see § Highlights pipeline.) A downstream transform breaks the symmetry: `semordnilap → head_off` diverges the two directions (`STRESSED → DESSERTS → ESSERTS` is not the reverse of `DESSERTS → STRESSED → TRESSED`), so those rows fail the mirror test and stay separate with directed `→` glyphs. The tool author writes the dumb bidirectional emit; whether a pair dedupes is decided afterward, from whether the rows actually mirror once the full pipeline has run.

Of the two directions, the survivor is chosen explicitly — whichever entry chain sorts lexicographically smaller — so the result is deterministic regardless of the order the executor emitted the pair in. The survivor keeps its own direction's highlights; the dropped direction's are not carried over. (Carrying them — lighting both atoms from both directions' search hits — was considered and dropped: the carried highlight could land on an already-lit atom, which by the unification rule spawns an extra atom, letting a unified row outgrow the static atom count.)

Because search is a pipeline tool running *before* unification, this composes: searching `ss` on semordnilap output highlights `stre[ss]ed` on the surviving row's tail. A one-sided query — matching only one direction's tail — kills the other direction, leaving an un-mirrored lone row that stays a directed `→`. That degradation is the accepted cost of folding search into the pipeline rather than running it after unification; running it after would keep the `↔` but make search a special non-tool case.

`unify` runs only when the stack actually produces multi-atom rows — when some active stage is a transform or a highlighting filter. A filter-only chain leaves every row a lone atom, where both the mirror collapse and the within-row collapse are no-ops, so the executor skips the pass and returns its rows untouched. In a grouped pipeline `unify` runs *per group* — mirror collapse only makes sense within a single cluster, since cross-group mirrors aren't a thing the user is comparing.

## Chain-row display

Atoms render top-to-bottom on every viewport — there is no side-by-side layout at any width. The entries table is one CSS Grid per row with `grid-auto-rows`; each atom occupies one grid line (`count`, then `entry` / `len` / `score`), and lines past the first wrap onto their own grid row while staying column-aligned with the line above via shared `--entry-w` / `--len-w` / `--score-w` variables. The relation glyph prefixes every word-introducing atom's entry; a same-word repeat atom carries none. Row stride is atom count × row height; the virtual scroller reads the static atom count for its stride math, and the row's own height is content-driven by the grid.

Comment and Source columns appear on every chain shape — a one-atom row and a stacked multi-atom row alike — when the viewport has room, dropping staggered as it narrows (source first at <960px, then comment at <760px). They render per-atom: each atom line carries its own comment and source, so a chain row reads top-to-bottom as where every word in the journey comes from. A synthetic atom — built from a tool's `[string]` output, sourced from no wordlist — gets blank cells, and a coined one a dash in its score cell. Column visibility is pure CSS media-query gating; the renderer emits len / score / comment / source on every atom line, including same-word repeats — a Kangaroos + Search row shows the metadata on both highlight lines rather than leaving the second line's cells empty. Headers stay constant: the Entry / Length / Score labels describe what each *line* contains, not the row, so one header set serves every chain shape.

## Group-row display

A group row lays out the cluster's surviving chains **side-by-side**, with each chain rendered the way a flat chain row would — atoms stacked top-to-bottom (entry / score per atom-row), the relation glyph prefixing each word-introducing atom. The row's chrome (row number, Count, the anchor slot when present, group columns) lives on the row's first atom-row only; chains extend down from there. Row stride is `atomCount × ROW_HEIGHT` where `atomCount` is shared with flat chains via `currentAtomCount(stack)` — the cluster seed plus what every chained tool adds.

The shape mirrors flat chains intentionally: a group row reads as "many of those flat chains, clustered." There is no Length, Comment, or Source column on group chains — a cluster is about set membership and the per-chain atoms are already wider than a single flat atom — but everything else carries over: same `.atom-entry`/`.atom-score` spans, same `<mark>` highlight markup, same EntryPanel routing.

**Overflow truncates rather than scrolls.** A row wider than its `.group-chains` slot clips at the slot's right edge, ending in a `+N more` chip — `N` the count of chains past the edge — with a fade gradient ramping the last visible chain out beneath the chip. Clicking the chip opens a popover with all of the row's chains, the same chain shape, wrap-stacked. A group member is editable wherever it shows — a visible chain's atom or a hidden chain's atom in the popover — through the EntryPanel. The popover dismisses on Escape, an outside click, or a re-click of its chip; it renders in chunks (200 chains at a time, more loaded as the user scrolls to the bottom via an `IntersectionObserver` sentinel) so a multi-thousand-chain cluster opens without a freeze.

## Sort axes per tier

Axes split by the pipeline's shape — a filter-only chain, a chain with a transform, or a pipeline with a group tool — not by an output kind. `isFilterOnlyChain(stack)` and `isGroupChain(stack)` are the signals, plus `currentAtomCount(stack)` — a filter-only chain can still stack several atoms (three searches on one word), but they're all the same word and score, so the score-spread axes would be noise; only a transform gives a row genuinely distinct atoms to sort across. A transform that hides a side (§ *A row can hide the side it came from*) leaves a lone atom, where a spread is one number repeated, so it stays in the single-atom tier: the spread axes are earned by the **atom count**, not by the mere presence of a transform, which is what keeps the rule true for a hidden output as well as a hidden input.

- **Filter-only chains** (empty stack, searches, plain filters): Entry, Length, Score, Comment. Default Entry asc.
- **Chains with a transform:** Entry, Length, Min length, Max length, Min score, Max score, Comment. Default Entry asc — same default in every tier, so adding a transform never silently swaps the axis on the user, and the table holds still when one comes or goes. Min score is a click into the Score header's menu away for grid-filling "what's worth fishing out" passes. Length stays a first-atom axis (below); Min/Max length are its across-the-row twins, the shortest and longest atom of the chain, paralleling Min/Max score.

Comment owns its own column (single-axis, like Entry and Length), sorting on the first atom's comment text (`localeCompare`). The Sources column (merged `All Wordlists` view only) shows each entry's contributing wordlists as a row of icons rather than a single name, so it carries no sort axis — there's no one value to order by. Because the worker keys every source by `dbKey` and nothing sorts by name, it never carries the human label at all.
- **Grouped pipelines** (a group tool in the stack): Entry, Count, Min score, Max score, Min length, Max length. Default Entry asc. **With an anchor** (Initialisms): Entry's label and projection track the anchor (alphabetical by `anchor.norm`, labeled "Initialism"), and two extra axes register — `length` ("Initialism length", `anchor.norm.length`) and `score` ("Initialism score", `anchor.score`); those measure the anchor, distinct from the cluster-wide Min/Max length across the member entries.

**Column headers are the sort control** — there is no separate Sort-by control; the headers carry the whole story. Each header column owns an ordered set of axes (canonical first), filtered at render time to the axes the current tier actually has. A **single-axis column** sorts on a direct click: it flips direction when its axis is already active, else jumps to that axis ascending (`nextSortForColumn` over a `data-sort-axes` attribute `buildEntryHeadersHTML` stamps onto each cell, dispatched by a delegated listener on `.sticky-stack`). A **multi-axis column** instead opens `SortMenu` on click — an anchored listbox naming each of its axes (the active one marked with its direction arrow), with `aria-haspopup` advertising the popup; picking an axis switches to it ascending, or flips direction when it's already active. The bindings: Entry/Length/Score map to `entry`/`length`/`score`; once a transform promotes the tier the Length column also owns `min-length`/`max-length` and the Score column `max-score`, so their menus offer Length plus Min/Max length, and Min/Max score. In a grouped pipeline Count owns `count`, each group column owns its own key, the anchor header (Initialisms) owns `entry`/`length`/`score`, and the **Entries column owns `min-score`/`max-score`/`min-length`/`max-length`** — group rows carry no score or length column, so the cluster's aggregate scores and lengths live there (it also owns `entry` when no anchor has claimed that axis). **Every axis a tier has is reachable from some column.** Naming the menu rows by axis (not the column label) is what makes *which* sub-axis is active legible — the header arrow only marks *that* the column is the active sort. First-click direction is always ascending, uniform across columns, for predictability. The shared `applySortList` rebuilds the headers on every sort change so the header arrow and the menu's active mark never disagree. Headers are keyboard-focusable; Enter/Space sorts, or opens the menu, with focus restored across the rebuild. The single-vs-multi split is the deliberate gesture difference: a column with one way to sort acts immediately, a column with a choice asks which — surfacing the alternatives (Max score, the grouped Min/Max) on first click rather than behind a separate affordance, at the cost of one extra click to flip a multi-axis column's direction.

**A modifier-click — Shift, Ctrl, Alt, or Cmd, any of them — extends the sort instead of replacing it.** The clicked axis joins as the next-lower priority rather than becoming the sole sort, so you can sort by Count then break ties by Letters. The sort is an ordered list `[{key, dir}]` (`AppView.sortList`, the source of truth that `sortKey`/`sortDir` read `[0]` of); a plain click replaces it with a single entry, a modifier-click runs it through `extendSortList`. Modifier-clicking an axis already in the list flips just that level's direction; clicking a *sibling* axis of a column already in the list (Min ⇄ Max score) swaps in place, because a column shows one arrow and so owns at most one active axis. Once two or more levels are active each active header shows a small rank badge (①②…) beside its arrow — a lone sort shows just the arrow, so the simple case stays unadorned. The levels compose into one comparator through `composeSortAxis`: each pick runs at its own fixed direction in priority order, then the primary axis's built-in tiebreakers settle the rest, leaving `compareItems` and the per-tier axis tables untouched. The plain click that collapses back to a single sort is the fast common path; multi-sort is an undiscoverable, desktop-only power gesture (no touch equivalent — phones do without), made legible only by the badges once it's in use. The worker honors the list for **every tier** — the flat tier over its index-shaped `FLAT_SORT_AXES` copy, the grouped and transform tiers over the shared chain-axis tables in `engine/sort.js` (the same `SORT_AXES` main reads to label its headers, so the worker's order and the header's axis can't drift). No tier sorts on main.

*Entry* and *Length* project off the **first atom** — the merged-wordlist entry the row grew from — so the table holds its order when a tool is added: a filter or 1-output transform leaves every first atom in place, and the rows can't reshuffle. That first-atom *Length* is why the multi-atom tiers keep it even beside *Min/Max length*: it's the stable axis, the spread is the across-the-row read. *Min/Max score* and *Min/Max length* project across every atom; for filter-only chains *Score* and *Length* read the row's single word directly.

*Entry* sorts by **word family**, not raw alphabetical: inflectional relatives (`cat`/`cats`, `eat`/`ate`/`eaten`, `have`/`had a go at`) share a *family key* ([`engine/morphology.js`](../site/src/engine/morphology.js)) and sort adjacent, alphabetical within the family. The key is a per-row field (`entry.family`) that `assignFamilies` stamps after the merge, anchored against the list's own vocabulary so out-of-dictionary crossword fill still reduces to a base that's actually present; the axis falls back to `norm` for synthetic rows that carry no key. The key **groups but never collates**: being a morphological reduction it can name a spelling no row has (`AM band` reduces to `be band`, and the list holds no `be band`, `is band` or `were band`), which would file the whole family under a letter the user cannot account for. So a family sorts at its **anchor** — the alphabetically first member *visible in the current view*, article-stripped — with the family key riding as the second half of one composite primary so two families sharing an anchor stay contiguous under a second sort pick. Base forms get no preference: given `be nice` and `am nice` the family collates at `am nice`, because base forms are an internal artifact the user never sees. Per-view, not per-corpus, is deliberate: anchoring at a member the active filter has hidden is the same defect in smaller form. The consequence is that a family's position depends on which of its members are on screen, so a cluster can shift as a result streams in — accepted, because a position the user can't see the reason for is worse than one that moves. It supplants plain alphabetical outright — there is no A–Z Entry option — and reads as a smarter alphabetical, since relatives that already sat near each other in alphabetical order now cluster exactly. The grouping is inflection only (plurals, verb conjugations, articles); derivation (`red`/`redness`/`redden`) is deliberately out of scope. Each axis carries `{label, primary, tiebreakers}`. Flipping the user direction reverses the primary **and** any tiebreaker that omits its own `dir` — Entry's alphabetical-within-family order is such a tiebreaker (it continues the primary's ordering, not a ranking of ties), so descending reads as a full mirror, members included, rather than reversed clusters with their interiors left ascending. A tiebreaker that *declares* a direction keeps it regardless of the toggle, so short low-scoring junk doesn't float to the top of a tied bucket (longer > shorter, higher > lower, alphabetical asc as the final stable fallback).

**Collation reads letters, not spelling.** Every alphabetical comparison the sort makes compares norms first and falls back to the display only between two spellings of one norm (`collationKey`, [`engine/sort.js`](../site/src/engine/sort.js)): the family key, the anchor, the order within a family, and the final tiebreak on every other axis, in the flat, chain, and group tiers alike. The family key joins its reduced tokens without spaces, so `accounts payable` and `accountpayable` share one family, and spacing out a run-together entry leaves it where it sat. Download and Copy already write entries in norm order, so the table and its exports agree. A multi-word base need not lead its inflections (`lathers up` precedes `lather up`, as `ate` precedes `eat`), which follows from base forms being invisible to the user. Two gaps remain, and closing either needs the segmenter at corpus build: a leading article files a spaced entry under its next word (`the best` under B) while its bare twin `thebest` stays under T, and a mid-phrase inflection (`bagged it` / `baggedit`) reduces only where its words are visible.

The reducer behind the key is a small suffix-rule set (`-s`/`-es`/`-ies`/`-ed`/`-ing`, with consonant-undoubling) plus an *irregulars* map for the forms no rule reaches. That map is **Open English WordNet's `noun.exc` + `verb.exc`** (the maintained, CC BY 4.0 WordNet fork — [`engine/irregulars-data.js`](../site/src/engine/irregulars-data.js), regenerated by [`scripts/gen-irregulars.js`](../scripts/gen-irregulars.js): fetch the WNDB zip, reduce to the ~1,600 surface→base pairs a rule can't derive) plus a four-entry override for the forms its exception lists omit — the suppletions it models as separate lemmas (`people`→`person`, `women`→`woman`) and a couple of irregular plurals it lacks (`dice`, `bacteria`). Measured against the full merged corpus (~750k entries) it adds ~2,000 correct groupings rules-plus-curated alone missed — the long irregular tail (`octopus`/`octopi`, `focus`/`foci`, `brother`/`brethren`, `seraph`/`seraphim`, the Latin/Greek plurals) and, because `toNorm` strips hyphens to a single token, the lexicalized **non-trailing plurals** (`passerby`/`passersby`, `man-at-arms`/`men-at-arms`, `aide-de-camp`/`aides-de-camp`) that pluralize a head noun mid-word instead of at the end. (Open English WordNet over the frozen Princeton 3.1: the cleaner CC BY 4.0 license, and it resolves ambiguous plurals like `leaves`→`leaf` and `bases`→`basis` natively where Princeton's multi-base entries needed hand-correction; the ~690 ultra-obscure plurals it drops cost only ~260 groupings corpus-wide.)

Where several candidate stems are all present in the list, the reducer prefers one that is a **common English word** over a merely longer one, falling back to longest only when none are common. The `-ed`/`-ing` rules each emit a silent-e stem (`called`→`calle`, `calling`→`calle`) so genuine silent-e verbs recover their base (`hoped`→`hope`, `liking`→`like`); but in a ~750k crossword corpus that stem routinely coincides with an unrelated real entry one letter longer than the true base — the French `calle` sits right beside `call` — and on a pure length tiebreak it captures `called`/`calling` and splits them off `call`/`calls`. On the merged corpus ~330 verb families split this genuine way (a naive suffix-collision count runs to ~940, but most of that is junk fragments or *correct* homograph splits — `bared`→`bare`, `pined`→`pine`, whose `-ed`/`-ing` really do belong to a separate `-e` verb and must stay apart). The common-word signal is the **top 30,000 words** of the wordfreq `large_en` corpus — a build-time-derived slice (words only, frequencies dropped) of the *same* corpus space-out fetches in full at runtime for segmentation — generated into [`engine/common-words-data.js`](../site/src/engine/common-words-data.js) by [`scripts/gen-common-words.js`](../scripts/gen-common-words.js) (~80 KB gzipped) and **injected into the worker** (`configureCommonWords`) where families are computed, rather than statically imported by `morphology.js`, so the list rides the worker bundle alone and never the main bundle (which pulls `morphology` transitively via the every-layer `test-api` but reduces no tokens). So `call` (common) wins over `calle` (which isn't in the list) while `calle` keeps its own family, rejoining ~82% of the genuine splits. A *bigger* list does worse, not better: a full 100k-word dictionary repairs fewer, because it readmits obscure `-e` words (`faire`, `pointe`, `thorne`) as legitimate anchors — the frequency threshold is doing the work, so ~30k is the sweet spot, not a floor. Genuine silent-e verbs stay intact: `hope` and `hop` are both common, so length still breaks the tie to `hope`; out-of-dictionary fill stays intact too, since with no common candidate the longest-match fallback keeps the vocabulary anchoring. The one residual miss is an obscure `-e` verb whose shorter homograph is the common word (`rimed`→`rim`, not `rime`) — rare enough to accept. The tiebreak is a **static word list, never the entries' scores**: families stay a pure structural derivation, so a rescore never reshapes a family and the edit-splice stays norm-local (scoring `calle` up could otherwise silently re-key `called` two rows away).

Three more checks keep a stem from being a stranger. **Case:** a word the list only ever capitalizes is a name, so for a word the list writes lowercase it ranks below every lowercase candidate; otherwise a surname one letter longer than the true base captures the paradigm (`Goade` took `goaded`/`goading` from `goad`, `Cooke` took `cooking`, `Waite` took `waiting`). It's demoted, not excluded: a lowercase name plural (`beethovens`) still joins `Beethoven`, since nothing else can claim it. The vocabulary records this as a second set of the ~5% of words the list only capitalizes; a word absent from the list, such as one typed mid-rename, takes its case from the typing. **Dictionary:** a *common* word reduces only to a lowercase candidate that is itself common or a dictionary lemma. In a ~750k corpus nearly every stem has a junk fragment or name beside it, and a common word's true base is usually itself, so without this it keys to the fragment (`nothing`→`Noth`, `bus`→`BU`, `speed`→`spee`, `bring`→`bre`, `always`→`alway`). The lemma half keeps real bases outside the 30k (`depressing`→`depress`, `inverted`→`invert`). The guard applies to common words only, so it never bars obscure fill from anchoring, and it never acts as a tiebreak, so it doesn't readmit the obscure `-e` anchors a bigger common list would. The lemmas are **Open English WordNet's headwords**, generated as `LEMMA_BASES` beside the common list and filtered at build time to the ~700 a common word can reduce to: the rule consults no others, so WordNet's other ~68k would cost ~4 MB of worker heap for nothing. **Hand list:** a few non-inflections whose false base is a real lemma (`upstairs`/`upstair`, `pudding`/`pud`, `species`/`specie`) sit in `NOT_INFLECTED`. Measured on the default merge, the three repair ~380 words (~3,450 entries) and misfile ~57 (~80 entries), mostly rare words the list only capitalizes (`burke`, `dyke`) and recent coinages WordNet lacks (`phishing`, `fracking`). Like the tiebreak, none of it reads a score.

Three boundaries are deliberate, each chosen off that same corpus benchmark. **Nouns and verbs only** — WordNet's `adj.exc`/`adv.exc` degree forms are left out: they collide agent nouns with comparatives (`dryer`→*dry* would split *blow dryer* from *blow dryers*), collapse suppletive degrees (`good`/`better`/`best` into one family, dragging unrelated `The Best Day`-style titles along), and would group inconsistently anyway — `drier`/*dry* but not `taller`/*tall*, since regular `-er` has no rule and adding one over-fires (`corner`→*corn*, `boxer`→*box*). **The generated data is trimmed** to the rule-unreachable pairs; the regular doubled forms WordNet also lists (`abetted`→*abet*) are dropped because the suffix rules already reach them whenever the base is present, which in a large list it nearly always is. **Hyphens stay inside a token** rather than splitting it: tokenizing on hyphens would generalize past WordNet's known compounds, but on the corpus it breaks more than it fixes — it orphans the far more common solid↔hyphen plural pairs (`ack-ack`↔`ackacks`, `also-ran`↔`also-rans`) — so the win from `runners-up`-style phrases isn't worth the loss.

A multi-output transform (anagram) branches one input into rows that share their *whole* first atom — indistinguishable by any first-atom projection. Each first-atom tiebreaker chain replays the tool-less order (Entry's is alphabetical-within-family, riding the sort direction as above; Length's is score desc then entry asc), then ends with `rowChainTail` — the later atoms joined low-separator — so branches fall into alphabetical order by their own output. Under Entry that tail rides the direction too (it omits its `dir`, same convention as the family display), so a descending sort mirrors a single input's branches as well, not just the clusters around them; under Length the tail stays a fixed-asc fallback.

In a grouped pipeline the axes project off the whole group: Entry off the chains' seed atoms in display order, Count off the surviving chain count, Min/Max score and Min/Max length across every atom in every chain. The chains *within* a group are themselves ordered to match the **primary** axis — alphabetical-by-seed under Entry, seed-score-descending otherwise — and Entry holds them ascending regardless of the row direction, since the toggle reverses the rows, not the chains inside a cluster.

The URL drops `sort=` when the sort is just the tier default (`entry` asc, one level). A stack edit that flips the tier — adding or removing a transform or a group tool — never snaps the chosen axes to a tier default; it remaps them, level by level. `entry` exists in every tier and carries across untouched. `length` and `score` each ⇄ their across-the-row Min twin (`length` ⇄ `min-length`, `score` ⇄ `min-score`), and the Max form collapses back onto that same single axis when the row goes single-atom — the first-atom `length` axis itself also persists in the multi-atom tiers, coexisting with the spread, so a single→multi Length sort holds directly. `count` is group-only with no real counterpart, so it maps to `length` one-way — a magnitude sort surviving the group's dissolution rather than dropping to the default. Every axis survives a tier round-trip rather than being silently lost. `reconcileSort` applies this per level: a level with no counterpart in the new tier drops out, and if a remap collides two levels onto one axis the later one folds away, leaving the order otherwise intact. The tier default applies only when nothing survives, never as a snap-back when crossing a boundary, so the user's sort intent survives adding and removing tools. Each level's direction is preserved across a remap. The whole sort story is provisional — expect iteration now that the UI is live.

## Highlights pipeline

Search hits and tool-emitted highlights share one renderer and one channel: an atom's `highlights` is a flat list of `{ kind, start, end }` records in entry coordinates — or `null` when the atom is not a **highlight slot** at all (the originator, a plain transform output). A slot atom whose tool matched without producing any ranges holds `[]`, not `null`: `[]` still means "a slot, just empty." Each highlighting tool annotates its *own* atom — a search its same-word atom, a transform its input-mark atom (Head off's struck-through `removed` letters, Regex-replace's matched capture groups) or its output atom — so highlights from different tools never share an atom and never need merging. Tools emit those atoms unconditionally; `unify`'s `collapseRepeatAtoms` then folds adjacent same-word atoms together, **unless both are highlight slots** — that's the rule that collapses the originator into the first search yet leaves three searches as three distinct atoms. Keying the fold on slot-ness (`highlights !== null`) rather than on a non-empty array is what keeps a row's atom count equal to `currentAtomCount`'s static prediction even when a tool highlights only conditionally — a wildcard-only search matches every entry but produces no ranges, and its `[]`-holding atom must still count. Search is a tool, so its hits are baked into the chain like any tool's — `buildSearchPattern` exposes a `searchRanges(text)` function returning `search:N` records (one per matched literal run of the query — see *Literal-run highlighting* — the `N` cycling through the shared highlight palette — the same `--hl*` colors the tool gallery's category spines use); transforms like Head off emit `removed` ranges. `renderHighlightedText(text, ranges)` walks an atom's merged-and-sorted ranges once, emitting `<mark class="search-match search-match-N">` for `search:N` kinds and `<span class="hl-<kind>">` for tool kinds.

**Literal-run highlighting.** Both Search and Regex color the *literal runs* of a pattern — maximal stretches of verbatim literal characters — and leave wildcards dark. The premise: highlighting *locates and groups*, it never *reveals* (the entry text is fully visible regardless), so a wildcard position carries no information worth a colored band and a dark notch for it only costs contiguity. So a run breaks on every wildcard: Search's `* ? # @` and `[…]` classes, Regex's `.`, classes (`[…]`, `\d`…), quantified atoms, groups, alternation, and anchors. `c?t` (Search) and `c.t` (Regex) both light `c` and `t`, leaving the middle dark — the two tools stay consistent because they apply the same rule. `buildSearchPattern` wraps each literal run of the compiled query in a capture group; `analyzeRegexPattern` does the same for a regex body, except it first checks for the user's own capture groups and honors those instead when the pattern has any. Either way a match's `indices` expose the runs to `groupSpansToRanges`.

The Regex tool reuses the `search:N` channel on both sides rather than minting its own kinds. As a replace transform it builds the output itself (`runRegexReplace`, not `String.replace`, so it can record output offsets), and which side carries which color follows the same group/no-group split the filter side uses. **With capture groups**, it colors each capture group on the input atom and its `$N`/`$&` echoes on the output atom with the *same* color — rearranged letters visibly move between the two — and literal replacement text stays dark. **With no capture groups**, there is no cross-side flow to trace, so each side falls back to literal-run highlighting: the pattern's literal runs on the input atom, the replacement string's literal runs on the output atom, both cycling `search:N`. The input runs come from a separate run-wrapped highlight regex (`hlRe`) built alongside the functional one — the functional regex can't be run-wrapped because synthetic groups would renumber the user's `$N`. A `$&`/`$N` echo on the output stays dark in this regime: with nothing to pair it to, the literal text is what carries meaning.

Search-replace highlights differently from its filter mode: `runSearchReplace` does a literal whole-span substitution, so there are no literal runs to segment within a match. It marks the whole matched span on the input atom and the whole replacement span on the output atom — one `search:N` color per match, paired across the two so the swap reads at a glance.

The kind registry is open-ended — adding a new tool highlight kind is one (kind name, CSS rule) pair. `removed` is the only tool-emitted kind shipped today (line-through + 0.5 opacity); future kinds (`kept`, `inserted`, `shifted`) land as tools start producing them. Match and capture-group coloring did not need a new kind — the Regex tool reuses the `search:N` channel (see *Highlights pipeline*).

The `EntriesScroller` routes through `renderHighlightedText` for both pipeline hits and the at-rest list.

**Range positions carry their coordinate space.** Each range carries an implicit `coord` tag — `norm` for letter-pattern tools (Head off, Back off, Anagrams, …), `display` for Search's hits. Initialisms is display-aware but tags its own ranges `norm`, because it marks the initials of parts the segmenter cut out of the norm. The executor in `runToolStage` tags ranges as it appends them to atoms, so tools don't have to think about coordinates. At paint time `projectRangesToDisplay` projects `norm`-tagged ranges onto the display string via a per-wlEntry `Uint16Array` (norm index → display index), so a Head off range `[0, count]` lights up the right display characters even when the display has spaces or accents between the letters. Display-tagged ranges (Search hits) pass through unchanged.

On plain entries (`display === null`) the projection is the identity and the array is never built — near-zero cost on letter-only wordlists. On rich entries the array is built lazily and cached on `wlEntry._normMap`.

**A highlight re-derived at render time gets a `ctx`.** Both re-derivation paths — `compileFlatHighlighters` for the flat tier and `materializeGroupRow`'s `memberHighlights` for grouped members — run off the worker's *retained* result, outside the run that produced it, with no executor `ctx` in scope. Initialisms needs one: its marks come from the spacing table. So both take a `renderCtx(scope)` carrying the vocab and a **read-only peek** at the artifact cache, uncounted so a repaint never skews the cache's hit telemetry. A filter whose `prepare` is async or reads `ctx` (Initialisms is both) declares a sync `replay(params, ctx)` that rebuilds the same prepared value, since the render path cannot await — without it the compiler would ship a Promise as `prepared` and every mark would silently vanish.
